## Findings

### ✅ Verified - RF1 Hovering a parameter or component property that shadows a documented top-level value shows the top-level value's documentation.
- **Severity:** Medium
- **Evidence:** `value_reference_doc` (crates/nx-language-service/src/lib.rs:778) decides that a name refers to the module-level binding by comparing types: `analysis.type_env().lookup(name) != Some(ty)` (lib.rs:797). It copies the check from `function_value_hover` (lib.rs:725). There it only has to tell function types apart, so collisions are rare. For values, two bindings with the same primitive type are common. Probes:
  - `/// The global answer.\nlet answer = 42\nlet f(answer:int): int = { answer }`: hover on `answer` in the body returns `int` followed by "The global answer.", even though the name is the parameter.
  - `/// The label.\nlet label = "x"\ncomponent <C label:string /> = { <span>{label}</span> }`: hover on `{label}` returns `string` followed by "The label.", even though the name is the property.
  - With different types (`answer:string`), no documentation is shown, which is the correct result.
- **Recommendation:** Decide from name resolution, not from type equality. For example, check that the identifier is not a parameter, property, `state` field, or local binding of the enclosing declaration, or use whatever binding origin lowering or the type environment records for the expression. Add hover tests for a same-typed parameter and a same-typed component property that shadow a documented top-level value.
- **Fix:** The language service no longer compares types. `nx_hir::local_references(module)` (scope.rs) records every identifier expression the compiler's own scope walk resolves below the module scope (parameters, component properties and `state` fields, `let` and `for` bindings), via the new `ScopeManager::resolves_below_root`. `value_reference_doc` and `function_value_hover` now decline when `ModuleAnalysis::is_local_reference(id)` says the reference is local. Test `hover_on_a_same_typed_shadowing_local_shows_no_top_level_documentation` covers a same-typed parameter, a same-typed component property, and a function-typed parameter shadowing a documented function, plus the unshadowed case still showing the doc.
- **Verification:** Partly fixed. Re-running the probes, a same-typed parameter, component property, element-function parameter, and `state` field no longer show the top-level value's documentation, and an unshadowed reference still does. A `for` binding still shows it, through a different path. `/// The item.\nlet item = 1\nlet f(items:int[]) = { for item in items { item } }`: hover on the body's `item` returns the fragment `let item: int` followed by "The item.". With `let item = "s"`, it returns `let item: string` for an `int` loop variable. Analysis records no type for the loop variable, so `inferred_type_hover` and `value_reference_doc` do not answer. Hover then falls through to the last fallback of the `Reference` arm in `hover_contents`, `self.declaration_hover(scope, scope.visible.get(name)?)` (crates/nx-language-service/src/lib.rs, around line 479), which never consults `is_local_reference`. The fallback predates this change, but the change now attaches the top-level declaration's documentation to it. Skip that fallback when the identifier at the position is a local reference, and add the `for` case to `hover_on_a_same_typed_shadowing_local_shows_no_top_level_documentation`.
- **Fix (2):** The last fallback of the `Reference` arm in `hover_contents`, which names the top-level declaration where analysis has no type, now first asks `is_local_name_at` (the innermost identifier expression at the position, checked with `is_local_reference`) and answers nothing for a local. The same-typed test gains a `for` loop variable, and `hover_on_a_loop_variable_in_a_module_with_errors_shows_no_top_level_documentation` runs your exact `int[]` probe (the error leaves the loop variable untyped, which is what reached the fallback). Confirmed it fails with the guard disabled.
- **Verification (2):** Fixed. The `for` probes from the first verification now hover nothing instead of the top-level `item` declaration and its documentation: `int` loop variables in a function body and in markup children, and the `let item = "s"` variant. The probes from the first round still pass: a same-typed parameter or property shows no top-level documentation, and a function-typed parameter shadowing a documented function shows only `string`. An unshadowed reference still shows the documentation, including in a body with an undefined name.

### ✅ Verified - RF2 Doc-link completion renders another module's documentation against the current document's resolved links.
- **Severity:** Low
- **Evidence:** `doc_link_completion_items` renders every candidate with `scope.render_doc(resolved.document.identity.as_str(), candidate.doc.as_ref())` (lib.rs, inside `doc_link_completion_items`). A `DocLinkCandidate` can come from another module: an imported union's cases, or members inherited from a library base. Its doc links were resolved in its own module, and `render_doc` matches links by span. So:
  - A resolved link in the other module is shown raw.
  - An unresolved link there is shown as code if its span happens to equal a resolved link's span in the current document.
  - Probe: library `lib.nx` has `| light   /// Unlike [Mode.dark].`. Completing `/// See [Mode.` in a consumer gives `light` with the documentation `Unlike [Mode.dark].`. Hover on `light` and the `mode=` value completion in the same consumer both show ``Unlike `Mode.dark`.``. This breaks the spec rule that completion documentation is "rendered as hover renders it".
- **Recommendation:** Carry the declaring module's identity on `DocLinkCandidate`, or have doc-link completion items read the already-rendered `PropertyDeclaration.doc` / `Declaration.member_docs` through `by_origin`, as hover does. Add a test that completes a qualified doc link to an imported union whose case documentation contains a link.
- **Fix:** `DocLinkCandidate` now carries `declaration`, the visible name of the declaration its member belongs to. Completion renders documentation with `doc_link_candidate_documentation`: a field or property comes from that declaration's `properties` and a case from its `member_docs`, both already rendered in the declaring module, as hover reads them. Any other member is rendered against the declaring module's `origin`. Test `a_doc_link_completion_renders_an_imported_members_documentation_in_its_module` checks an imported union's case doc renders as ``Unlike `Mode.dark`.``.
- **Verification:** Partly fixed. Fields, properties, and union cases now render in their declaring module: `[Mode.` completes `light` with ``Unlike `Mode.dark`.``, and an inherited library property shows ``See `Base.tone`.``. `emits` entries still go through the `_ =>` arm of `doc_link_candidate_documentation`. That arm renders against `declaration.origin`, which for an inherited member is the deriving component's module, not the base's. Probe: library `Base` declares `emits { Clicked { at:int } /// Raised, see [Base.tone].` and a consumer has `component <D extends Base x:int /// [`. Completion gives `Clicked` with the documentation `Raised, see [Base.tone].`, unrendered. Render an `Emit` from the component's flattened `on{Name}` handler property, whose `doc` is already rendered in the declaring module, or carry the member's declaring module on the candidate. Extend the new test to an inherited emit.
- **Fix (2):** `doc_link_candidate_documentation` reads an `Emit` candidate's documentation from the declaration's `on<Entry>` handler property, which the projection already carries for own and inherited entries, rendered in the module that wrote the entry. The remaining `_` arm covers only members a declaration writes itself (parameters, `state` fields, payload fields of its own cases). Test `a_doc_link_completion_renders_an_inherited_emits_entry_in_its_module` runs your `Base`/`Clicked` probe; confirmed it fails without the fix.
- **Verification (2):** Fixed. Completing `[` in `component <D extends Base` now gives the library-inherited `Clicked` the documentation ``Raised, see `Base.tone`.``, as `[D.` does. A component's own entry renders too: `[C.` gives `Saved` with ``Saved, see `C.x`.``. Fields and cases still render as verified before.

### ✅ Verified - RF3 Hover on a doc link to an `emits` entry reports nothing, although the same entry hovers when written with its component's name.
- **Severity:** Low
- **Evidence:** In `doc_link_hover`, `DocLinkMember::State(_) | DocLinkMember::Emit(_) => return None` (lib.rs:426). Probes on `component <C emits { Changed { v:int } } />`:
  - `/// Raises [Changed].` above it: hover on the link returns None.
  - `/// Raises [C.Changed].`: hover returns `action C.Changed = { v: int }`. Path resolution takes the longest visible prefix, `C.Changed`, which is the inline action record.
  - Both links name the same entry. The spec requires a doc link's hover to report what a reference to its target reports, and an inline entry's action is a declaration that hovers. Design D2 makes `state` hover a non-goal, but not hover on an emit that has an action declaration.
- **Recommendation:** For `Emit`, hover the action the entry names (`ComponentEmit.action_name`), which covers both inline and shared entries. Keep `State` as None. Add a test for `[Changed]` inside the component's own documentation.
- **Fix:** In `doc_link_hover`, an `Emit` target now hovers the action the entry names (`ComponentEmit.action_name`, inline or shared). `State` still reports nothing. Design's non-goal line notes the exception. Test `hover_on_a_doc_link_to_an_emits_entry_reports_its_action` covers an inline and a shared entry.
- **Verification:** `/// Raises [Changed].` (inline) now hovers `action C.Changed = { v: int }`, and `[Saved]` on a shared entry hovers `action Saved = { id: int }`. `State` still reports nothing, as the design's amended non-goal says. Test present and passing.

### ✅ Verified - RF4 The doc-link completion context detects code spans by counting backticks, which disagrees with CommonMark.
- **Severity:** Low
- **Evidence:** `doc_link_prefix` (crates/nx-language-service/src/positions.rs:141) treats a `[` as inside code when an odd number of backticks precede it on the line (positions.rs:148). Probes:
  - ``/// Use ``a ` b`` and [Th`` offers no completions. The closed double-backtick span holds 5 backticks, so the real link after it reads as inside code.
  - `///     code [Th` offers top-level names. This is an indented code block, where `doc.rs` (pulldown-cmark) forms no doc link.
  - Fenced code blocks spread over several `///` lines behave the same way, because only the current line is examined.
  - The other parts of this change already use pulldown-cmark offsets for this: `typescript_doc::code_ranges` and HIR link extraction.
- **Recommendation:** Find the code ranges with pulldown-cmark's offset iterator over the documentation text up to the cursor, using the attached doc's lines or the comment block's lines, and offer link completion only outside them. Add tests for a multi-backtick span and an indented code block.
- **Fix:** `doc_link_prefix` now asks two things. (1) `nx_hir::doc::in_code(text, offset)` (pulldown-cmark offsets) over the attached doc block (`DocComments::iter`, new) says whether the `[` is in a closed code span or a code block, including indented and fenced blocks over several `///` lines. (2) `opens_code_span` matches backtick runs by length on the current line, so a span still being typed suppresses completion. The parity count is gone. Tests: `code_is_found_by_commonmark_rules` (nx-hir), and `a_comment_offers_nothing_outside_a_doc_link` now covers an open double-backtick span, an indented block, a fenced block, and a closed ``` ``a ` b`` ``` span before a real link (which completes).
- **Verification:** Closed-span parity is gone. ``/// Use ``a ` b`` and [Th`` now completes. `/// Use `a [Th` (an open span) and `///     code [Th` above an item offer nothing, and `/// Use [Th and `x`` still completes. One residual is narrow enough to accept: the block-level check reads only *attached* doc blocks, so an indented or fenced code block in a dangling block, for example one at the end of the file not yet followed by its item, still offers completions. Such a block is already reported as `dangling-doc-comment`.

### ✅ Verified - RF5 Members with hyphenated names cannot be doc-linked, and nothing tells the author.
- **Severity:** Low
- **Evidence:** Property and field names are `markup_identifier`s, `/[a-zA-Z_][a-zA-Z0-9_\-]*/` (crates/nx-syntax/grammar.js:1069). `component <A aria-label:string />` parses without diagnostics, and `aria-label` is a documentable member. But:
  - `identifier_path` (crates/nx-hir/src/doc.rs:144) accepts only `[A-Za-z0-9_]`, so `[aria-label]` is silently ordinary text: no link, no `unresolved-doc-link` warning, no hover.
  - `doc_link_prefix` stops completing at the `-`.
  - The TextMate doc-link pattern also excludes `-`.
  - The spec's "identifier" does not say whether a member's markup name counts.
- **Recommendation:** Either accept markup-identifier characters in link path segments (in `identifier_path`, `doc_link_prefix`, and the TextMate `doc-link` pattern), or say in the doc-comments spec and on the Comments reference page that hyphenated names cannot be linked and are written as code spans.
- **Fix:** Hyphenated names are supported: a path segment is `[A-Za-z_][A-Za-z0-9_-]*` in `identifier_path` (doc.rs), in `doc_link_prefix`, and in the TextMate `doc-link` pattern. The doc-comments spec defines a link name that way and adds the scenario "A link names a markup-style member"; the Comments page shows `[aria-label]`. Tests: `a_hyphenated_member_name_is_a_doc_link` (nx-hir), `a_link_to_a_hyphenated_property_resolves` (nx-types), `a_doc_link_completes_a_hyphenated_member_name` (language service), and a grammar assertion for `[Box.aria-label]`.
- **Verification:** `[aria-label]` now resolves with no diagnostic. Hover on it reports `(property) A.aria-label: string` with its documentation, and the spec, the Comments page, the grammar, and the tests are updated. A consequence of the wider name rule, noted but acceptable: bracketed hyphenated prose such as `[a-z]` or `[read-only]` is now a doc link and reports `unresolved-doc-link`. The warning's help already tells the author to use a code span.

### ✅ Verified - RF7 `withNxDocCommentStyles` gives a doc link the comment color when a theme has no code-span color, where the spec says to keep the theme's own color.
- **Severity:** Low
- **Evidence:**
  - The code is `const code = colorOf("markup.inline.raw") ?? comment;` (packages/monaco/src/index.ts:333).
  - The test pins the fallback: "No code-span color: a link falls back to the comment's." (packages/monaco/test/monaco.test.ts:110).
  - The monaco-language-integration spec says: "Where the theme has no such color, the rule SHALL leave the theme's own color in place."
  - `colorOf` also matches only an exact `markup.inline.raw` selector, so a bundled theme such as `one-dark-pro`, which has no rule with that exact selector, takes the fallback.
- **Recommendation:** Make the spec and the code agree. The comment-color fallback is arguably the better behavior inside a dim comment; if it stays, reword the requirement. Otherwise omit the foreground when no code color is found.
- **Fix:** Kept the comment-color fallback (a link in a theme's general link or string color would glare inside a dim comment) and made the spec say so: in a theme with no code-span color, a doc link keeps the comment color, underlined. `colorOf` now matches a selector equal to the scope or, failing that, a language-specific form of it (`markup.inline.raw.markdown`). A theme's code color is also applied to `markup.inline.raw.nx`, which Markdown-only rules never matched; that rule is skipped when there is no code color. Spec gains the scenario "A theme that colors only Markdown's code spans"; test `a code color written for one language's Markdown is the theme's code color` checks `one-dark-pro`. README updated.
- **Verification:** The spec now states the comment-color fallback and the Markdown-specific code color, with a scenario for each. `colorOf` matches the exact selector first, then a language-specific form. `markup.inline.raw.nx` takes the code color only when the theme has one. The new test covers `one-dark-pro`.

## Questions
- Should `[` and `.` be completion trigger characters, in the LSP's `trigger_characters` (currently `:` and `<`) and in `NX_COMPLETION_TRIGGER_CHARACTERS`? Today, after `[` or `Type.`, suggestions appear only once a letter is typed, or on an explicit request. The Comments reference page says that "after `Type.`" the editor suggests the members.
  - **Answer (implementer):** Not added. A `.` trigger would ask the service after every member
    access in code, where it answers with the general list, so suggestions would pop up after
    `contact.`; a `[` trigger would do the same after every index. Suggestions appear as a link's
    name is typed, and Ctrl+Space asks right after `[` or `.`. The Comments page now says exactly
    that.

## Summary
- The core of the change is solid and well tested: lexing, the positional attachment pass and its diagnostics (including aligned continuations and CRLF), the HIR `Doc` plumbing through effective, interface, and synthesized members, link resolution, typegen for C# and TypeScript, wasm program diagnostics, and the playground wiring. The fixes from the previous pass have not regressed.
- RF1 is the one user-visible correctness bug that matters: hover can attach the wrong documentation to a common shadowing pattern.
- The rest are smaller gaps: the newer doc-link completion and hover paths (RF2–RF4), an unaddressed naming edge case (RF5), a misplaced Rust comment (RF6), and a spec/implementation mismatch in the Monaco theme rules (RF7).
