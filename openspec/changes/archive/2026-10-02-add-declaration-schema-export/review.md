## Findings

### ✅ Verified - RF1 `object` maps to `{}`, which admits `null`, but the runtime refuses `null` at an exactly-one `object` site
- **Severity:** Medium
- **Evidence:** `Shape::Object | Shape::Parameter => SchemaValue::Object(Vec::new())` (crates/nx-api/src/schema.rs:1096). The empty schema accepts `null`, but the TypeScript runtime's boundary does not. For `let f(value:object): object = { value }`, the arguments `{ "value": null }` pass Ajv against the input schema, and `callFunction` then fails with `nx-ir-boundary-type` ("Expected value to hold a value, got null"). The same happens for `let g(v:object+)` with `{ "v": [null] }` or `{ "v": [1, null] }`. This breaks the central contract that every input-valid value is accepted at the boundary ("Schemas agree with the runtimes' boundary", design D4). The spec's primitives requirement causes it: it says `{}` is right "because that is what a runtime accepts", which is not true. The agreement test cannot catch the mismatch because `sample()` turns `{}` into `{ any: [1] }` (bindings/wasm/test/schema-agreement.test.ts:225-227) and no argument fixture passes `null` at an `object` site. An unapplied generic record's parameter field (`Shape::Parameter`) has the same problem.
- **Recommendation:** Map an `object` item, and a type parameter left open, to a schema that excludes `null`, such as `{ "not": { "type": "null" } }`. Keep update records nullable through `nullable()` as they are now. Update the spec's primitive requirement and its "top type" scenario, the website mapping table and the wasm README sentence "`object` is `{}`", and regenerate the golden documents. Add corpus argument cases that the runtime must refuse, or a negative check that `null` at an exactly-one `object` site is invalid against the schema. Also have the generator try `null` for `{}`, so the agreement test would catch this widening.
- **Fix:** `object`, and a type parameter left open, now map to `{ "not": { "type": "null" } }`, which matches the runtime exactly: it refuses only a top-level `null` at an `object` site and takes arrays and objects whole (`any_value()` in schema.rs). An update record's clearable `object` field stays `anyOf [not-null, null]`. Updated the spec's primitives requirement and its scenario (now "The top type admits any value but null", with a `null` counter-case), the generic-record and host-supplied scenarios, design D4/D10/D11, tasks 2.9/3.5, the wasm README and the website mapping table, and regenerated the goldens. Rust test `object_admits_any_value_but_null`. The agreement generator now returns `null` for a schema that admits anything; a scratch run that put `{}` back failed with `nx-ir-boundary-type` on `primitives.nx echo`.
- **Verification:** Re-probed against the rebuilt module: `{ value: null }` and `object+` with `[null]` are now invalid against the input schema (`not` fails) and are exactly the values the runtime refuses, while `[null]`, `[]` and `[[null]]` at an `object` site validate and are accepted whole. Golden corpus, spec scenario, design, website table and wasm README all say `{ "not": { "type": "null" } }`; the generator returns `null` for an open schema, so a widening back to `{}` is caught. `object_admits_any_value_but_null` passes.

### ✅ Verified - RF2 An abstract-record site lists descendants from workspace modules the runtime never links
- **Severity:** Medium
- **Evidence:** `Program::descendants` walks every module in `self.modules`, which is every library module plus every root module of the artifact (crates/nx-api/src/schema.rs:396-423, 741-786). A workspace root module that nothing reachable imports still counts. Probe: workspace `main.nx` imports `base.nx` (`abstract type Base`, `type A extends Base`) and declares `let f(s:Base)`. A third module `other.nx`, imported by nobody, declares `type X extends Base`. The input schema of `f` is `anyOf [A, X]`. Arguments `{ s: { $type: "X", id: 1, x: "q" } }` are schema-valid, but with the program linked from the entry as the agreement test does (`linkNxIrProgram(entry, { resolve })`), `callFunction` refuses them with `nx-ir-boundary-type` ("Expected s to be a Base, got 'X'"). Design D6 justifies the closed world as "what `resolveSubtype` accepts", but the runtime accepts only linked modules. (Unimported registry libraries are correctly excluded, because `artifact.libraries` holds only selected libraries.)
- **Recommendation:** Limit the descendant set to the modules the runtime would link for the call. That is the transitive import closure of the entry module (or of the function's module, if hosts link from there) plus the linked libraries. Alternatively, state in the spec and the docs that the host must link every root module, and make the agreement test link that way. Add a Rust test and a corpus or agreement case with an unimported descendant module.
- **Status:** Left open; needs a design decision. A probe confirmed the finding and showed it is wider than reported: the runtime links only the modules the images *reference* (IR module tables list referenced modules, not imports), so a descendant in a module the entry **imports** but never references is refused too (`importedUnreferenced ["main.nx","base.nx"]` → "Expected s to be a Base, got 'X'"). Restricting descendants to the entry's import closure would therefore not be enough. Options: (a) have IR emission add every module that declares a descendant of an abstract type used at a function's boundary to that image's module table, so linking pulls it in (a codegen change; the schema rule stays as specified); (b) compute the exact linked set in `nx-api`, which means mirroring codegen's reference rules there; (c) narrow the spec to "the program's linked modules" and document that a host must link every module it wants recognized. (a) keeps the export simple and fixes the runtime gap for hand-written arguments too; it touches codegen, which this change scoped out.
- **Verification:** The Status note is accurate. With `main.nx` importing both `base.nx` and `other.nx` but never naming `X`, the build emits all three images, yet the program linked from `main.nx` still refuses `{ s: { $type: "X", … } }` with `nx-ir-boundary-type` ("Expected s to be a Base, got 'X'"), while the input schema lists `X`. So limiting descendants to the import closure would not close the gap. The finding stays open pending the design decision among the note's options.
- **Fix:** Option (a), chosen by the user. `nx-api` gained `program_artifact_boundary_subtype_modules`, which walks every function's parameter and result types (through fields, union cases, aliases, type arguments and the shapes extending an abstract record) and answers with the modules declaring a concrete subtype of each abstract record reached, using the export's own `Program::descendants`, so the schema and the link agree by construction. `CodegenProgram.boundary_subtype_modules` carries the list, and the entry module's emitter adds those modules to its module table after the modules it references (crates/nx-codegen/src/ir.rs). No other image changes, so library images stay program-independent; the existing IR tests, the conformance corpus and the .NET suite are unchanged. Tests: `the_modules_declaring_boundary_subtypes_are_the_ones_the_schemas_list` (nx-api: imported-unreferenced, unimported, reached through a field, none), `the_entry_lists_the_modules_that_declare_its_boundary_subtypes` (IR tables: entry `main.nx, base.nx, x.nx, y.nx`, `x.nx` lists only itself and `base.nx`), `a_subtype_declared_in_a_module_nothing_references_is_accepted_from_a_host` (Rust runtime), and a wasm agreement case validating and calling `f` with `$type` A, X and Y on the TypeScript runtime. Artifacts: a MODIFIED `nx-ir-format` requirement ("An artifact carries one module and names the modules it links against", with a new scenario), the export spec's descendants and agreement requirements, design D6 and new D14, the proposal, tasks 8.1–8.4, `docs/nx-ir-format.md` and the changelog. Full suites pass: Rust workspace 2,988, wasm SDK 115, Node SDK 35, IR runtime, `verify:packages`, .NET 172; clippy and fmt are clean.
- **Verification (fix):** Re-probed against the rebuilt module, linking from the entry with `linkNxIrProgram`. In both the unimported case and the imported-but-unreferenced case, `{ s: { $type: "X", … } }` is now schema-valid and accepted ("ok"), and so is `A`. Module tables, read from `prepareNxIrModule(...).artifact.modules`:
  - A program with no abstract boundary type keeps its table exactly (`main.nx` → `[main.nx, u.nx]`; the unimported `z.nx` is not added).
  - The `@nx/agent` library image is byte-identical (same SHA-1) whether or not the program declares a `ToolContext` subtype at a boundary; only the entry's table gains `@nx/agent/agent.nx`.
  - When the subtype module imports the entry, the tables are mutual (`main.nx` → `[main.nx, other.nx]`, `other.nx` → `[other.nx, main.nx]`), and linking and calls still succeed.
  - A host that emits or resolves only the modules it needed before (here `main.nx` and `base.nx`) now fails to link, with "Module 'main.nx' links against 'other.nx', which the resolver did not supply." This is inherent to option (a), and the nx-ir-format delta and `docs/nx-ir-format.md` document it. A host that resolves the modules each table names is unaffected.
  
  Suites pass: `nx-api` schema tests (71), `nx-codegen` (257), the Rust IR runtime tests, wasm SDK (115), Node SDK (35) and the IR runtime package; `openspec validate --strict` passes. The fix is verified. Two new issues it introduces or exposes are recorded below as RF8 and RF9.

### ✅ Verified - RF3 A computed default written as a member access is emitted as a constant-case `default`
- **Severity:** Low
- **Evidence:** `literal_default` maps any `Expr::Member { member, .. }` to `constant_case_default(shape, member)` and never looks at `base` (crates/nx-api/src/schema.rs:810). Probe: `type Status = active | paused`, `type Cfg = { paused:Status }`, `let f(c:Cfg, s:Status = { c.paused }): Status`. The input schema gives `s` the value `"default": "paused"`, but omitting `s` with `c.paused == "active"` returns `"active"`. The spec says that any default other than a literal or a constant-case reference "SHALL leave the field without a `default` keyword". The wrong `default` misleads a model about what omission means.
- **Recommendation:** Accept `Expr::Member` only when `base` names the site's union itself (for example an identifier that resolves to that union declaration), or rely on `Expr::ResolvedUnionCase` alone. Add a test for a computed default whose member name matches a case.
- **Fix:** `Expr::Member` now counts as a constant-case default only when its base is an identifier that resolves, in the declaring module, to the site's union itself (`site_union` + `resolve_name`); `ResolvedUnionCase` is unchanged. Rust test `a_member_access_default_is_a_constant_case_only_through_the_union` covers `{ c.paused }` (no `default`) beside `{Status.paused}` (`"default": "paused"`).
- **Verification:** `literal_default` now accepts `Expr::Member` only when its base is an identifier that resolves to the site's union (schema.rs `site_union` + `resolve_name`). Probe: `s:Status = { c.paused }` has no `default`, and `t:Status = {Status.paused}` keeps `"default": "paused"`. The new Rust test passes.

### ✅ Verified - RF8 A polymorphically recursive generic record at a function boundary overflows the stack, which now aborts IR emission
- **Severity:** Medium
- **Evidence:** For `type Box = { T:type v:T inner?:<Box T=<Box T=T /> /> }` and `let f(b:<Box T=int />): int = { 1 }`, the program builds. `functionSchema` then traps the wasm host. That latent problem predates the RF2 fix, and I missed it in the first review. Since RF2, `generateNxIr()` also traps (`NxHostCrashedError` in `nx_wasm_program_nx_ir`), and `nxlang codegen main.nx --target nx-ir` aborts with "thread 'main' has overflowed its stack". The same file emits fine with the CLI built from HEAD (`main.nxir` written), and emits fine after the fix when no function takes `Box` at its boundary. The cause: `BoundaryReach::visit_declared` (crates/nx-api/src/schema.rs) and the schema `Document` (`record_def`) key their visited sets on `Declared` with its type arguments. Each step nests the arguments one level deeper (`Box<int>`, `Box<Box<int>>`, …), so neither walk terminates. Because `build_codegen_program` now runs the boundary walk, a valid program that never asks for a schema can no longer be emitted.
- **Recommendation:** Make the boundary walk terminate independently of type arguments. For example, key `visited` on the declaration address and visit each argument shape separately: reachability of abstract records doesn't depend on which instantiation reaches them. In the schema `Document`, bound instantiation depth, or detect an instantiation that contains its own declaration, and report `schema-inexpressible-type` (or open the parameter to `any_value()`) instead of recursing. Add an nx-api test and an nx-codegen emission test with this `Box`.
- **Fix:** Both walks now end. `BoundaryReach::visit_declared` visits each declaration once whatever its type arguments, and visits the arguments on their own (an argument reaches only the fields its parameter types, so nothing is lost). In the schema builder, `record_def` describes an instantiation whose arguments apply the same record twice or more (`applications_of`) as the record named with no arguments, whose parameter fields take the `object` schema, which is what the runtime checks there since IR erases record type arguments. For the reviewer's `Box`, `f(b:<Box T=int />)` answers with five `$defs` (`Box_int`, `Box_Box_int`, `Box`, `Box_Box_object`, `Box_object`), and IR emission succeeds. Tests: `a_record_applied_to_itself_without_end_is_described_and_walked_in_finite_steps` (schema and walk), `a_record_applied_to_itself_without_end_emits` (IR), and `an_abstract_record_reached_through_a_type_argument_counts` (the argument is still visited). The rule is in the export spec's generic-record requirement (new scenario "A record applied to itself without end stays finite"), design D10 and task 8.5.
- **Verification:** Partly fixed. The emission regression is gone. For the reported `Box`, `generateNxIr()` succeeds in the wasm host, `nxlang codegen main.nx --target nx-ir` from this tree writes `main.nxir`, and `functionSchema` answers with the five `$defs` the Fix note lists. Mutual recursion (`A` → `<B T=<A T=T/>/>` → `<A T=<B T=T/>/>`) also answers, with 9 `$defs`, and emits. The schema walk still diverges when the argument grows through *another* generic record: `type Pair = { L:type R:type l:L r:R }` with `type Box = { T:type v:T inner?:<Box T=<Pair L=T R=T /> /> }` and `let f(b:<Box T=int />)`. That program emits fine, through both the wasm host and the CLI, because the boundary walk keys on the declaration. But `functionSchema` traps the wasm host ("memory allocation of 112 bytes failed" → `NxHostCrashedError`), and the host is then unusable for every later call. The reason: `applications_of` counts only how often `Box` appears in its own arguments (`Pair<int,int>`, `Pair<Pair<…>,Pair<…>>`, …). That count stays 0, so the collapse never fires while the arguments grow exponentially. What remains is Low: only the schema query is affected, and the shape is exotic. Fix it by collapsing on recursion rather than on self-application. For example, keep the stack of records whose entries are being built and, when `record_def` meets a record already on that stack with different arguments, describe it unapplied. Alternatively, bound the argument nesting depth. Add this `Pair` case to `a_record_applied_to_itself_without_end_is_described_and_walked_in_finite_steps`.
- **Fix (2):** `record_def` now also collapses an instantiation to the record named with no arguments when any type argument nests applied types more than four deep (`argument_depth` > `MAX_TYPE_ARGUMENT_DEPTH`), beside the self-application count. A program has finitely many shapes of bounded depth, so the schema walk ends whatever path the argument grows through, and the collapse keeps the agreement, as before. Test `a_record_whose_argument_grows_through_another_record_stays_finite` covers the reviewer's `Box`/`Pair` case (finite `$defs`, `Box` present), two mutually recursive records, and a written-out `<Page T=<Page T=Plan />/>` that keeps its arguments (`Page_Page_Plan`). The export spec's generic-record requirement, design D10 and task 8.5 state the bound.
- **Verification (2):** Re-probed `functionSchema` against the rebuilt wasm module, with a fresh host per case. Every case answers in 2 ms or less, validates its arguments with Ajv, and the call succeeds on the TypeScript runtime:
  - The reported `Box`/`Pair` case: 13 `$defs`.
  - The original self-applied `Box`: 5 `$defs`.
  - A two-parameter `Box` whose arguments cross through `Pair` (`T=<Pair L=T R=U/>`, `U=<Pair L=U R=T/>`): 14 `$defs`.
  - Three records rotating `A` → `B<C<T>>` → `C<A<T>>` → `A<B<T>>`: 165 `$defs`. Finite, but the largest of these.
  - The output side (`g(): <Box T=int/>`): its returned value validates.
  - `typeSchema` of the unapplied `Box`.
  - A written-out five-deep `<Page T=<Page T=…Plan…/>/>`: collapses to `Page`. This is wider than the declared type, but still within what the runtime checks.
  
  I found no other shape that can grow without end. Type arguments are applied types only (a `+`/`*` argument is rejected), aliases take no arguments, and union cases and abstract-site descendants are always walked unapplied. So `argument_depth` bounds every instantiation the walk can create, and keys and `natural_key` are bounded with it. The number of `$defs` can still multiply with the count of mutually recursive generic records, as the 165 above shows. That is acceptable for such exotic shapes. Suites: `nx-api` schema tests 75, `nx-codegen` 259, wasm SDK 115, Node SDK 35; `openspec validate --strict` passes.

### ✅ Verified - RF9 The entry's module table gains modules for functions a program linked from the entry cannot call
- **Severity:** Low
- **Evidence:** `program_artifact_boundary_subtype_modules` walks every function of every module, including root modules that nothing imports. Probe: entry `main.nx` is only `let root() = 1`; `tools.nx`, which nobody imports, declares `let g(s:Base)`; `base.nx` declares `Base` and `A`. The entry's table becomes `[main.nx, base.nx]`, although nothing linked from `main.nx` mentions `Base` and `g` is not in that program. This matches the delta's wording ("a function of the program"), but it has costs. The entry gains a link dependency (a host must now supply `base.nx`), and the entry image changes whenever an unrelated module's boundary types change, which defeats image caching keyed on content.
- **Recommendation:** Either restrict the walk to functions in modules a program linked from the entry contains (the entry's referenced closure, iterated to a fixpoint with the added modules), or keep the broad rule deliberately and say so in D14 and the nx-ir-format delta, including the extra link dependency. A test should pin whichever rule is chosen.
- **Fix:** Narrowed.
