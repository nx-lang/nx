## Questions
- Both recommended cases rest on a host's function record being accepted at a function type without its parameters being checked, and on the failure that follows, in a default or in the body, naming no argument although the host's record caused it. That is what both runtimes do, what the specs' "by a function it calls" says, and what the `through` / `needsTwo` assertions already pin for the body. Is it the intended answer for a default as well? If a mismatched function record should one day be refused at the boundary and name its parameter, these cases need another trigger.
- Seen while writing the probes, outside this change: a record field default can call a function-typed field only by position (`step(1)`; `<step n={1} />` there is read as an element and refused), while a function-typed parameter can be called only as an element (`step(1)` is refused with "call it as an element"). It matters here only because it decides how the recommended test sources are spelled.

## Summary
- No behavioural defect found. The two runtimes gave the same code and the same argument, or none, for every call probed beyond the tests: a default that fails after another field's default succeeded, two wrong arguments, a missing argument before a wrong one, an explicit `null` for a parameter with a default, an argument the function does not declare, and the function-value cases above. The package's classification follows design decision 3, the delta specs match the code, the committed `dist` matches the source, and the documentation says what the code does.
- Two findings, both test coverage of design decision 2: each of the two conditions that keep a default's failure unnamed can be deleted from either runtime with the corpus and the differential test still passing, and for the second with every test still passing. The cases that would hold them need no checker gap and are given above.
