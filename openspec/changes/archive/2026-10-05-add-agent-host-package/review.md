### ✅ Verified - RF1 A host's generated context type cannot be passed as the tool context
- **Severity:** Medium
- **Evidence:** `packages/agent/src/execute.ts:49` declares `ToolContextRecord = { readonly $type: string; readonly [field: string]: JsonValue }`, and it types `ToolCallContext.context` (`execute.ts:62`) and the `context` option of `toAiSdkTools` (`packages/agent/src/ai-sdk.ts:40`). `nxlang typegen` writes a host's context type as an `interface` that extends the `ToolContext` this package publishes (`src/generated/agent.ts:111`; the README's own sample at `README.md:115`), and TypeScript does not give an interface an implicit index signature. Compiling a consumer under `--strict` that passes a value typed `ChatToolContext` (the generated interface) as `context` fails twice: `error TS2322: Type 'ChatToolContext' is not assignable to type 'ToolContextRecord'. Index signature for type 'string' is missing in type 'ChatToolContext'`, once for `execute` and once for `toAiSdkTools({ context: () => record })`. The generated type also requires `callId`, which the package replaces at every call, so the host has to invent one to build the value. Every sample in the README and `test/consumer-types.test.ts` passes an object literal, which is why nothing catches it. `design.md` (Risks) relies on the opposite: "a host that fills its record from its own generated type cannot produce a wrong shape".
- **Recommendation:** Type the record by what `execute` checks, a `$type` string and nothing more (for example `{ readonly $type: string }`, which an interface satisfies and which lets `callId` be left out), in `execute.ts` and `ai-sdk.ts`. Add a case to `test/consumer-types.test.ts` that declares `interface ChatToolContext extends ToolContext { $type: "ChatToolContext"; conversationId: string }` and passes a value of it (and of `Omit<ChatToolContext, "callId">`) to `execute` and to `toAiSdkTools`' `context`, under both module resolutions.
- **Fix:** `ToolContextRecord` (`packages/agent/src/execute.ts`) is now `{ readonly $type: string } | { readonly $type: string; readonly [field: string]: JsonValue }`. The first member is what a generated interface, or `Omit<ChatToolContext, "callId">`, is assignable to. The second is kept because with the first alone an object literal that names the record's fields fails the excess-property check, which every README sample relies on; in a union, a property is known when any member knows it. `test/consumer-types.test.ts` now declares the generated interface and passes a value of it, of `Omit<…, "callId">` and an object literal as `ToolCallContext.context` and as the return of `ToAiSdkToolsOptions.context`, under both module resolutions, and expects an error for a record with no `$type` and for a string. With the old type put back in the built `execute.d.ts`, both cases of that test fail with the `TS2322` the finding quotes. The README's *Tool context* section says the generated type can be passed, with or without `callId`.
- **Verification:** Verified. Read `ToolContextRecord` at `packages/agent/src/execute.ts:58` (now a union whose first member is `{ readonly $type: string }`) and the new cases in `test/consumer-types.test.ts`. Recreated the `tsc` probe against the rebuilt `dist`: a value of the generated `interface ChatToolContext extends ToolContext`, one of `Omit<ChatToolContext, "callId">`, an object literal with nested fields and `undefined` all compile as `ToolCallContext.context` and as the return of `toAiSdkTools`' `context`, under `--strict --exactOptionalPropertyTypes` with `nodenext` and with `bundler` resolution; a record with no `$type`, a string and a `$type` that is not a string are each still an error. The README's *Tool context* section says so. `pnpm --filter @nx-lang/agent test` passes (225).

### ✅ Verified - RF2 `hostSuppliedWithin` names only the first listed type a held record matches

With two listed types of which one extends the other, a held record is both. The agent package lists one type, so it is not affected today.
- **Recommendation:** In the walk, mark every listed type the record (or union base) is or extends, not the first: return all matching places from the helper the walk uses, and keep `position` for `host_supplied_match`, which names one. Add a Rust test that lists `ToolContext` and `ChatToolContext` in both orders for `ChatToolContext+` and for a record field.
- **Fix:** `listed_record` and `listed_union_base` (`crates/nx-api/src/schema.rs`) answer every place a record or a union's base matches, and `HeldWalk` marks each; `host_supplied_match` takes the first, so `hostSupplied` still names one type. A type the host lists twice is now one listed type, at its first place, which "each once" needs once more than one place can match. The Rust test `a_record_that_is_two_listed_types_is_named_for_each` lists `ToolContext`, `ChatToolContext` and an abstract subtype that is a union's base, in two orders, for `ChatToolContext+`, a record field, `AuditToolContext+` and the union, and lists two types twice. It fails with either helper cut back to its first match, and with the de-duplication removed. The delta spec says a record that is more than one listed type is named for each, with the scenario "A record that is two listed types is named for each".
- **Verification:** Verified. Read `listed_record`, `listed_union_base` and `HeldWalk` (`crates/nx-api/src/schema.rs:975`, `:995`, `:1360`, `:1381`, `:1401`): each marks every place that matches, `host_supplied_match` takes the first (`:962`), and the listed types are de-duplicated by declaration before the walk (`:305-312`). ### ✅ Verified - RF3 A parameter typed by a context type's update record puts the context's fields to the model unreported
- **Severity:** Low
- **Evidence:** Every record has a derived `T.Update`. A tool function `let patchCtx(patch:ChatToolContext.Update): string` is answered with neither `hostSupplied` nor `hostSuppliedWithin` (`typeRef` is `ChatToolContext.Update`), so `normalizeAgent` accepts it with no diagnostic and the stored `inputSchema` asks the model for `callId`, `conversationId` and `contactEmail`. `ToolContext.Update` behaves the same. By contrast `Request.Update`, where `Request` has a context field, is reported, because the walk reaches the field. The walk (`HeldWalk::declaration`, `crates/nx-api/src/schema.rs:1333`) matches a record only when it is, or extends, a listed type, and an update record does neither. The spec's wording ("`ToolContext` or a record that extends it") does not cover it, but its stated reason does: "the model would otherwise be asked for the host's context". This is the same exposure the `+` and field cases were added to close. I confirmed the behaviour; whether it is a defect or an accepted limit is a decision the artifacts do not record.
- **Recommendation:** Decide and write it down. Either count the update record of a listed type (or of a record extending one) as holding that type in the walk, with a Rust test and a package test, and a sentence in the delta spec; or state in the spec and in the README's *Tool context* section that a derived `.Update` of a context type is an ordinary parameter.
- **Fix:** Decided as the second option and written down: a type derived from a listed type is another type. A value of `ChatToolContext.Update` is not a `ChatToolContext`, the host has no such value to supply, and no author can expect the host to fill one in, so nothing the host supplies is asked of the model; a function that takes a patch from the model is asking for it on purpose, as one with a `conversationId: string` parameter would. The rule stays "the listed record itself, or one that extends it, is reached", which is why `Request.Update` is still reported. Recorded in the delta spec (the sentence on derived types and the scenario "A type derived from a listed type holds none of it"), pinned by the Rust test `a_derived_type_of_a_listed_type_holds_none_of_it` (`ChatToolContext.Update`, `ToolContext.Update`, `ChatToolContext.Property`, and `Request.Update`, which is still named), and stated in the README's *Tool context* section, the `hostSuppliedWithin` doc comment of both bindings and `declaration-schemas.md`. This is a decision of mine on a point the artifacts left open; the other option is a small change to `HeldWalk::declaration` if it is preferred.
- **Verification:** Verified as the second option of the recommendation: decided and written down, with no change of behaviour. The probe answers as before (`ChatToolContext.Update` and `ToolContext.Update` are ordinary parameters; `Request.Update` names `ToolContext`), which is now what the delta spec says (the sentence on derived types and the scenario "A type derived from a listed type holds none of it"), what `a_derived_type_of_a_listed_type_holds_none_of_it` pins, and what the README, both bindings' `hostSuppliedWithin` doc comments and `declaration-schemas.md` state. I think the decision is sound: the held-context rule exists because an author can expect the host to fill a value it cannot fill, and nobody can expect the host to fill a patch; a function that takes one from the model asks for it as plainly as one with a `conversationId:string` parameter does. It also sits coherently beside "a form that wraps or narrows another type is looked through", since a derived record is a declaration of its own and not a wrapper. Two things remain outside this finding: `design.md` does not record the decision (RF9), and it was made by the fixer on a point the artifacts left open, so the user should see it.
