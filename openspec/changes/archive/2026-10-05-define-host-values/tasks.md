  - Entry points, what each measures, and where it is read (all in `runtime/typescript/src/index.ts`):
    - `evaluateFunction`: each positional argument. Read by `readHostArguments` once the function is found and before `invokeFunction`, each by its parameter's name, all before the first is bound.     - `callFunction`: the function record, and the arguments by name as one record. The function record is read at the entry, after it is found to be a record at all.     - `dispatchComponentActions`: each entry of the batch. Read at the entry, before `dispatchBatch`. The instance is not input.
    - `normalizeComponentState`: state. Read at the entry.
    - `applyComponentStatePatch`: the current state and the patch. Read at the entry.
  - "At the entry" is the first statements of the function each passes to `evaluate`, which runs after the options are checked and the input is measured. `readHostRecord` is for props, a state and a patch, `readHostValues` for content and a batch, `readHostValue` for one value. `readHostRecord` requires a plain object and `readHostValues` an array (`requireHostList`), so what holds the values is read as well: review finding RF1 showed that content or a batch passed as a `Set` was measured as one value and then iterated unread.
  - Callers of `isObject`, `requireObject` and `isPlainInput`, and whether a host value reaches them unread:

- [x] 2.2 Measure the reading's cost before anything is built on it: time `evaluateComponent` over a state of ten thousand records, and `callFunction` with an argument of the same size, a thousand times each, with and without `maxInputSize`, on the commit before 2.1 and after it; record the times under this task, and if any difference is more than five percent of the call, fold the reading into the measure's walk as design decision 2 describes, measure again and record that too
  - Measured on the laptop this was written on, Node 24, a state and an argument of 10,000 records of three fields, per call, median of five rounds of 1,000 calls, two runs:
    - Before (commit `50fc3ea`): `evaluateComponent` 2.74 and 2.87 ms with no limit, 3.29 and 3.39 ms with `maxInputSize`; `callFunction` 3.54 and 2.97 ms, 3.77 and 3.52 ms. Two runs of the same build differ by up to 5%, and one outlier by 19%.
    - After 2.1 as first written (the walk with its own stack, a set of the objects it is inside, a list of names for each object): 4.75, 4.88, 4.53 and 5.08 ms. About 1.6 ms a call, 60%. Far over the bound.
    - After 2.1 with `isReadAsPassed`: 2.84 and 3.08 ms, 3.36 and 3.60 ms, 3.00 and 3.15 ms, 3.58 and 3.72 ms. Against the before of the same run, 4% to 7% in the second and under 4% in the first. Timed alone, the check takes 13 ns a record of one shape and 19 to 23 ns over mixed shapes, which is 0.13 to 0.2 ms of a 2.9 ms call: about 5%.
  - Not folded into the measure's walk. That would remove the cost only from a call with `maxInputSize`, which already pays about 0.5 ms (18%) for the measure, and leave a call with no limit where it is; and the 60% that made the bound matter is gone by other means. The cost is at the bound and not clearly under it, on a call that does nothing but take 10,000 records. `add-ir-runtime-performance-harness` is where it should be watched.
