## Findings

### ✅ Verified - RF1 A list of host values that is not an array is not read: array-like arguments now throw a `TypeError`, and content or a batch passed as a `Set` is measured as one and reaches the check unread
- **Severity:** Medium
- **Evidence:** The reading requires a plain object where a record is passed (`requirePlainRecord`, `runtime/typescript/src/index.ts:2901`), and requires nothing where a list is passed. The measure already knows a list may not be an array (`measureValues`, `index.ts:2675`, measures it as one value); the reading does not (`readHostValues`, `index.ts:2919`, loops on `values.length`; `invokeFunction`, `index.ts:3072`, calls `args.map`). Confirmed by probes:
  - *Regression.* `evaluateFunction(program, "keep", arguments)` and `evaluateFunction(program, "keep", { length: 1, 0: { a: 1 } })` return `"kept"` on `50fc3ea` and now throw `TypeError: args.map is not a function`, which is not an `NxIrRuntimeError`.
  - *Unread input.* `constructComponentDescriptor(program, "Card", {}, new Set([{ when: new Date(0), bytes: new Uint8Array(3) }]))` succeeds and returns `body: [{ when: {}, bytes: { "0": 0, "1": 0, "2": 0 } }]`: the `Date` was converted and the typed array walked. The same items in an array are refused at `Card content[0].when`.
  - *The limit.* The same call with a `Set` of 50,000 records under `maxInputSize: 10` succeeds with `usage.inputSize` 2 and a `body` of 50,000 items; as an array it is refused by the limit. `dispatchComponentActions` with a `Set` of 50,000 entries, each holding a `Date` at a field typed `object`, under `maxInputSize: 10`, runs all 50,000 handlers with `inputSize` 1 (`dispatchBatch` iterates with `batch.forEach`, `index.ts:2216`).

  So the sentence this change adds to `docs/nx-ir-format.md:811` ("a value that counted one is never one the runtime goes on to walk") and the conclusion of task 1.2 ("no host value reaches the check by a path that passes neither place") do not hold for these three inputs, and the delta spec's "every value the call goes on to check or to hold SHALL be read" is not met. The TypeScript signatures exclude a `Set`, so this is reachable from JavaScript or through a cast only, which is also true of most of what the change refuses. No test passes a list that is not an array.
- **Recommendation:** Require an array for positional arguments, content and a batch at the same place the reading starts, as `requirePlainRecord` does for a record, failing with `nx-ir-boundary-type` and no `argument` ("Expected Card content to be an array, got an instance of Set..."). That removes the `TypeError`, closes the limit for these inputs and makes the measure's non-array branch unreachable in a call. Add a test for each of the three, and correct task 1.2's note.
- **Fix:** What holds a list of host values now has to be an array, as what holds named values has to be a plain object: `requireHostList` (`runtime/typescript/src/index.ts`) is called for the positional arguments of `evaluateFunction` at the entry and by `readHostValues` for content and a batch, and refuses anything else with `nx-ir-boundary-type` and no `argument` ("Expected Card content to be an array, got an instance of Set, which is not a plain object."). The arguments of a function are now read by `readHostArguments` and `readNamedHostArguments` before `invokeFunction`, which no longer calls `args.map` on what a host passed, so there is no `TypeError`. An object with a `length` as positional arguments, which worked on `50fc3ea`, is refused: one rule for every list. The delta spec (`specs/typescript-ir-runtime/spec.md`) says so, with the scenario *A list that is not an array is refused*; `docs/nx-ir-format.md` (*Host values*), the README and the changelog say so; task 1.2's note is corrected. Tests: in "arguments, a function record, props, content, a state, a patch and a batch are all read..." of `test/emitted-ir.test.mjs`, an object with a `length` as arguments, a `Set` of 50,000 records as content and one as a batch, each with no limit and under `maxInputSize: 10`.
- **Verification:** Holds. Reran the probes that showed it (`probe1.mjs`, `probe2.mjs`, `probe3.mjs`) against the rebuilt runtime: positional arguments passed as `arguments`, as an object with a `length`, as `null` and as a `Uint8Array` are each refused with `nx-ir-boundary-type`, "Expected the arguments of 'keep' to be an array, got ...", and no `TypeError` is left; content as a `Date`, a plain object, a string, `null` and a `Set`, and a batch as a plain object, `null` and a `Set`, are each refused the same way with no `argument`; the `Set` of 50,000 records as content and as a batch under `maxInputSize: 10` is refused where it was accepted, and the same items in an array are still refused by the limit. `requireHostList` runs first in `evaluateFunction` and inside `readHostValues`, so nothing iterates a list before it is known to be an array. The delta spec has the rule and the scenario, the tests are there (an object with a `length`, a `Set` as content and as a batch, with and without a limit), and task 1.2's note is corrected. The moved reading of arguments brought one new cost, RF5 below.

### ✅ Verified - RF2 Reading a value that holds the same object more than once takes time in proportion to its size as a tree, which no option bounds unless `maxInputSize` is set
- **Severity:** Low
- **Evidence:** `isReadAsPassed` (`index.ts:2831`) and the full walk (`index.ts:2747`, which keeps only the objects on the current path in `entered`) both re-read an object each time it is reached. Confirmed by probe with `let keep(extra:object): string` and a value in which each of `n` objects holds the next one twice, under `maxOperations: 1000` and no input limit: 20 levels (41 objects) 31 ms, 24 levels 375 ms, 26 levels (53 objects) 1,483 ms, four times as long for every two levels; `usage.operations` is 4 each time. On `50fc3ea` each returns in under a millisecond, since nothing reads a value at `object` that the function does not return. With `maxInputSize: 1000` the 26-level value is refused by the limit in 1 ms. The design's cost (decision 2: "one pass over the input", "bounded by the size of the input, which is the host's to limit") is right once "size" is read as the measure defines it, with every reference a new value, but nothing a host reads says that the scenario *The same object held twice is accepted* costs this, or that a call with an operation budget and no input limit is no longer bounded for such a value. A value read from JSON cannot have this shape, so only a host's own structure sharing reaches it.
- **Recommendation:** Either make the reading linear in distinct objects (in the full walk, remember an object that was read with nothing left out and skip it when it is met again; let the fast path give up to the full walk after a fixed number of values), or say in `runtime/typescript/README.md` (*Host values*) and `docs/nx-ir-format.md` (*What the limit bounds*) that a shared value is read once for each place it is held and that `maxInputSize` is what bounds it.
- **Fix:** Stated, not bounded. Making the reading linear in distinct objects would need a set of the objects seen in the fast path, which is the cost task 2.2 removed, and the input size already counts every reference as a new value, so the reading and the measure agree as they are. `runtime/typescript/README.md` (*Host values*) now says a shared object is read and measured once for each place it is held and that `maxInputSize`, not `maxOperations`, bounds the reading; `docs/nx-ir-format.md` says the same in *Host values* and has a bullet in *What the limit bounds* with the 2^50 example and that a budget alone does not bound such a call; the delta spec's sentence on the same object held twice says it is read once for each place it is held, as the input size counts it.
- **Verification:** Holds as the second course of the recommendation: the cost is stated, not bounded. Reran `probe4.mjs` to confirm the behaviour the documents describe is the behaviour there is: 26 levels of sharing under `maxOperations: 1000` still take 1.5 s for 4 operations, and `maxInputSize: 1000` refuses the value in 1 ms. `runtime/typescript/README.md` (*Host values*) says a shared object is read and measured once for each place it is held and that `maxInputSize`, not `maxOperations`, bounds the reading; `docs/nx-ir-format.md` says it in *Host values* and in a bullet of *What the limit bounds* (fifty objects that each hold the next twice are 2^50 values, and the budget alone does not bound such a call), which is accurate; the delta spec's sentence on the same object held twice says it too. The documents rest on reading, the behaviour on the probe.

### ✅ Verified - RF3 The README's sample of an `undefined` member does not type-check, because `NxCanonicalValue` does not admit one
- **Severity:** Low
- **Evidence:** `runtime/typescript/README.md:156` shows `evaluateFunction(program, "greet", [{ name: "Ada", nickname: undefined }]); // and so is this` in a `ts` block. Confirmed with `tsc --strict` against `dist/src/index.d.ts`: `error TS2322: Type '{ name: string; nickname: undefined; }' is not assignable to type 'NxCanonicalValue'`. `initializeComponent(program, "Card", { title: maybe })` with `maybe: string | undefined` fails the same way. The doc comment of `NxCanonicalValue` (`index.ts:729`) now says "a member a host sets to `undefined` is a member left out" on a type whose object member is `{ readonly [key: string]: NxCanonicalValue }` (`index.ts:741`). The spelling the spec defines for the JavaScript form is therefore accepted at run time and refused at compile time unless it arrives through a declared type with an optional property (`type Person = { name: string; nickname?: string }` passes) or a cast, which is what `packages/agent/test/execute.test.ts:410` uses. The runtime's README samples are not compiled by any test, unlike the agent package's, so nothing caught it.
- **Recommendation:** Decide which is meant. If a TypeScript host is meant to be able to write the member, give the evaluation APIs an input type whose object members may be `undefined` (a separate `NxHostValue`, so results stay `NxCanonicalValue`). If not, change the sample to the case that compiles (a value of a type with an optional property) and say in the README and the doc comment that the type does not admit the literal.
- **Fix:** A TypeScript host is meant to be able to write the member, so the evaluation functions take new input types: `NxHostValue`, whose object members may be `undefined`, and `NxHostRecord` for props, a state, a patch and arguments by name (`index.ts`, beside `NxCanonicalValue`). Positional arguments are `readonly (NxHostValue | undefined)[]`, since one that is `undefined` is not supplied. Results stay `NxCanonicalValue`, which is assignable to `NxHostValue`, so what the runtime returns can be passed back. The delta spec requires it, with the scenario *A member set to undefined is written without a cast*. `test/runtime.test.ts` has `hostValueTypes`, compiled by `pnpm test` and never called: every entry point with a member that is `undefined`, a state passed back, and two `@ts-expect-error` lines (an `undefined` member at `NxCanonicalValue`, a `Date` at `NxHostValue`). The README's sample compiles under `tsc --strict` against `dist/src/index.d.ts`; its line passing an instance of a class now has a cast and says TypeScript refuses it too. The doc comment of `NxCanonicalValue` points to `NxHostValue` for the member.
- **Verification:** Holds. Reran `tsc --strict` on the sample that failed (`tscheck/sample.ts`) against the rebuilt `dist/src/index.d.ts`: the literal with `nickname: undefined` and props `{ title: maybe }` with `maybe: string | undefined` now compile, and an instance of a class and a `Date` are still refused by the compiler. Both `ts` blocks of the README's *Host values* section compile as written (`tscheck/readme.ts`), and so does passing back a result, a returned state and rendered output, so `NxCanonicalValue` is assignable to the new input types as claimed. `hostValueTypes` in `test/runtime.test.ts` covers all eight entry points and has the two `@ts-expect-error` lines; it is compiled by `pnpm test`, which passes. The agent package, the one in-repo caller, compiles and passes against the new signatures (238 tests). An interface with no index signature is still not assignable, as before the change; `design.md` already says a host builds literals.

### ✅ Verified - RF4 `callFunction` given something that is no host value as its function now fails with `nx-ir-boundary-type` and a message that lists kinds it would not accept either
- **Severity:** Low
- **Evidence:** `callFunction` reads its function value with the general reading before it looks for a `Function` record (`index.ts:3682`). Confirmed by probe: `callFunction(program, undefined, {})` failed on `50fc3ea` with `nx-ir-function-value`, "callFunction expects a Function record: { $type: "Function", module, name }.", and now fails with `nx-ir-boundary-type`, "Expected the function callFunction is given to be null, a boolean, a number, a string, an array or a plain object, got undefined." A string there still gets the old code and message, so the two mistakes a host is most likely to make (a template that is absent, a name where a record is wanted) now have different codes, and the more likely one names six kinds of value of which five are refused next. No spec pins the code for this case, and the change's tests cover only a value inside the record (`{ ...fn("keep"), note: deep }`).
- **Recommendation:** In `callFunction`, refuse a value that is not a plain object (or a function value the runtime made) with the existing `nx-ir-function-value` failure first, and read what the record holds after. Add the `undefined` case to the test "the function record of the call ... name no argument".
- **Fix:** `callFunction` now looks at what it was given first: a value that is not a plain object is refused with `nx-ir-function-value` and the message it had, `undefined`, `null`, a number, an array, a `Date` and a function included, and a record is then read as any host value is, so a `Date` inside the record is still `nx-ir-boundary-type` with its path. Test: six such values added to "the function record of the call, a count of arguments and another entry point name no argument".
- **Verification:** Holds. Reran the probes: `callFunction` given `undefined`, a `Date` or a string as its function fails with `nx-ir-function-value` and the message it had on `50fc3ea`; the function value a state holds is refused the same way, as before; a record with no `$type` that holds a `Date` is still refused by its path with `nx-ir-boundary-type`; a record with no prototype is still called. The test "the function record of the call ... name no argument" has the six values. The reorder puts the check of the record ahead of `programOf`, so a call with both faults reports the record first; nothing specifies that order.

### ✅ Verified - RF5 Positional arguments are copied whole before their count is checked, so a call with too many arguments costs time and memory in proportion to the list
- **Severity:** Low
- **Evidence:** Introduced by the fix of RF1. `readHostArguments` (`runtime/typescript/src/index.ts:3185`) builds a new array with `Array.from(args, ...)` over the whole list, and `evaluateFunction` calls it before `invokeFunction`, where the count is checked (`index.ts:3104`). Confirmed by probe (`probe5.mjs`) with `let keep(extra:object): string` and no input limit: `evaluateFunction(program, "keep", new Array(50_000_000))` takes 1.8 s and about 800 MB of heap to fail with "Function 'keep' expected at most 1 arguments, got 50000000", and a list of five million numbers takes 141 ms and 118 MB; on `50fc3ea`, and on the build before the fixes, both fail in 0.2 ms with no allocation. Under `maxInputSize: 100` the limit still refuses the list in 0.3 ms. The order of two faults moved with it: `evaluateFunction(program, "keep", [{ when: new Date(0) }, 1])` reported the count before the fixes and now reports the `Date` in `extra`; either is allowed by the spec. The list is the host's own, so nothing a model or a wire sends reaches this.
- **Recommendation:** Check the count before the arguments are read, in `evaluateFunction` or at the top of `readHostArguments` (the check in `invokeFunction` can stay for the calls a body makes), or read only the first `params.length` entries and leave the list's length for the count. Add the case to the test of a count of arguments.
- **Fix:** The count is checked before anything is read: `requireArgumentCount` (`runtime/typescript/src/index.ts`) holds the check `invokeFunction` had and is called by `evaluateFunction` ahead of `readHostArguments`, which now maps over the parameters and not over the list, so it reads and allocates no more than the function has parameters. A value that is no host value beside an argument too many is reported as the count again, as on `50fc3ea`. Test: in "the function record of the call, a count of arguments and another entry point name no argument" of `test/emitted-ir.test.mjs`, a `Date` among too many arguments, and fifty million arguments refused for their count without the heap growing by 50 MB. Also changed, from the two cosmetic points of the verification: a refusal says "which is not a plain object" only where a plain object would have been accepted, so a list that is not an array is "Expected Card content to be an array, got an instance of Set."; and the parameters of the evaluation functions have the names they had (`props`, `content`, `state`, `currentState`, `patch`), with the values as read held in locals.
- **Verification:** Holds (2026-10-05 16:06). Reran `probe5.mjs` against the rebuilt runtime: fifty million positional arguments and five million numbers are each refused for their count in 0.2 ms with no growth of the heap, as on `50fc3ea`, where the fix of RF1 took 1.8 s and about 800 MB; a `Date` in a real argument beside one too many is reported as the count again; under `maxInputSize: 100` the limit still comes first. Every other line of that probe is as it was on the build last verified: the argument named by position and by name, `undefined` and `null` arguments, missing and surplus ones, the order of failures in `callFunction`, records and argument records with no prototype or with a `__proto__` key, and a named call inside the program. `requireArgumentCount` is called by `evaluateFunction` before `readHostArguments`, which maps over the parameters, and by `invokeFunction` for the calls a body makes. The renaming was checked two ways. By reading, in each of the eight entry points the host's parameter is used only by the measure and by the reading, and every later use is of the value as read (`readProps`, `readContent`, `readState`, `readPatch`, `entries`, `read`). By a probe written for it (`probe6.mjs`), a member that is `undefined` below the top of what each entry point is passed is absent in what the call holds or returns and still present in the host's object, for arguments by position and by name, props, content, a state, a patch and a batch; `evaluateComponent`, which returns only rendered output, accepts a top-level `undefined` member of its props and of its state, which the check refuses when it is given the host's value. The messages: a list that is not an array is "Expected Card content to be an array, got an instance of Set.", a record that is not a plain object is "... to be a plain object, got an instance of Object.", and a value inside the input keeps "got an instance of Date, which is not a plain object."; rerunning `probe1.mjs` and `probe2.mjs` against this build and the last verified one shows those lines and no others differ, and no call throws anything but an `NxIrRuntimeError`. Also run: `pnpm test` in `runtime/typescript` (exit 0, 687 `ok` lines, none `not ok`) and in `packages/agent` (238 pass, 0 fail); `openspec validate define-host-values --strict` (valid); a `tsc` build to a scratch directory, identical to the committed `dist/src/index.js`, `dist/src/index.d.ts` and `dist/test/runtime.test.js`; the fuzz of the reading, the same 40,000 values with no difference; and a diff of the built runtime against the build last verified, read whole: the count check, `readHostArguments`, the three messages and the renaming are all that changed, and `index.d.ts` differs only in the five parameter names. ## Questions
- The table of forms (`docs/nx-ir-format.md:559`, and `design.md`) gives "that record, or the value the runtime returned in a state" as the JavaScript form of a function value. `callFunction(program, stepper.state.step, { n: 2 })`, with the function value a state holds, is refused with `nx-ir-function-value` (probe; the same on `50fc3ea`), while the `JSON.parse(JSON.stringify(...))` of it is called. Is `callFunction` meant to take the runtime's own function value, or should the table say the object is accepted where a value is held and not as the function to call?
  - **Answer:** The table. `callFunction` is unchanged and takes the record; the cell of `docs/nx-ir-format.md` and of `design.md` now reads "that record, or, where a value is held, the value the runtime returned in a state".
- Task 1.4 records that a hole in a list at a typed site was let through and is now refused, and that the message of an `undefined` item changed. Both follow the spec. `src/vscode/CHANGELOG.md` names the `undefined` item and not the changed message; is that enough for hosts that match on message text?
  - **Answer:** Added to the changelog: an `undefined` item of a list at a typed site keeps its code and has the new message.

## Summary
- The change does what its specs say for every scenario I checked: each scenario of the three delta specs has a test or was reproduced by a probe, the deltas differ from the main specs only where the proposal says, the docs match the code in every cell and sentence I checked, and the committed `dist` is the source's build. The core of it, the reading and the measure's rule for `undefined`, held against a reference implementation over 40,000 generated values with no difference.
- RF1 is the one to fix before archiving: it is a regression (a `TypeError` where a call worked) and the one place the change's own guarantee, that nothing which counts one is walked, does not hold. It is small to fix.
- RF2 to RF4 are low: a cost that should be bounded or stated, a sample and a type that disagree with the rule the change defines, and a diagnostic that got worse for one mistake.
- Timing of a call that takes 10,000 typed records, each build in its own process: the new build was between 4% faster and 15% slower than `50fc3ea` over twelve pairs of runs, with one outlier at 34%. That is consistent with what task 2.2 recorded ("at the bound and not clearly under it") and too noisy on this machine to say more.
- Verification, 2026-10-05 16:02: RF1 to RF4 are verified, each by rerunning what showed it. One new low finding, RF5, came with the fix of RF1. Both questions are answered and the answers are in the documents.
- Verification, 2026-10-05 16:06: RF5 is verified, with the two cosmetic points of the earlier pass (the wording of a refusal of a list, and the names of the public parameters). RF1 to RF5 are all verified and nothing is open.
