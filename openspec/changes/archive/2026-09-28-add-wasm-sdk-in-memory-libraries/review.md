## Findings

### ✅ Verified - RF1 A workspace module whose identity equals a library module's identity silently takes that module's place in library resolution
- **Severity:** High
- **Confidence:** High (reproduced)
- **Evidence:** In-memory library modules are named `<root>/<module>`, which is a valid workspace identity. Nothing rejects a workspace module with the same identity. The program then holds two modules under one identity. `build_resolved_program` keys `module_ids` by `file_name` for root modules and then for library modules (`crates/nx-api/src/artifacts.rs:2743`, `:2761`), so the later insert overwrites the earlier one. `analyze_logical_module_graph` keeps the workspace text for that identity in the source map (`or_insert_with`, `artifacts.rs:1578`), which is the text the library image's fingerprint is computed over. `program_version_map` overwrites the workspace module's version (`artifacts.rs:2329`). I reproduced it through the wasm SDK. I loaded `libraries/question-flow` with `Step.nx = export type Step = { id:string }`, then validated a tenant workspace of `chat-link.nx` (`<Step id="a" />`) plus a module `libraries/question-flow/Step.nx` = `export type Step = { y:int }`. Validation reports `Element 'Step' has no property 'id'` and `Element 'Step' requires property 'y'`, so the library's `Step` now resolves to the tenant's declaration. With `export type Evil = { x:int }` instead, `Step` "requires property 'x'": the library's definition index now points into the tenant module. This could not happen before this change: directory-library identities are absolute paths, and workspace identities cannot be absolute. It matters most in the multi-tenant server scenario the proposal targets. Untrusted workspace input can silently change the meaning of a shared library inside its own program, and the emitted image set then has two different modules under one identity.
- **Recommendation:** Reject the workspace at build and validate time with a diagnostic when any workspace identity equals, or sits under, a visible library root. The simplest rule is a workspace identity equal to a loaded library module's `file_name` or prefixed by `<root>/`. Add a Rust test and a wasm test for it.
- **Fix:** `analyze_logical_module_graph` now adds a program-level `workspace-module-in-library-root` error (`library_namespace_diagnostics` in `crates/nx-api/src/artifacts.rs`) for any workspace module whose identity equals a library module's or lies under `<root>/` of a logical root the context can see or the program links (prefix reservation, per the question below), so validation and the build both refuse it. Tests: `a_workspace_module_inside_a_library_root_is_refused` (Rust, both the exact-identity and prefix cases, plus a `libraries/question-flow-extras.nx` sibling that still builds) and `refuses a workspace module that lies inside a library's root` (wasm). design.md D1 and the library-registry spec gained the rule and a scenario.
- **Verification:** Verified. `library_namespace_diagnostics` (`crates/nx-api/src/artifacts.rs:1686`) is added to `program_diagnostics`, so both `validate_workspace` and `build_workspace_program_artifact` refuse the workspace. Re-running the original probe now gives `workspace-module-in-library-root` for `libraries/question-flow/Step.nx` in both build (throws) and validate. A new probe confirms that an unlinked `libraries/question-flow/x.nx` is refused (prefix reservation) and that a sibling `libraries/question-flow-x.nx` is accepted. Rust and wasm tests are present and pass. Minor note, not a blocker: the check runs after analysis, so the refusal still comes with the cascade diagnostics that the shadowed resolution produces (e.g. `Element 'Step' requires property 'y'`). The build fails either way.

### ✅ Verified - RF2 Workspace validation returns library diagnostics (warnings), not only diagnostics for the submitted modules
- **Severity:** Medium
- **Confidence:** High (reproduced)
- **Evidence:** The spec says validation "returns every diagnostic for the submitted modules" (specs/workspace-programs/spec.md, "Workspace validation is available as data through every SDK"). `validate_workspace` returns `analysis.diagnostics()` (`artifacts.rs:779`), and `LogicalProgramAnalysis::diagnostics` appends every linked library's diagnostics (`artifacts.rs:744-752`). An in-memory library with errors is refused at load, but one with warnings loads, and `loadLibrary` returns `void`, so the host never sees those warnings. They then appear in every tenant's validation. Probe: `Step.nx` containing `export let f(n:int) = { n ?? 0 }` loads fine. After that, validating any tenant that implicitly imports the library returns `fallback-never-taken` labelled at `libraries/question-flow/Step.nx:2:25`. That is a server-owned file the author cannot edit, and ReachMe would show it to every author.
- **Recommendation:** Filter validation (and, for consistency, build-error payloads) to diagnostics whose primary label is in a workspace module, plus program-level diagnostics with no label. Return library warnings from `load_libraries_from_sources`/`loadLibraries` instead, so the host sees them once at load. Add a test with a warning-bearing library.
- **Fix:** Added `LogicalProgramAnalysis::workspace_diagnostics`, which keeps program, workspace-module and library *error* diagnostics but drops a library's warnings/info/hints; `validate_workspace` and the failed-build payload use it (`ProgramArtifact.diagnostics` is unchanged). Library errors stay because they fail the build (directory libraries loaded via `load_library_artifact` can carry them). Library warnings are now answered at load: new `LibraryArtifact::api_diagnostics()`, the wasm `nx_wasm_registry_load` payload is now the libraries' diagnostics (once per root, in the order given) instead of the root list, and `loadLibraries`/`loadLibrary` return `readonly NxDiagnostic[]` in both the wasm and Node SDKs. Tests: Rust `a_library_warning_is_reported_at_load_and_not_in_workspace_validation`, wasm `answers a library's warnings at load and leaves them out of tenant validation`, Node `answers a library's warnings at load and leaves them out of workspace validation`, and the parity test now compares load diagnostics across SDKs. design.md D4/D5, workspace-programs and library-registry specs, and both READMEs updated.
- **Verification:** Verified. `workspace_diagnostics` (`artifacts.rs:816`) keeps only library errors, and it feeds validation and failed-build payloads. Probe: a library with a `fallback-never-taken` warning now returns that warning from `loadLibrary` (labelled at 2:25), and tenant validation returns `[]`. Warnings in a tenant module are still returned. Node native `load_libraries` matches wasm (de-duplicated per root, in the order given). The READMEs, design D4/D5 and specs are updated. See RF8 for a side effect on directory-loaded libraries.

### ✅ Verified - RF3 A failed workspace build renders library-labelled diagnostics without the library source, so their line and column are wrong and differ from validation
- **Severity:** Medium
- **Confidence:** High (reproduced)
- **Evidence:** D4 says library diagnostics "now render against its source text", and the README says a build "throws only for what validation already said". The validation path uses `analysis.source_map`, which now includes library sources (`artifacts.rs:779`). The build error path in `build_workspace_program_artifact` still renders with `graph.source_map()` (`artifacts.rs:836`), which holds only workspace modules. Probe: for the same tenant error plus a library warning, `validateWorkspace` reports the library warning at `startLine 2, startColumn 25`, while `buildWorkspaceArtifact` throws `NxEvaluationError` with the same diagnostic at `startLine 1, startColumn 1`. The wasm/Node parity test compares validation only, so it does not catch this.
- **Recommendation:** Render the build error with `&artifact.source_map`, which already carries the prelude and library sources, instead of `graph.source_map()`. Add an assertion that build-error diagnostics equal validation diagnostics for the same input.
- **Fix:** `build_workspace_program_artifact` now analyzes once, takes `workspace_diagnostics()` and renders the error with `artifact.source_map` (via the new `program_artifact_from_analysis` split), so a failed build throws exactly what validation returns. Tests: Rust `a_failed_build_answers_with_the_diagnostics_validation_does` and wasm `throws a failed build with exactly the diagnostics validation answers with`; the workspace-programs spec gained a scenario.
- **Verification:** Verified. `build_workspace_program_artifact` now analyzes once and renders `workspace_diagnostics()` against `artifact.source_map` (`artifacts.rs:919-929`). Probe: for the same bad tenant, `validateWorkspace` and the thrown `buildWorkspaceArtifact` diagnostics are identical. The Rust and wasm equality tests pass.

### ✅ Verified - RF4 The new implicit-import ambiguity check also fires on suffix matches against directory libraries, which breaks builds that worked before
- **Severity:** Low
- **Confidence:** Medium
- **Evidence:** `unknown_implicit_import_diagnostics` now fails the build whenever the identity is in the workspace and `visible_library_by_logical_identity` returns anything other than `Missing` (`artifacts.rs:1771`). That lookup also accepts *suffix* matches (`artifacts.rs:635`: `root_identity.ends_with("/<identity>")`), and it applies to directory-loaded roots, whose logical identity is their absolute path without the leading `/`. Before this change, a host that implicitly imported workspace module `drawnui` built fine with a directory library `/…/drawnui` visible, because the workspace module won. Now it fails with `implicit-import-ambiguous`. The failure also differs from a written import of the same identity, which still resolves to the workspace module first (`apply_graph_imports`). The message is also wrong in the `(true, Ambiguous(..))` case: it says "names both a workspace module and a loaded library" when several libraries matched.
- **Recommendation:** For the workspace-vs-library collision, consider only an exact logical-root match, which is what the spec scenario describes. Or document the suffix behaviour. Add a regression test with a visible directory library.
- **Fix:** `unknown_implicit_import_diagnostics` now reports the workspace-vs-library ambiguity only when a visible library's root is exactly the identity (new `ProgramBuildContext::has_visible_library_root`); suffix matches no longer compete with a workspace module, and the misleading message for the several-libraries case is gone because that case no longer reaches it. Test: `a_directory_library_whose_path_ends_in_a_workspace_identity_does_not_make_it_ambiguous` (temp directory library `.../drawnui` + workspace module `drawnui`). design.md D3 and the workspace-programs scenario now say "exactly the root", with a new regression scenario.
- **Verification:** Verified. The workspace-vs-library ambiguity now uses `has_visible_library_root` (`artifacts.rs:680`), an exact logical-root match, in `unknown_implicit_import_diagnostics` (`artifacts.rs:1920-1931`). Suffix matches only apply when no workspace module has the identity. The misleading message for the several-libraries case is gone. The regression test with a directory library `.../drawnui` plus workspace `drawnui` passes. The exact-root ambiguity is still reported (probe `ambig`).

### ✅ Verified - RF5 `implicitImports: []` cannot clear a build context's implicit imports, contrary to the documented "when given, it replaces"
- **Severity:** Low
- **Confidence:** High
- **Evidence:** `bindings/wasm/src/types.ts:327` documents that per-call `implicitImports`, "when given, … replaces the build context's own implicit imports". The wrapper always sends an array (`host.ts:869`, `Array.from(options.implicitImports ?? [])`), and native `workspace_build_context` keeps the context's list whenever the request's list is empty (`bindings/wasm/native/src/lib.rs:487-496`). So `{ implicitImports: [] }` behaves like omitting the field, and a caller cannot build a module without the context's implicit imports, for example the library-declaring module itself.
- **Recommendation:** Send the field only when it is defined and deserialize it as `Option<Vec<String>>`, so that `Some([])` replaces. Or change the doc to "a non-empty list replaces".
- **Fix:** The wasm native build/validate requests now deserialize `implicitImports` as `Option<Vec<String>>` and `workspace_build_context` replaces the context's list whenever it is present, empty included; the TS `workspacePayload` sends the field only when the caller gave it. The doc now says "even as an empty list". Tests: native `an_empty_implicit_import_list_replaces_the_contexts_own` and wasm `replaces the context's implicit imports with a list given per call, even an empty one`. (Node build contexts carry no implicit imports, so its empty-vs-omitted handling is unaffected.)
- **Verification:** Verified. Native `workspace_build_context` takes `Option<Vec<String>>` and replaces on `Some`, including an empty list (`bindings/wasm/native/src/lib.rs:491-500`). The TS `workspacePayload` only sends the field when the caller gave it. Probe: `<Step id={1} />` gives `record-field-type-mismatch` when the field is omitted and `[]` with `implicitImports: []`. Native and wasm tests pass.

### ✅ Verified - RF6 A `visibleRoots` entry that is not a loaded library fails in wasm with an OS error, and native may accept an unrelated directory
- **Severity:** Low
- **Confidence:** High
- **Evidence:** `build_context_with_visible_roots` falls back to `fs::canonicalize(root)?` for any root that is not a loaded logical root (`artifacts.rs:422`). In wasm, `createBuildContext({ visibleRoots: ["libraries/nope"] })` throws `NxEvaluationError` with the message "No such file or directory (os error 44)", which does not name the root, although `host.ts:173` documents the error as "a visible root is not a loaded library". On native, a relative logical spelling that is not loaded but happens to exist relative to the CWD is canonicalized and silently accepted as a directory root that no library is loaded under.
- **Recommendation:** When the root is relative (logical) and not loaded, return a diagnostic such as `library-root-not-loaded` naming it, instead of canonicalizing. Map that to a clear message in the wasm binding.
- **Fix:** `build_context_with_visible_roots` now wraps the canonicalize failure in an error that names the root: for a relative spelling, "Visible root '<root>' is not a loaded library, and no directory exists at it: ...", which is what the wasm SDK surfaces as `NxEvaluationError`. Tests: native `a_visible_root_that_is_not_loaded_is_named_in_the_error` and wasm `names a visible root that is not a loaded library`. The native case of a relative spelling that is an existing directory relative to the CWD is deliberately still accepted: `build_context_with_visible_roots` is a public API that takes directory paths, and relative directory paths were valid input before this change (a directory not yet loaded also becomes visible once loaded, since visibility is resolved at use). Refusing it would be a breaking change for directory callers, so it was left as is.
- **Verification:** Verified. The wasm error now names the root: `Visible root 'libraries/nope' is not a loaded library, and no directory exists at it: …` (probe). Native still accepts a relative spelling that is an existing directory relative to the CWD. That is a reasonable compatibility decision for a public directory-path API, and it is documented in the fix note.

### ✅ Verified - RF8 Directory-loaded libraries' warnings no longer reach any SDK caller, a behavior change the design calls additive
- **Severity:** Low
- **Confidence:** High (from the code; confirmed with a Node probe)
- **Evidence:** The RF2 fix applies `workspace_diagnostics` to every linked library, including directory-loaded ones (`crates/nx-api/src/artifacts.rs:816-833`). At HEAD, `validate_workspace` returned `analysis.diagnostics()`, which included every linked library's warnings. Directory loads were given no replacement channel: Node `NxLibraryRegistry.loadFromDirectory` still returns `void` (`bindings/node/src/index.ts:177`, `bindings/node/native/src/lib.rs:138`). Only in-memory `loadLibraries`/`loadLibrary` answer with `api_diagnostics()`. The same applies to C FFI `nx_validate_workspace` (`crates/nx-ffi/src/lib.rs:711`) and to the language service's `diagnostic_report` (`crates/nx-language-service/src/lib.rs:317`), which both call `validate_workspace`. Probe: a directory library `ui/Label.nx` containing `export let f(n:int) = { n ?? 0 }`, loaded with `loadFromDirectory`, then `workspace.validate(ctx)` for a module that imports it, returns `[]`, and nothing else surfaces the warning. design.md's Migration Plan still says "existing SDK calls keep their behavior", and D4's "These apply to directory-loaded libraries too" paragraph only mentions images and fingerprints.
- **Recommendation:** Either (a) scope the filtering to in-memory (logical-root) libraries and keep directory libraries' warnings in validation as before, or (b) keep the new rule and give directory loads the same channel, e.g. `loadFromDirectory` returns `readonly NxDiagnostic[]` from `api_diagnostics()`, and record the behavior change in design.md (D4 and Migration Plan). Add a test for whichever is chosen.
- **Fix:** Took option (a). `LogicalProgramAnalysis::workspace_diagnostics` now drops non-error diagnostics only for libraries loaded from memory (logical root, not the prelude). A directory-loaded library's diagnostics all reach validation and failed-build payloads as before, so Node `loadFromDirectory` callers, C FFI `nx_validate_workspace` and the language service's `diagnostic_report` keep their existing behavior. The one difference is that these warnings now render against the library's source text with real positions, which is the RF3 source-map fix. Tests: Rust `a_directory_library_warning_is_still_reported_by_workspace_validation` and Node `still reports a directory library's warnings through workspace validation` (both assert the warning at line 2). design.md D4, the workspace-programs spec (requirement text plus a new "A directory library's warnings are still reported" scenario), the library-registry spec, the `api_diagnostics` doc and both READMEs now scope the rule to in-memory libraries.
- **Verification:** Verified. `workspace_diagnostics` (`crates/nx-api/src/artifacts.rs:820-839`) now drops non-error diagnostics only when the library's root is logical and it is not the prelude. A directory library's diagnostics all reach validation and failed builds, as they did at HEAD. I re-ran the Node probe: after `loadFromDirectory`, the `ui/Label.nx` warning `fallback-never-taken` comes back from `workspace.validate` again, at line 2, column 25 (better than HEAD, thanks to the RF3 source-map fix). No regressions for in-memory libraries. In Node, `loadLibrary` answers with the warning and `validate` returns `[]`. The wasm `probe3` results are unchanged (load answers with the warning, tenant validation is clean, build and validate diagnostics are identical). The prelude keeps its HEAD behavior. `cargo test --workspace` passes, bindings/wasm has 74 passing, and bindings/node has 29 passing, including the new Rust and Node directory-library tests. design.md D4, the workspace-programs and library-registry specs, and both READMEs now consistently scope the rule to in-memory libraries. No new issues found.

## Questions
- For RF1: should a library root "reserve" its whole `<root>/` namespace in the workspace (rejecting `libraries/question-flow/Anything.nx`), or only the exact module identities the library holds? Reserving the prefix is simpler and also rules out future collisions when a library gains modules.
  - **Answer (fixer):** The fix reserves the whole prefix, for the reasons given, and also refuses a workspace identity equal to any linked library module's identity (which covers the prelude's).
- `loadLibraries` is not atomic: libraries earlier in the batch stay loaded when a later one fails. This is documented and retry-safe, since identical reloads are no-ops, but the error does not say which roots were loaded. Is that acceptable for ReachMe's worker-pool startup, or should the error payload list the loaded roots?
  - **Status:** Not changed. The wasm load payload on success is now the libraries' diagnostics rather than the root list (RF2), and a failure still does not say which roots loaded. Because identical reloads are no-ops, retrying the whole batch is safe. Listing the loaded roots on failure would need a failure payload other than a diagnostic array, which is an ABI shape decision for the maintainer.
  - **Resolution (maintainer, 2026-09-28):** ✅ Resolved: kept as is. This matches common module-loader behavior (Python `import`, CommonJS `require`, Cargo): what succeeded stays loaded, what failed is not retained, and a retry is idempotent. A host that needs all-or-nothing loads into a fresh registry and adopts it only on success. ReachMe's worker pool fails closed at startup, so it never serves from a partially loaded registry.
