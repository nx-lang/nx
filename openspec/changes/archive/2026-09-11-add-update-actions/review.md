## Findings

### ✅ Verified - RF1 typegen emits a dangling type name for any field typed `T.Update`
- **Severity:** High
- **Evidence:** Companions are named `<T>_update`, but a type reference `T.Update` is rendered by the generic name path and never mapped to the companion. Verified with `export type User = { name:string email:string? } export type Form = { pending:User.Update? draft:User.Update[] }`:
  - TypeScript (`crates/nx-cli/src/typegen/languages/typescript.rs:732` → `sanitize_ts_type_name` at `:764`) emits `pending: User_Update | null; draft: User_Update[];` next to `export interface User_update`; `User_Update` does not exist.
  - C# (`crates/nx-cli/src/typegen/languages/csharp.rs:890`) emits `public User.Update? Pending` and `NxOptional<User.Update[]> Draft`; C# reads that as a nested type `User.Update`, which does not exist, so the generated file will not compile.
  - The `ExportedType::Update(_)` arm at `csharp.rs:876` is dead: the graph is keyed by the companion name (`crates/nx-cli/src/typegen/model.rs:1115` sets `name: "<T>_update"`), so a lookup of `User.Update` never reaches it.
- **Recommendation:** In the TS and C# type-name resolvers, map `<T>.Update` to the `<T>_update` companion. Decide explicitly what to emit when the companion was collision-skipped or the target is not exported (today the plain-record case is also dangling, so at minimum warn). Add a typegen test for an exported record with a `T.Update`-typed field in both languages, and include the case in the checked-in .NET fixture so it is compiled.
- **Fix:** The typegen model now rewrites every `<T>.Update` type reference to the `<T>_update` companion after the graph is built (`rewrite_update_type_references` in `crates/nx-cli/src/typegen/model.rs`), so both emitters resolve it as a declared type and the C# `ExportedType::Update` arm is live. A reference with no companion (target not exported, or the name taken by an explicit declaration) is left as written with a warning naming the missing companion. Tests: `update_typed_fields_generate_as_the_companion_in_typescript`, `..._in_csharp`, and `update_typed_field_without_a_companion_warns` in `crates/nx-cli/src/typegen.rs`; the .NET fixture `update-records.nx` gained `Form = { pending:User.Update? drafts:User.Update[] }`, `UpdateRecords.g.cs` was regenerated, and `UpdateTypedFields_GenerateAsTheCompanionAndRoundTrip` compiles and round-trips it.
- **Verification:** Reproduced the original probe (`Form = { pending:User.Update? draft:User.Update[] }`): TypeScript now emits `pending: User_update | null; draft: User_update[]` and C# emits `User_update?` / `User_update[]`, both matching the declared companion. A target with no companion (non-exported, or name taken) keeps the bare name and prints a warning naming the missing companion. The .NET fixture round-trips the case. Verified.

### ✅ Verified - RF2 Live-state override clobbers a loop variable or `let` that shadows a state field
- **Severity:** Medium
- **Evidence:** `crates/nx-interpreter/src/interpreter.rs:953` re-defines every `owner_state` name from the working state after the captures are seeded, by name only. Verified: with `state { count:int = 0 items:int[] = {10 20 30} }` and `{for count in items { <Row onTapped=<Update count={count} /> /> }}`, row two's handler captured `count: 20`, but after dispatch the state's `count` is `0`. The checker binds `count` to the loop variable (it reports a type error when the loop variable is an `int` and the state field a `string`), so the runtime disagrees with static analysis. The component-action-handlers spec ("Captured locals keep their snapshot") requires loop variables and `let` bindings to keep their captured values.
- **Recommendation:** Record, at handler creation, which captured names actually resolved to the component-scope state binding (not just the owner's field-name list), and override only those at dispatch. Add an interpreter test where a loop variable shadows a state field.
- **Fix:** `eval_action_handler_expr` now records in `owner_state` only the state names whose visible binding is still the outermost (component-scope) one, via the new `ExecutionContext::is_bound_in_outermost_scope`; a loop variable or `let` that shadows a state field keeps its captured value. It also reads the effective state fields rather than the declared ones. Test: `a_loop_variable_that_shadows_a_state_field_keeps_its_captured_value` in `crates/nx-interpreter/tests/update_records.rs` (row two's handler patches `count` to `20`). Design risk list updated.
- **Verification:** Re-ran the shadowing probe: row two's handler now patches `count` to `20`, and the existing two-increments test confirms non-shadowed state reads stay live. `is_bound_in_outermost_scope` filters `owner_state` at handler creation. Verified.

### ✅ Verified - RF3 Handler bodies written as a match (`if x is { ... }`) are always rejected
- **Severity:** Medium
- **Evidence:** `crates/nx-types/src/infer.rs:686` `collect_handler_result_items` splits `Expr::Array` elements and `Expr::If` branches but falls through to the joined type for `Expr::Match`. Two different record arms join to `object`, so `onTapped={if mode is { a => <Saved /> b => <Cleared /> }}` fails with `handler-result-not-action ... found 'object'` even though both arms are emitted actions (verified; the same happens for an `<Update>` arm mixed with an action). The `if { cond => ... else => ... }` condition-list form works because it lowers to `Expr::If`.
- **Recommendation:** Add a `Match` arm that recurses into each arm body and the else branch, mirroring the `If` arm, and add a checker test for the match form.
- **Fix:** `collect_handler_result_items` gained an `Expr::Match` arm that recurses into each arm body and the else branch. Test: `a_match_result_is_routed_arm_by_arm` in `crates/nx-types/tests/update_records.rs` (accepted when every arm is an emitted action or own update; `handler-action-not-emitted` names the offending arm otherwise).
- **Verification:** `if mode is { a => <Saved /> b => <Cleared /> }` is accepted, and an arm returning an action the component does not emit is reported with `handler-action-not-emitted` at that arm. Verified.

### ✅ Verified - RF4 Rendered output assigns tokens to handlers that dispatch will always refuse
- **Severity:** Medium
- **Evidence:** `assign_tokens` (`crates/nx-interpreter/src/interpreter.rs:155`) tokens every `Value::ActionHandler`, but `ensure_handler_owned_by` (`:1216`) rejects any whose `owner` is not the snapshot's component. Verified: `let makeButton() = <Button onTapped=<Saved /> />` rendered from `Form`'s body produces `onTapped` with `owner: None, token: "h1-1"`, and dispatching that token fails with "handler token 'h1-1' bound elsewhere". The same applies to an external component's init output, whose rendered value is its props record carrying parent-bound handlers. The design risk note only asks to refuse a token whose owner is a *different* component; the spec says a root-bound handler's results are host effects.
- **Recommendation:** Either accept `owner: None` handlers in dispatch and route all their results to `effects`, or skip token assignment for handlers the snapshot's component does not own so the rendered output does not advertise an invocable handler. Add a test either way.
- **Fix:** Dispatch no longer refuses tokens by owner. `handler_is_owned_by` decides whether the handler was bound inside the snapshot's component: an owned handler reads state live and its own update records patch state; any other tokened handler (root-bound, or bound by a parent whose output this instance renders) runs from its captures alone and every result is an effect, which is exactly what the existing action-entry path does for parent-bound handlers. This follows the spec's routing rule ("host effect when bound outside any component body") and the D6 requirement that every bound handler carries a token. Tests: `a_root_bound_handler_in_the_output_runs_and_its_results_are_effects` and `a_parent_bound_handler_on_an_external_instance_runs_and_its_results_are_effects` in `crates/nx-interpreter/tests/update_records.rs`. Design risk bullet and the reference docs updated to say so.
- **Verification:** A root-created handler rendered inside `Form` now dispatches by its token and returns `Saved` as an effect; `handler_is_owned_by` gates live state and state patching only. Both new integration tests present. Verified.

### ✅ Verified - RF17 A record nested under a component-typed prop is not constructed at all
- **Severity:** Low
- **Evidence:** `coerce_value_to_resolved_type` (`crates/nx-interpreter/src/interpreter.rs:3175`) admits a host record whose `$type` names a component through `component_type_satisfies_expected`, then hands it to `construct_host_record_value` (`:3827`), which resolves only records and union cases and otherwise returns the fields as supplied. Verified with `component <Editor pending:User.Update /> = { ... }` and `component <Wrap inner:Editor /> = { <Panel inner={inner} /> }`: initializing `Wrap` with `inner` set to `{ $type: "Editor", pending: { $type: "User.Update", name: null, nick: "a" } }` succeeds and renders that value unchanged, carrying both a `null` for the non-nullable `name` and the undeclared `nick`. The same program with `<Wrap inner=<Editor pending=<User.Update name={null} nick="a" /> /> />` is rejected by the checker. The component-runtime-bindings requirement "Host-supplied records are constructed at every depth" says a host record is constructed "against the declaration its type name reaches, at every nesting depth"; a component declaration is reached here and nothing below it is checked.

An unknown prop or a non-handler value in a handler slot fails there too. The requirement text, a new scenario "A record under a component-typed prop is checked", design D2, task 3.9, and the reference-docs sentence name component values.
- **Verification:** `construct_host_record_value` (`crates/nx-interpreter/src/interpreter.rs:3872`) resolves a component and routes it through `ensure_concrete_component` and `normalize_component_props` in the component's own module. ### ✅ Verified - RF18 A raw batch entry with no bound handler is checked by name only
- **Severity:** Low
- **Evidence:** For a batch entry that is not a handler invocation, `dispatch_component_actions_with_limits` (`crates/nx-interpreter/src/interpreter.rs:1129`) calls `validate_component_action`, which matches the record's type name against the component's `emits` and nothing else. The payload is constructed (through `validate_handler_input` → `construct_external_record_value`) only when the snapshot's props hold a parent-bound handler for that action; otherwise the entry is dropped silently. Verified with `component <Editor emits { Apply { patch:User.Update } } />` initialized with no handler props: dispatching `{ $type: "Editor.Apply", patch: { $type: "User.Update", name: null } }` returns success with no effects, while the same entry against an instance whose parent bound `onApply` fails with "non-null value for 'name'". The requirement says a record the host supplies through "a dispatch batch entry SHALL be constructed from its fields ... at every nesting depth" without a handler condition, and the design's D2 paragraph repeats it. Dropping an unbound entry without error is also unstated anywhere.
- **Recommendation:** Construct every raw entry against its emitted action's declaration in `validate_component_action` (or immediately after it) before looking up the handler, so a drifted DTO fails whether or not a parent bound the handler. Decide and state whether an entry with no bound handler is a no-op or an error, and add a scenario plus an interpreter test for the unbound case.
- **Fix:** Dispatch now constructs every action entry through `validate_handler_input` against the emit's declaration (`emit.module_identity`) right after `validate_component_action` and before the handler lookup, so a drifted payload fails whether or not a parent bound the handler. The no-op question was already settled: the main `component-action-handlers` spec's "Unbound emitted actions do not produce effects" requires an unbound entry to contribute no effects, so a well-formed unbound entry stays a no-op; the dispatch doc comment now says both. Test: `a_host_action_entry_with_no_bound_handler_is_still_checked` (well-formed entry yields no effects; `name: null` fails naming `name`). The requirement text and a new scenario "An action entry with no bound handler is still checked", design D2, task 3.9, the reference docs, and the .NET README say it. A bound entry is now constructed twice (once here, once by the handler); the second pass is idempotent and was kept for simplicity.
- **Verification:** `dispatch_component_actions_with_limits` (`crates/nx-interpreter/src/interpreter.rs:1133`) constructs every action entry through `validate_handler_input` before the handler lookup. Re-ran the original probe: an unbound `Editor.Apply` carrying `name: null` now fails naming `name`; an unknown field and a missing required field on an unbound entry fail likewise, and a well-formed unbound entry still yields no effects, matching the main spec's "Unbound emitted actions do not produce effects". The double construction of a bound entry is harmless: an entry with a defaulted field produced one effect with the default filled once. The scenario, D2, task 3.9, the dispatch doc comment, the reference docs, and the .NET README are present. Verified.

## Questions

### ✅ Answered - Q1 Is the prop boundary in scope for "runtime construction enforces the same rules"?
- **Question:** Host-supplied update records in props were not validated: `coerce_value_to_resolved_type` passed any record through when the type name matched, so a prop typed `User.Update` accepted `{ nick: "a" }` or `{ name: null }` at init. This was pre-existing behavior shared with plain records, but the update-records spec's "Runtime construction enforces the same rules when static analysis is bypassed" reads as if it should apply at that boundary too.
- **Answer:** Yes. The gap was wider than props: every host boundary validated one level deep and no further. The props record at init and the action record at dispatch were rebuilt from their shape, but any record nested inside them (a prop typed `User.Update`, an element of `User.Update[]`, a `patch:User.Update` field of an action payload, a payload union case) was accepted by type name alone. For plain records that was harmless noise; for update records it let a drifted host DTO turn "unchanged" into "set to null" silently.
- **Fix:** The interpreter's coercion path now carries a `ValueOrigin`. A value the interpreter produced keeps the by-name record check, so ordinary function calls pay nothing. A value the host supplied through props, explicit state, or a batch entry is rebuilt from its fields against its declaration at every depth (`construct_host_record_value`, which the handler-input path also uses now), so unknown fields, `null` in a non-nullable slot, and missing required fields are reported at the boundary. Specified as the component-runtime-bindings requirement "Host-supplied records are constructed at every depth" with five scenarios; recorded as task 3.9 and in design D2 and its risk list; one sentence each in the reference docs and the .NET README.
- **Verification:** Seven end-to-end tests in `crates/nx-interpreter/tests/update_records.rs` (update record in a prop kept / unknown field / non-nullable null, in a prop array, in an action payload at dispatch, in explicit state at evaluate, and a nested plain record missing a required field) and `UpdateRecord_PassedAsAProp_WithAnUnknownField_IsRejectedAtInitialization` in `NxUpdateRecordTests.cs` through the FFI. `cargo test --workspace` and `dotnet test` (109 passed) green; `openspec validate add-update-actions --strict` valid. Two loose ends noted in `docs/add-update-actions-followsup.md`: host record construction evaluates nested defaults outside the call's resource limits, and host union case payloads resolve by name from the owner module.

### ✅ Answered - Q2 Should a handler bound outside the component be dispatchable from a component snapshot?
- **Question:** RF4: should a handler bound outside the component (`owner: None`) be dispatchable from a component snapshot with all results routed to effects, or should it simply not carry a token?
- **Answer:** It stays tokened and dispatchable, and everything it returns is an effect; the same applies to a handler bound by a different component. A host should not need to know where a handler was bound, and this matches what the action-entry path already did for parent-bound handlers. Resolved by the RF4 fix.
