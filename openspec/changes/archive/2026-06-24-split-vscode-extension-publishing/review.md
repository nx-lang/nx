## Findings

### ✅ Verified - RF1 VS Code extension publish workflow is not idempotent, so the documented repair flow cannot recover a partial publish
- **Severity:** Medium
- **Evidence:** The sibling `package-publish.yml` deliberately treats "already published" as an idempotent retry: NuGet uses `dotnet nuget push --skip-duplicate` ([package-publish.yml:243](../../../.github/workflows/package-publish.yml#L243)) and npm checks `npm view` and skips with a warning instead of failing ([package-publish.yml:209-214](../../../.github/workflows/package-publish.yml#L209-L214), [package-publish.yml:261](../../../.github/workflows/package-publish.yml#L261)). The new VS Code publish workflow does the opposite: `version:check:vsix` *throws* if the version already exists in either registry ([check-vsix-version.mjs:36-37](../../../src/vscode/scripts/check-vsix-version.mjs#L36-L37), [check-vsix-version.mjs:49-50](../../../src/vscode/scripts/check-vsix-version.mjs#L49-L50)), and `publish-vsix.mjs` passes no skip-duplicate flag ([publish-vsix.mjs:11-24](../../../src/vscode/scripts/publish-vsix.mjs#L11-L24)). The old combined job guarded the version check with `if: ${{ inputs.repair_run_id == '' }}`; the new workflow runs it unconditionally ([vscode-extension-publish.yml:160-165](../../../.github/workflows/vscode-extension-publish.yml#L160-L165)). The typical repair trigger — Marketplace succeeded but Open VSX failed (or vice-versa) — will now fail at the version check (or, if that were bypassed, at the first `publish:vsce`/`publish:ovsx` step) before it can republish the missing registry. `docs/deployment.md` actively promotes this `gh workflow run vscode-extension-publish.yml ... -f artifact_run_id=` repair path ([deployment.md:74](../../../docs/deployment.md#L74)), so the documented recovery action does not work for the most common partial-failure case.
- **Recommendation:** Make publication idempotent per registry, mirroring the package workflow: detect "already published" for each of Marketplace/Open VSX and skip that registry instead of failing the run (e.g. reuse the `versionAppearsInOutput` probe to gate each publish step, or add `--skip-duplicate` where the CLI supports it). At minimum, restore a repair bypass so an already-published registry does not block republishing the other.
- **Fix:** Updated `publish-vsix.mjs` to check the selected registry for the VSIX version before publishing and exit successfully when that version is already present. Removed the global workflow version check that required both registries to be empty, and documented that VSIX repair skips already-published registry versions.
- **Verification:** Confirmed. `publish-vsix.mjs` now probes the target registry per-registry (`isAlreadyPublished()` at [publish-vsix.mjs:70-99](../../../src/vscode/scripts/publish-vsix.mjs#L70-L99)) and exits 0 when the version is already present, while still failing closed on unexpected probe errors ([publish-vsix.mjs:92-93](../../../src/vscode/scripts/publish-vsix.mjs#L92-L93)). The global `Check extension versions` step is gone from the workflow ([vscode-extension-publish.yml:145-180](../../../.github/workflows/vscode-extension-publish.yml#L145-L180)), so a Marketplace-succeeded/Open-VSX-failed repair now skips `publish:vsce` and proceeds to `publish:ovsx`. `docs/deployment.md` documents the skip behavior ([deployment.md:76-78](../../../docs/deployment.md#L76-L78)). The operational repair defect is resolved. **Note:** this skip-and-succeed behavior now diverges from the change's own spec scenario — tracked as RF4 below.

### ✅ Verified - RF2 New production-secret publish workflow uses floating action tags while the sibling publish workflow pins to commit SHAs
- **Severity:** Medium
- **Evidence:** `package-publish.yml`, the established production-publish workflow, pins every third-party action to a full commit SHA (`actions/checkout@08c6903…`, `actions/download-artifact@634f93…ce0 # v5`, `actions/setup-node@49933ea…`). The new `vscode-extension-publish.yml`, which also runs in the `production` environment with `VSCE_PAT`/`OVSX_PAT` secrets, uses mutable tags instead: `actions/checkout@v4`, `pnpm/action-setup@v4`, `actions/setup-node@v4`, and `actions/download-artifact@v4` ([vscode-extension-publish.yml:100-126](../../../.github/workflows/vscode-extension-publish.yml#L100-L126)). This is both a supply-chain hardening regression relative to the sibling and a version drift (download-artifact `v4` here vs `v5` in package-publish).
- **Recommendation:** Pin the actions in the new publish workflow to commit SHAs to match `package-publish.yml`, and align the `download-artifact` major version.
- **Fix:** Pinned the production publish workflow actions to commit SHAs, using the same pinned checkout, setup-node, and download-artifact actions as the sibling package publish workflow, and pinned `pnpm/action-setup` to the current `v4` commit.
- **Verification:** Confirmed. `checkout@08c6903…` ([vscode-extension-publish.yml:103](../../../.github/workflows/vscode-extension-publish.yml#L103)), `setup-node@49933ea…` ([:112](../../../.github/workflows/vscode-extension-publish.yml#L112)), and `download-artifact@634f93…ce0 # v5` ([:123](../../../.github/workflows/vscode-extension-publish.yml#L123)) now match the SHAs in `package-publish.yml` exactly, resolving both the pinning gap and the v4/v5 drift. `pnpm/action-setup@b906affc…ce14559ad1aafd4ab0e942779e9f58b1 # v4` ([:106](../../../.github/workflows/vscode-extension-publish.yml#L106)) is now SHA-pinned (no sibling reference exists since the package workflow does not use pnpm; the SHA was not independently cross-checked against upstream but is correctly formatted and labeled v4).

### ✅ Verified - RF3 Expected VSIX targets are hardcoded and duplicated from the source build matrix
- **Severity:** Low
- **Evidence:** The validation hardcodes the three artifact names `vscode-vsix-linux-x64 vscode-vsix-darwin-arm64 vscode-vsix-win32-x64` ([vscode-extension-publish.yml:77](../../../.github/workflows/vscode-extension-publish.yml#L77)) and the download step asserts exactly 3 VSIX files ([vscode-extension-publish.yml:131-136](../../../.github/workflows/vscode-extension-publish.yml#L131-L136)). These mirror the matrix in `vscode-extension.yml` ([vscode-extension.yml:27-33](../../../.github/workflows/vscode-extension.yml#L27-L33)) with no shared source. Adding or removing a platform target in the build matrix would silently break publishing (missing-artifact error or wrong count) with no compile-time link between the two files.
- **Recommendation:** Document the coupling with a comment in both files, or derive the expected target set dynamically (e.g. from the downloaded artifact names) rather than a fixed list/count.
- **Fix:** Replaced the hardcoded VSIX artifact names and fixed count with dynamic discovery of `vscode-vsix-*` artifacts from the source run, then verified the downloaded VSIX file count matches the discovered artifact count.
- **Verification:** Confirmed. The `prepare` job now greps `^vscode-vsix-` artifacts from the source run, fails only when zero are found, and exports `vsix_artifact_count` ([vscode-extension-publish.yml:77-89](../../../.github/workflows/vscode-extension-publish.yml#L77-L89)); the download step verifies the downloaded `.vsix` count against that discovered count rather than a literal `3` ([vscode-extension-publish.yml:134-140](../../../.github/workflows/vscode-extension-publish.yml#L134-L140)). No hardcoded target list or fixed count remains, so adding/removing a build-matrix target no longer silently breaks publishing.

## New Findings Discovered During 2026-06-24 01:05 Verification

### ✅ Verified - RF4 RF1 idempotency fix now contradicts the change's own "Extension version is not publishable" spec scenario
- **Severity:** Low
- **Evidence:** The change's delta spec requires a hard failure when the version is already published: *"WHEN ... the computed VSIX version is already published to the target registry ... THEN the workflow MUST fail before publishing to any registry"* ([specs/vscode-extension-publishing/spec.md:30-35](specs/vscode-extension-publishing/spec.md)). The RF1 fix changed this to skip-and-succeed: `publish-vsix.mjs` exits 0 when the version is already present ([publish-vsix.mjs:96-98](../../../src/vscode/scripts/publish-vsix.mjs#L96-L98)), and the global version-check step that previously enforced the failure was removed from the workflow. The implementation is operationally correct (it enables the repair flow), but it no longer matches its own spec scenario, so the spec and code now disagree on the required behavior for an already-published version.
- **Recommendation:** Reconcile the spec with the chosen idempotent-skip semantics — e.g. reword the "Extension version is not publishable" scenario so the "already published" branch describes skipping that registry and succeeding (reserving MUST-fail for the genuinely "cannot compute a registry-valid version" branch), and ensure the "version checks pass in the publish workflow" wording in the "Publish to both registries" scenario reflects the now-inline per-registry probe. This also answers the RF1 Question: the repair model is "fill in the missing registry for the same version," which should be stated in the spec.
- **Fix:** Updated the VS Code extension publishing delta spec to reserve hard failure for invalid/uncomputable VSIX versions, add an idempotent already-published registry skip scenario, describe same-version manual repair to missing registries, and replace the broad "version checks pass" wording with per-registry publication checks/idempotent skips.
- **Verification:** Confirmed, and the change still passes `openspec validate --strict`. The former "Extension version is not publishable" scenario is now "Extension version is invalid" with only the uncomputable-version MUST-fail branch ([spec.md:30-33](specs/vscode-extension-publishing/spec.md)); a new "Already-published registry version is skipped" scenario describes idempotent per-registry skip plus continuing to registries where the version is missing ([spec.md:35-42](specs/vscode-extension-publishing/spec.md)) — an exact match for `isAlreadyPublished()` in [publish-vsix.mjs:70-99](../../../src/vscode/scripts/publish-vsix.mjs#L70-L99). The manual-repair scenario gains a same-version skip/fill bullet ([spec.md:51-52](specs/vscode-extension-publishing/spec.md)) matching `docs/deployment.md`, and the "Publish to both registries" scenario replaces "version checks pass" with per-registry checks/idempotent skips ([spec.md:67](specs/vscode-extension-publishing/spec.md)). Spec and implementation now agree; the invalid-version MUST-fail case remains enforced upstream at `version:stage`/`package:verify` and by registry CLI rejection.

## Summary
- The split is implemented cleanly and matches the specs: the source `VS Code Extension` workflow now only builds/verifies/uploads VSIX artifacts, the new `Publish VS Code extension` workflow gates registry writes behind source-run validation and the `production` environment, the `Cargo.toml` URL is corrected with no stale `bret/nx` references remaining, and the docs accurately describe two explicit publish actions plus the Rust-out-of-scope note. Requirement coverage is good.
- The main gap is operational rather than structural: the publish/repair path is non-idempotent (RF1) and diverges from the hardened, idempotent pattern already established in `package-publish.yml` (RF1, RF2). RF3 is a low-severity maintainability coupling. No accidental Rust publishing or PR-context registry writes were found.
