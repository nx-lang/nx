## Findings

### ✅ Verified - RF1 A value that holds another value twice grows exponentially for a few operations per level, so the budget bounds neither time nor allocation
- **Severity:** High
- **Evidence:** The cost model charges for items placed in a sequence and for concatenated text, on the premise that "all growth comes from sequence-building nodes and from `concat`" (`design.md`, Context) and therefore "everything an evaluation builds is bounded by its budget" with a quadratic worst case for reads (`docs/nx-ir-format.md:629-633`, `runtime/typescript/README.md:176`, `crates/nx-ir-runtime/README.md:214`). A record that references one value twice breaks the premise: the value is shared, so each level costs a constant number of operations, but checking it against a type, and converting it for the host, walks it as a tree. Probe program:

  ```nx
  type Tree = { kids?:Tree+ }
  let grow(n:int, t:Tree): Tree = { if n == 0 { t } else { grow(n - 1, <Tree kids={ t t } />) } }
  let held(n:int): int = { if grow(n, <Tree />) == <Tree /> { 1 } else { 0 } }
  let build(n:int): Tree = { grow(n, <Tree />) }
  ```

  Each level of `grow` costs 15 operations (`held(4)` 73, `held(8)` 133, `held(12)` 193, `held(16)` 253), and every run below succeeded under a budget of 100,000:

  | Call | Operations | TypeScript runtime | Rust runtime (release) |
  | --- | --- | --- | --- |
  | `held(16)` | 253 | 0.55 s, 335 MB peak RSS | 1.1 s, 61 MB peak RSS |
  | `held(18)` | 283 | 2.1 s, 598 MB | 5.0 s |
  | `held(20)` | 313 | 9.4 s | 19 s |
  | `held(22)` | 343 | 55 s | 78 s |
  | `build(16)` | 249 | 0.63 s | 0.81 s, 94 MB |

  Time and memory double per level. `held(60)` would cost about 913 operations and sits well inside the default call depth of 100, so a budget of 1,000 does not stop a call that never finishes. In `held` the value never reaches the host: the growth is in the argument check at each call (`normalizeValue`, `runtime/typescript/src/index.ts:3700`; `Machine::normalize`, `crates/nx-ir-runtime/src/normalize.rs:111`), which also un-shares the value in memory. In `build` the result conversion adds to it (`to_host`, `crates/nx-ir-runtime/src/value.rs:340`). This is the failure the change exists to prevent: a tenant function hanging a Durable Object (`proposal.md`, Why), and in the Rust runtime an allocation failure that aborts the process, which `design.md` decision 2 says the item and string charges "stand between". It also contradicts the scenario "the runtime SHALL NOT have allocated a list or a string the budget does not pay for" in spirit and the goal "a host bounds the work and the allocation of one evaluation call with one number".
- **Recommendation:** Decide how values with shared structure are bounded before hosts rely on the budget for code they did not write. Options, roughly in order of how much they change: (a) charge the walks that are linear in a value's tree size, at least the type check of an argument or field and the conversion of a result for the host, one operation per value visited, so the count stays deterministic without fixing a walk order for equality; (b) make re-checking free in fact, by not re-walking (or re-copying) a value that a typed construction already produced, and bound the result conversion separately; (c) charge a record or union-case construction for the size of what it holds. Whichever is chosen, add the probe above to both runtimes' tests and to the `evaluation-cost` corpus program, and correct the "bounded by its budget" and "quadratic" statements in `docs/nx-ir-format.md` and both READMEs, and decision 2 and the first risk in `design.md`, which today tell a host that 100,000 is on the order of a second in the worst case.
- **Status:** Confirmed and left open for the author to decide; not a fix to make unasked. Reproduced with the probe in the TypeScript runtime: `held(16)` takes 0.54 s under a budget of 1,000, and the time quadruples every two levels. It is not fixed here because every remedy changes what an operation is. The `nx-ir-format` requirement this change adds says that checking a value against a type and comparing two values "SHALL cost nothing", so a fix rewrites that requirement, its worked counts and every recorded corpus count, and there is more than one defensible design. Recommendation, a variant of option (c): charge a value's size where it is placed. Placing an item in a sequence, or binding a property or content value of a constructed record, union case, element or component, costs the number of values it holds (a primitive 1, a sequence the sum of its items, a record 1 plus its fields), counted by a walk that stops once it passes what the budget has left and is skipped when no budget is set. That makes the tree size of everything an evaluation builds at most its budget, which is the premise the documented bound needs, so the quadratic statement becomes true; the walk's work is proportional to the operations it charges; an evaluation with no budget pays nothing; and the count needs no walk order for equality, which is why option (a) was set aside in `design.md`. Option (b) alone does not close it: equality and the host conversion still walk the value as a tree. Until this is decided the "bounded by its budget" statements in `docs/nx-ir-format.md`, both READMEs and `design.md` are wrong, and they are unchanged; nothing of this change is committed.
- **Fix:** (at the user's direction, after the status above) The cost model now charges every walk over a value, in both runtimes, in place of the size-at-placement charge the status note proposed; the user chose this after discussing both, and it needs no walk of its own. Three charges are added to `nx-ir-format`: one per value checked against a type that is not a sequence type (host input included); one per pair of values an equality compares, with no early exit inside a sequence or a record so that the count does not depend on field order, plus one per 64 code units of the shorter of two strings; and one per value written for the host, plus one per 64 code units of a string, for results, descriptors, rendered output, effects and state. The string charges close a second instance of the same hole found while fixing this one: a list of 100 references to one string of 16,384 code units cost 896 operations and was 1.6 million code units to the host. Rust: `Machine::normalize` charges after a sequence type is taken apart; `values_equal`, `handlers_equal`, `to_host` and `update::diff` take a `Meter` (`eval.rs`, `mod meter`) that charges an evaluation with a budget and nobody otherwise; `check_depth`, the one walk only this runtime makes, looks into a shared allocation again only when it is reached deeper (`value.rs`). TypeScript: `normalizeValue`, `valuesEqual`, `handlersEqual` (new: handlers compare by node and captures, as in Rust, where they compared internal objects field by field), `canonicalizeRendered`, and `chargeWrittenFields` for state, which this runtime returns without rewriting. Tests: `a_value_shared_many_times_over_is_paid_for_wherever_it_is_walked` and `a_string_held_many_times_over_is_paid_for_each_time_it_is_written` in `ir_runtime_tests.rs`, and the matching block in `emitted-ir.test.mjs`, run the probes at forty levels for each walk (checked, compared, written, stored in state, and held without being walked, which must cost under 1,000). The corpus program `evaluation-cost` gains `checked`, `compared`, `comparedText` and `written`, and every `operations.json` is regenerated; the two runtimes agree on every count and recorded failure. The worked counts, the bound ("proportional to its count", replacing the quadratic caveat) and the non-goal of charging reads are corrected in `specs/`, `design.md` (decision 2), `proposal.md`, `tasks.md` (section 7), `docs/nx-ir-format.md`, both READMEs and the corpus README, and the reasoning for the default budget in `add-agent-host-package`'s design, which cited the quadratic bound, is corrected with the number left alone. With no budget set the walks skip charging altogether, since nothing reads the count; overhead numbers for five cases are in `design.md`, decision 10.
- **Reviewer note (2026-10-03 02:50):** Not marked fixed, so not verified; it stays open for the user. The reasons given for leaving it are sound: every remedy rewrites the `nx-ir-format` requirement and every recorded count. By my reading the proposed variant of (c) would stop the probe (placing `t` twice would cost twice the size of `t`, so the cost doubles with the value), but that is a reading of the proposal, not something tested.
- **Verification:** (2026-10-03 13:56) Verified for the hole as reported. The original probe now stops on the budget at every depth, in both runtimes, with flat time and memory: under a budget of 100,000, `held` and `build` at 12, 16, 22 and 60 levels each fail naming `maxOperations` in 12 to 15 ms and 6 to 13 MB in Rust and in 40 to 57 ms and about 80 MB in TypeScript (`held(8)` now costs 6,771 and `held(12)` 139,431, where they cost 133 and 193). ### ✅ Verified - RF5 The Rust `concat` charge scans both operands on every concatenation, budget or not
- **Severity:** Low
- **Evidence:** `charge_concat` (`crates/nx-ir-runtime/src/eval.rs:663`) decodes both operands to count UTF-16 code units whenever their byte lengths sum to 64 or more, including when `max_operations` is `None`. Measured with a loop of 200,000 concatenations of 80 code units, no budget: +1 to +3 percent against the commit before the change, the same as the arithmetic loop. Recorded in `design.md`, decision 10.
- **Verification:** Verified by reading and by measurement. `charge_concat` returns before touching either operand when `max_operations` is `None`, which cannot change a result since an absent budget cannot be exhausted; `utf16_len` takes the byte length for ASCII; the non-ASCII counts are still pinned by the `é` cases and the corpus `concat` entrypoint; `place` and `charge` behave as before. That is noisier than the +1 to +3 the fix note reports but under the tasks' 5 percent, and the scan the finding was about is gone.

### ✅ Verified - RF7 In the Rust runtime a budget changes the result of an equality
- **Severity:** Medium
- **Evidence:** `values_equal` and `handlers_equal` return true for two values that are one allocation only when nothing is charged (`crates/nx-ir-runtime/src/value.rs:206`, `:243`); under a budget they compare the fields. The two disagree for a value that holds a NaN. With `type F = { v:float64 }`, `let selfEq(f:F): boolean = { f == f }` and `v` computed as infinity minus infinity (a float multiplied past its range, twice), `selfEq` returns `true` with no budget and `false` under any budget that covers the call (it costs 1,970), and the same for an untyped element compared with itself. The TypeScript runtime returns `false` both ways. So setting `max_operations` changes what a successful evaluation returns, and the Rust runtime with no budget disagrees with the TypeScript runtime, where the spec promises the same result. `design.md` decision 2 presents the shortcut as invisible ("taken only where nothing is charged, since a count has to see through it").
- **Recommendation:** Make the result independent of the meter: drop the one-allocation shortcut, which the TypeScript runtime never had, or keep it only where it cannot change the answer. Add the NaN case to both runtimes' tests, with and without a budget.
