### ✅ Verified - RF1 A dispatch runs against an ancestor that holds an equal handler, not the same one, so a component nested under itself patches the wrong instance
- **Severity:** High
- **Evidence:** `InstanceTree::creator` (`crates/nx-ir-runtime/src/tree.rs:399-409`) takes the farthest ancestor for which `ComponentInstance::token_of` answers, and `token_of` (`crates/nx-ir-runtime/src/component.rs:107-114`) compares with `same_handler`, which is `Arc::ptr_eq(..) || handlers_equal(..)` (`component.rs:131-133`): the same handler node with an equal capture counts as the same handler. Two instances of one component, one under the other, whose props and state are equal hold handlers that are equal and are not one handler. The TypeScript tree compares identity (`held === handler`, `instances.ts:112-119`). Reproduced with
  `component <Rec extends Node /> = { state { open:boolean = false } <Stack><Button Text="Toggle" onTapped=<Update open={!open} /> />{ if open { <Rec /> } else { <Label Text="closed" /> } }</Stack> }`:
  open the outer, visit the inner under it, tap the inner's toggle (inner `open` becomes `true`, as expected), tap the inner's toggle again with its current token. Expected inner `false`, outer `true`; actual inner `true`, outer `false`. `route` resolves an emit's handler through the same function (`tree.rs:393-394`), so an emit can be carried past the parent that bound it in the same way. No test nests a component under itself.
- **Recommendation:** Compare identity in `token_of` (`Arc::ptr_eq(held, handler)`). A handler reaches a child only by `Arc::clone` (`resolve_parent_handlers`, `component.rs:233`; `to_host_at`, `value.rs:638`), so identity is what "the same handler" means inside one tree. Checked in a patched copy of the crate: with `ptr_eq` the reproduction passes and all 30 `ir_instance_tree` tests still pass. Add the reproduction as a test, and say "the same handler" means the one allocation in the spec's `A handler runs against the instance whose body bound it` requirement if it is meant to be read that way.
- **Fix:** `ComponentInstance::token_of` compares identity (`Arc::ptr_eq`), with a comment saying why (`crates/nx-ir-runtime/src/component.rs`); the public `same_handler` and `bound_handler_is` keep their comparison by value. The reproduction is the test `a_component_nested_under_itself_is_told_from_its_ancestor` in `ir_instance_tree_tests.rs`. The spec's `A handler runs against the instance whose body bound it` now says the same handler is the very handler that was handed down, with a scenario of that name, and the design records the decision and what the first implementation got wrong.
- **Verification:** (2026-10-07 12:07) Verified. `token_of` compares with `Arc::ptr_eq` (`component.rs:115-122`). My reproduction now leaves the outer open and closes the inner, and a three-deep variant (all three instances open, each toggled in turn, with and without passes) patches only the node tapped. `a_component_nested_under_itself_is_told_from_its_ancestor` covers it; the spec and design say identity.

### ✅ Verified - RF2 Comparing nested values is a recursion the stack budget does not bound, and it overruns a stack whose budget and margin are set as the README says
- **Severity:** Medium
- **Evidence:** `values_equal`, `records_equal` and `handlers_equal` (`crates/nx-ir-runtime/src/value.rs:189-229`, `262-323`, `328-351`) recurse once or twice for each level two values nest and ask neither a depth count nor `Stack::within`. They are reached from `==` and `!=` (`eval.rs:777`), match patterns (`eval.rs:1568`) and `diff` (`update.rs:99`). `Depths::levels_of` (`value.rs:391`) is a second unchecked walk, bounded only by the 256 levels. The modified requirement says the budget "SHALL bound every recursion the runtime makes over an image or a value" and that an evaluation that would use more fails "before the stack is exceeded"; the README says the budget is checked "at every expression and every value it walks" and that a margin covers the rest (`crates/nx-ir-runtime/README.md:350`). Reproduced in a native release build: a thread with `budget + margin + 8 KiB` of stack, `max_stack_bytes = budget`, `let burnEq(k:int, a:object, b:object): boolean = { if k <= 0 { a == b } else { burnEq(k - 1, a, b) } }` called for `k = 0..400` with two host records nested 100 deep. Budget 128 KiB with a 32 KiB margin (the README's example value): `thread has overflowed its stack`, abort, at `k = 91`. Budget 64 KiB, margin 8 KiB, 40 levels: the same. The same recursion with `true` in place of `a == b` returns a value or a `maxStackBytes` diagnostic for every `k`, at every margin tried, so the comparison is what leaves the stack. The tests of task 1.3 exercise only the evaluator's check and the host-boundary walks.
- **Recommendation:** Give the comparison the budget: pass the `Stack` (or the `Machine`) to `values_equal`/`records_equal`/`handlers_equal` and to `Depths::levels_of`, and fail with `value_too_deep()` at each value that holds others, as `from_host_at` and `to_host_at` now do. Add a test shaped like the reproduction (a spawned thread with a small real stack makes an overrun a failed test rather than a passing one). The update helpers and `changed` keep the default budget by design (`helpers.rs:10-14`); the README's *Small stacks* section should say so, since a host that cannot give the default budget cannot lower theirs.
- **Fix:** `values_equal`, `records_equal`, `handlers_equal` and `Depths::check`/`levels_of` take the call's `Stack` and fail with `value_too_deep()` at each value that holds others (`value.rs`); `==`, match patterns, `diff` and `patch_state` pass the machine's (`eval.rs`, `update.rs`, `component.rs`). The helpers and `same_handler`/`bound_handler_is`, which take no options, pass the default budget. Tests: `a_comparison_and_the_nesting_walk_stop_at_the_stack_budget` in `value.rs` (200-level values, a 1 KiB budget, each of the four walks, in any build), and the reproduction as `a_comparison_far_down_a_recursion_stays_within_a_small_stack` in `ir_runtime_tests.rs`, on a thread whose stack is the budget, the margin and 8 KiB. In a release build that test aborts with a stack overflow when the comparison's check is taken out (checked), and passes with it; an unoptimized build needs a larger budget and margin for its frames, so there the unit test is the one that pins the check. The spec's stack paragraph names the comparison and the nesting walk and says the APIs without options walk under the default budget, with the scenario `A comparison of deep values stops at the stack budget`; the README's *Small stacks* lists what the budget covers and which calls keep the default.
- **Verification:** (2026-10-07 12:07) Verified for the walks the finding named. `values_equal`, `records_equal`, `handlers_equal` and `Depths::levels_of` ask the call's `Stack` at each value that holds others (`value.rs:192-200`, `415-421`), and `==`, match patterns, `diff` and `patch_state` pass the machine's. The release probe that aborted (`budget 128 KiB, margin 32 KiB, 100 levels`) now returns a value or a `maxStackBytes` diagnostic for every `k`, as do eight other budget, margin and depth combinations down to an 8 KiB margin. Both new tests pass in debug and `--release`, and the charges are unchanged (the cost and corpus tests pass). The README and spec list what the budget covers and which calls keep the default. A different recursion still leaves the stack under the same settings; it is RF8 below, not a defect of this fix.

### ✅ Verified - RF3 An event dispatched before the pass that follows an earlier dispatch is misrouted without a diagnostic
- **Severity:** Medium
- **Evidence:** After a node is dispatched against, the nodes under it still hold handlers of its previous instance until the next pass initializes them again. A dispatch in that window finds no ancestor that holds the handler and silently falls back. Three reproductions, each a second `dispatch` with no pass between:
  - The spec's three-deep shape, the leaf tapped twice: the second `Leaf.Picked` comes back as a `HostEffect` and neither `Middle` nor `Top` changes. `route` (`tree.rs:393-394`) returns `None` when no ancestor holds the bound handler and the caller treats that as "nobody bound it" (`tree.rs:362-369`). The requirement says an effect "SHALL be routed when ... the node holds a handler its parent bound for that emit", which it does.
  - `Page` with a button of its own and a `Card` whose `onLogged` it binds: tap the page's button, then the card's. `Card.Logged` is returned to the host and `Page.last` stays empty.
  - `Page`'s button drawn in a `Box`'s content, the same token dispatched twice through the `Box`: the second dispatch runs `Page`'s handler against the `Box` instance (`creator` finds only the `Box`, `tree.rs:334`), the lifecycle treats it as not owned (`component.rs:993-1011`), and the host receives a `Page.Update { count: 1 }` record as a `HostEffect`. `Page.count` stays `1`.

  All three return `Ok`. A host that queues input and draws once a frame meets this with any double tap. The TypeScript tree does the same, so this is inherited, but the Rust tree is the one being specified, and neither the spec nor the README says a pass must separate two dispatches (the README's example ends with "Then draw again", `README.md:255`).
- **Recommendation:** Make the stale case a failure instead of a result. A handler records the component whose body bound it (`Handler::owner`, `value.rs:84`), so both cases are detectable: fail with `nx-ir-handler-token` when the node `creator` resolves is not an instance of the handler's owner, and when a node holds a bound handler for an emit and no ancestor holds that handler. The dispatch is already atomic, so the host redraws and may retry. Add a scenario and tests for it. If the fallback is intended, state the "one pass after every dispatch" rule in the spec and the README instead and say what a dispatch outside it returns.
- **Fix:** Made the stale case a failure, as recommended, with a test that is exact where `Handler::owner` would not be (a component nested under itself has the owner's component at both levels). A node receives a handler it did not create only from the instance it was initialized through, which the node already keeps (`through`). So in `InstanceTree::creator` (`tree.rs`), the farthest holder is the creator unless its `through` instance holds the handler too, which means it was handed the handler and the node above has since been replaced; and a bound handler that no ancestor holds was bound by an instance that is gone. Both fail with `nx-ir-handler-token`, from `dispatch` and from `route`, and the dispatch being atomic nothing changes. `route` now returns `Result<Option<..>>`: `None` is only "the component does not emit it" or "nothing bound a handler". Tests: `an_event_from_a_drawing_a_dispatch_replaced_is_refused` (the third reproduction, and that the `Box`'s own handler still runs and a pass restores the route) and `an_emit_whose_handler_belongs_to_a_replaced_render_is_refused` (the first two reproductions, each followed by a pass and a successful dispatch). The spec states the rule in both requirements with scenarios of those names, and the README's list has *Draw after every dispatch*.
- **Verification:** (2026-10-07 12:07) Verified. The three reproductions now fail with `nx-ir-handler-token` and change nothing, and each succeeds after a pass. I looked for a current drawing the rule refuses and found none: a handler handed down two levels of content still runs against its creator after the node between was dispatched against (its new instance holds the same handler); an emit bound by a grandparent, for a child drawn inside a node between, still routes after that node was dispatched against; a node's own handlers run however stale the nodes above it are; chains three deep run repeatedly with a pass between. I looked for a stale case it lets through and found none: with the page replaced, the handed-down handler is refused through either level, and through the inner level in a pass that has reached the box and not the inner node; with two siblings, an emit from either is refused after the other's emit replaced the parent, and a child that had patched itself before its emit was refused is as it was. The rule is exact because a node holds a handler it did not create only if the instance it was initialized through holds it, and `through` is replaced only when the node is initialized again.

### ✅ Verified - RF8 Reporting a failure deep in a value formats its path by a recursion as deep as the value, which the stack budget does not bound
- **Severity:** Medium
- **Evidence:** A diagnostic names where a value sits with `Path`, whose `Display` writes `"{parent}.{name}"` or `"{parent}[{index}]"` (`crates/nx-ir-runtime/src/normalize.rs:22-29`): one `write!` inside another for each segment, and each record level wraps the path above it as `Path::Root(&dyn Display)` (`normalize.rs:428`, `477`). The message is built where the failure is found, which for a value that fails at its deepest level is the deepest frame of the checked walk, so the formatter recurses about two frames for each level from the point where the budget check last passed. That is more than the margin for a deep value. Reproduced in a native release build with the RF2 probe's thread (`budget + margin + 8 KiB` of stack, `max_stack_bytes = budget`): `type Box = { inner?:Box n?:int }`, `let held(box:Box): int = { 1 }`, called with a host record nested 200 deep whose innermost `n` is a string. With a 32 KiB margin, every budget tried from 420,000 to 448,000 bytes (steps of 4,000) aborts with `thread has overflowed its stack`; below that range the call returns the `maxStackBytes` diagnostic and above it the `nx-ir-boundary-type` diagnostic, whose message is 1,833 bytes. The same value with a valid innermost field returns `1` from 420,000 up and never aborts. At 100 levels: an abort at 210,000 with a 32 KiB margin, and from 210,000 to 226,000 with 16 KiB. A 64 KiB margin did not abort at 200 levels. In a scratch copy with the two `write!` arms changed not to print the parent, none of these sweeps aborts, so the formatter is what leaves the stack. `resolve_parent_handlers` builds its messages from the same `Path` (`component.rs:245-258`). The requirement says the budget bounds "every recursion the runtime makes over an image or a value on behalf of that call" and that no host value exhausts the stack of a thread with the budget free; the README says the margin covers what the runtime uses "to report that it met" the budget (`README.md:359-362`), which holds for the budget's own diagnostic and not for a type failure found at depth.
- **Recommendation:** Print a path without a recursion that grows with it. Add a test shaped like `a_comparison_far_down_a_recursion_stays_within_a_small_stack`: a deep value that is wrong at its innermost level, budgets swept across the point where the walk first fits.
- **Fix:** A path is now one chain from its root and is printed in a loop (`crates/nx-ir-runtime/src/normalize.rs`). `Path`'s `Display` follows the parent links, collecting the segments, writes the root and then the segments in order, so the stack it takes does not grow with the path; and `normalize_fields` and `normalize_patch_fields` take a `&Path` and extend it with `Path::Field(path, ..)` where they wrapped it as `Path::Root(&dyn Display)`, so no level of a value hides the path above it. The callers that start a path (`component.rs`, `eval.rs`) pass `Path::Root(..)` of the label they passed before; the text of every diagnostic is unchanged. `resolve_parent_handlers` already linked its path and now prints it the same way. Tests: `a_path_prints_its_root_and_then_its_segments_in_order` in `normalize.rs`, and the reproduction as `a_failure_at_the_bottom_of_a_deep_value_is_reported_within_a_small_stack` in `ir_runtime_tests.rs`: the 200-level `Box` with a wrong innermost field, budgets swept in 2 KiB steps from 16 KiB until sixteen in a row report `nx-ir-boundary-type` with the whole path, each on a thread of the budget, the margin and 8 KiB. In a release build that test aborts with a stack overflow when the recursive formatter is put back (checked) and passes with the loop. The spec's stack paragraph says reporting a failure does not take stack in proportion to the value's depth, with the scenario `A failure at the bottom of a deep value is reported within the stack budget`; the design and the README's sentence about the margin say the same.
- **Verification:** (2026-10-07 12:19) Verified. `Path`'s `Display` follows the parent links in a loop (`normalize.rs:28-53`), and `normalize_fields` and `normalize_patch_fields` extend the path they are given (`normalize.rs:454`, `519`). Every remaining `Path::Root` starts a path at a label (`Labeled`, `Labeled3`, `Position`, `Quoted`, a name), none wraps a path at depth, and no other `Display` in the crate recurses. The probe that aborted no longer does: 200 levels at 32, 16 and 8 KiB margins across 380,000 to 480,000 bytes, and 100 levels at 32 and 16 KiB across 150,000 to 260,000, each return the `maxStackBytes` diagnostic and then the `nx-ir-boundary-type` diagnostic, whose message is the same 1,833 (933) bytes as before. I then looked for another walk or failure path that leaves a thread of the budget, a margin and 8 KiB in a release build, sweeping the budget in 1 KiB steps from 1 KiB to past the point where each call first fits, with values 240 to 250 levels deep (110 to 120 where a level is a record and a list), valid and wrong at the innermost level. ### ✅ Verified - RF9 A node the pass visited before its parent rendered again still counts as visited when the pass ends, so `finish` keeps a node whose place is gone and calls its parent settled
- **Severity:** Medium
- **Evidence:** `finish` decides a node's fate from `self.visited.contains_key(key)` (`crates/nx-ir-runtime/src/tree.rs:158-162`) and clears the parent's `unwalked` when the parent's last visit saw its current instance (`tree.rs:170-176`, `193-198`). The visit record of a child says nothing about which instance of the parent the child was read from. So when a node is dispatched against during a pass and the host visits it again in that pass, every child visited earlier in the pass, through the earlier instance, is taken for a place the new output has. The design guards the other half of this (`design.md`: "A visit records the instance it saw, so a node dispatched against between its visit and the end of the pass is not taken for walked"), and `a_node_dispatched_against_after_its_visit_is_not_taken_for_walked` tests it; this half is open. Two reproductions:

### Answers From The Fix Pass
- **`rust-version`:** not changed. It is the open question the design leaves for the maintainer; the three crates still declare 1.98.1.
- **Components of library modules:** the tree instantiates what the lifecycle can initialize, which is a component entrypoint of the entry module with a body (`Program::initialize_component` looks nowhere else). ### Answers From The Second Fix Pass
- **A place that leaves and returns while one pass is under way:** intended. The parent rendered again after its last visit that walked output without the place, so the pass ends without having walked what the parent holds, drops nothing under it, and leaves it unsettled; the node is then visited through the current instance by the next pass and is initialized again with the state it held. A host that wants the node gone when its place was absent for a moment ends the pass in between, which is what the spec's rule describes: a pass drops what it walked new output without finding.
