## Findings

### ✅ Verified - RF1 Every change in the pane's width re-renders the whole reading up to five times, so dragging the fiddle's divider stutters, even while Source shows
- **Severity:** Medium
- **Evidence:** `packages/viewer/src/index.ts:186-197`: the `ResizeObserver` calls `#render()` whenever `#body.clientWidth` differs from `#fitWidth`. `#render` (`index.ts:404-453`) rebuilds the index and redraws the DOM once, then up to four more times (`index.ts:419`), forcing a layout each time in `#wrapped()`. Dragging `.fiddle-divider` changes the width on every frame. The fiddle hides the view not shown with `visibility: hidden` (`FiddlePage.razor`, `.fiddle-code.shows-source .fiddle-visual`), which keeps it laid out, so the hidden reading also re-renders on every frame while the visitor is in Source. Measured in headless Chromium (swiftshader) on the dev host, stepping `.fiddle-code`'s width 25px per frame: about 60 to 200 ms per step with the viewer (`nx-layouts`, `nx-shapes`, `nx-text`), against 11 to 22 ms on the same page with the `<nx-viewer>` removed. Real hardware is faster, but the gap is about 8x, and it hits the playground's split pane too.
- **Recommendation:** Repaint the highlights on each resize as before, but re-measure only once the width settles (for example a trailing 100 to 150 ms timer, or at most once per animation frame with the last width), keeping the `keyAtTop`/`scrollToKey` anchoring. Skip re-measuring while the element is not visible (`checkVisibility({ visibilityProperty: true })` is false) and re-measure when it next shows; the fiddle's `show` path can trigger that. Add a viewer test that fakes several resizes in a row and asserts a single re-layout.
- **Fix:** `packages/viewer/src/index.ts`: the `ResizeObserver` repaints the highlights on every change but re-measures a reading already measured only once the width has held for 120 ms (a trailing timer); a reading first given a width (hidden or unattached until then) is measured at once. The anchored re-render is one `#remeasure()` (also RF5). The hidden reading keeps measuring (answering the question below): debounced, a divider drag costs one measure, and the fiddle's switch reads `keyAtTop`/`topOf` from it. New viewer test "measures the reading again once the pane's width settles, not on each step" (fake `ResizeObserver`, mock timers). Spec, README and design decision 9 say "once a change in the pane's width settles". Viewer 49 pass, playground 118, fiddle 110, Visual check and Rust browser check pass.
- **Verification:** Verified. `index.ts:187-202` repaints on every change and calls `#remeasure()` at once only for a reading not yet measured (`#fitWidth <= 0`). Otherwise it uses a 120 ms trailing timer, which skips the measure when the width came back to where it was. A new tree's `#render` resets `#fitWidth`, so a pending timer then does nothing. The new test drives a fake `ResizeObserver` with mock timers and checks no redraw during three steps, one after 150 ms, and none after. Spec, README and design decision 9 match. Re-measured in headless Chromium on the dev host with the rebuilt runtime, same 25 px steps: 18 to 76 ms per step (`nx-shapes`) and 18 to 44 ms (`nx-layouts`), settling near the 11 to 22 ms baseline, against 60 to 200 ms before.

That is a new dependency in the fiddle's `package.json` for its maintainer, so it is the user's call. Once decided: add `nx/test/visual.test.ts` as recommended, with jsdom installed as the viewer's `test/dom.ts` does, or instead run `nx/visual-check.mjs` in CI against a started dev host.
- **Fix:** At the user's direction, jsdom (`^26.1.0`, with `@types/jsdom`) is a fiddle dev dependency, loaded unbundled by `nx/test/run.mjs` as `typescript` is, and installed as globals by the new `nx/test/dom.ts`. The new `nx/test/visual.test.ts` drives `createVisualView` with a fake editor, a source-tree query the test answers with the real tree or fails, and a fake layout of the reading. It has 8 tests: asking on show and not while hidden; stale then one question after the pause; a superseded question aborted and its late answer dropped; failure message then recovery; `reset` dropping folds and selection and scrolling to the top; the selection and place carried into the reading; into the editor; and a round trip that moves nothing. The last found that `hide`, skipping `leave` for an unmoved reading, forgot the editor's place, so the next switch placed the reading again (to the same spot): `hide` now records `placedEditor` in that case (`nx/src/visual.ts`). AGENTS.md mentions the test. Task 9.7. `npm run test:nx -- --nx ../nx` 118 pass; Visual browser check all passed.
- **Verification:** Verified. `nx/test/visual.test.ts` drives the real `createVisualView` with real source trees, through the view's own wiring (show, hide, reset, `nx-select`). ### ✅ Verified - RF11 The outermost-only filter also holds back the items of a group whose header does not fit, so items nested more than six groups deep keep headers that do not fit
- **Severity:** Medium
- **Evidence:** `packages/viewer/src/index.ts:593` drops any found element that a found `outer` contains (`outer.contains(element)`). For a group, `outer` is the whole `.sheet`, but what was measured is only its header (`index.ts:573`). The items under it, in `.sheet-held`, sit in the same place whether the header wraps or not, yet each one waits a pass, and its items wait another. At HEAD, `#wrapped()` returned every element found in one pass. Repro with the `narrow` fake at 30 columns and ten nested `<Box name=… label=…>` groups (`type Box = { name:string label:string content items:Box* }`): levels 0 to 5 get rows, and levels 6 to 9 keep headers such as `Box name=level6 label=label number 6` as `fit-check` units that take two lines. UI trees nest that deep often (a page, a grid, a stack, a border, a stack, a button). Each level also costs one more full `renderSource` and layout, which adds to the resize cost RF1 dealt with.
- **Recommendation:** Hold back an element only when it sits inside what its outer element measured: its line, or its group's `:scope > .sheet-head`. For example, `found.some((outer) => outer !== element && targetOf(outer).contains(element))`. Then only values on a line or on a header wait a pass, and items are measured with their holder. Add a test that nests item groups deeper than six levels.
- **Fix:** `#wrapped()` records what it measured for each element (its line, or its group's header) and holds an element back only when it sits inside the measured line or header of one that does not fit; what a group holds under its header is measured in the same pass. New `deepGroups` test (8 nested groups at 30 columns, every header `Box`) fails with the old whole-element rule.
- **Verification:** Verified. `#wrapped()` (`packages/viewer/src/index.ts:572-597`) keeps each found element's measured target and holds back only what sits inside an outer target. In Chromium at 45ch, the ten-level `Box` nesting from the review now gives every level from 1 down rows in one render, and no `fit-check` that doesn't fit is left. `deepGroups` covers it in the suite.

### ✅ Verified - RF12 An element that shows one property, an element value, becomes a group, and its value gets rows it does not need, measured in a line that then changes shape
- **Severity:** Medium
- **Evidence:** `markFit` needs two shown properties (`source.ts:546`), so a holder such as `<Holder appearance=<Style alpha=1 beta=2 gamma=3 /> />` is never measured, and nothing holds back its value `V`. `V` is measured in the holder's line, where it spans the line break (`index.ts:584-588`), so `V` is marked wrapped. A wrapped `V` is no longer a line (`source.ts:574`, `:603`), so the holder is no longer `lineable` and reads as a group. In Chromium at 40ch (narrow layout, values under their names), the reading is `Holder`, a row `appearance`, and under it a group `Style` with rows `alpha`, `beta` and `gamma`. Yet `<Style alpha=1 beta=2 gamma=3/>` (31ch) fits under its name, which the outermost rule exists to measure. Before the fix, this read as one wrapped line. The spec's line requirement (`specs/viewer/spec.md:130-132`) still says an element that shows one property at most reads as a line, "which a row would not shorten". The `valueGroups` test covers only a holder with three properties.
- **Recommendation:** Measure a holder whose only shown property is an element value, as `markFit` does a folded group (least 1 when that one value is an element). The holder then turns into a group first, and its value is measured on its row the next pass. Reword the line requirement: a row does shorten such an element, since its value moves under its name. Add a scenario and a test. Or, if a one-property holder should stay a line, leave its element value unmeasured there and say so in the spec.
- **Fix:** `markFit` measures a property's element value only when its holder reads as a group (`holderOf` + `shapeOf(holder) === "group"`): on a line the value wraps with the line, so a holder showing one property stays a line, as the spec says. Covered by the `valueHolders` test (`Holder` stays a line), which fails without the check.
- **Verification:** Verified. `markFit` skips a value whose holder (`holderOf`, `source.ts:530-535`) doesn't read as a group (`source.ts:556-559`). In Chromium at 40ch, `<Holder appearance=<Style alpha=1 beta=2 gamma=3 /> />` now reads as one line, as the spec's line requirement says.
