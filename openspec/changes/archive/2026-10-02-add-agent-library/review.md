## Findings

### ✅ Verified - RF1 A relative import path that normalizes into `@nx/` silently resolves to the standard library, and the language service then disagrees with the compiler
- **Severity:** Medium
- **Evidence:** `standard_import` only recognizes a path whose *written* text starts with `@nx` (`crates/nx-api/src/artifacts.rs:1336`). Any other path goes through `normalize_workspace_import_identity` (`workspace_import_target_identity`, `artifacts.rs:1343`), and the normalized identity is then looked up through `visible_library_by_logical_identity`, which now answers `@nx/agent` from the standard table first (`artifacts.rs:710`). So `import "./@nx/agent"` in `main.nx` (or `"../@nx/agent"` from `app/x.nx`, or `"../../@nx/agent"` from an in-memory library module, through `normalize_logical_library_path` and `visible_library`) binds the standard library. Verified: `nxlang run` on `import "./@nx/agent"` + `<Agent name="support">Hi.</Agent>` prints the Agent with no diagnostic, while `import "./@nx/prelude.nx"` fails with a missing-module error. The language service only indexes a standard library whose import path text equals the root (`crates/nx-language-service/src/lib.rs:1117`), so for the same document the Node SDK snapshot reports no diagnostics but `hover` on `Agent` returns `null`. This contradicts `module-imports` ("Such a path SHALL NOT be resolved relative to the importing module") and the reserved-root requirement, gives the library a second, undocumented spelling, and turns the documented breaking case (a real `@nx` directory beside a module) into a silent rebinding instead of an error.
- **Recommendation:** After normalizing a relative workspace or logical library path, refuse a result that lies under `@nx/` (a diagnostic saying the root is reserved and that a standard library is imported as `@nx/<name>`), in the workspace, logical-library and directory-library pipelines. Add tests for `./@nx/agent` from `main.nx`, `../@nx/agent` from a nested module and from an in-memory library module.
- **Fix:** `standard_import_diagnostics` (`crates/nx-api/src/artifacts.rs`) now also resolves each relative path the way its pipeline does (workspace identity, or logical library root for an in-memory library module) and reports one landing under `@nx/` as `import-path-reserved`, labelled at the import. `apply_graph_imports` and `apply_build_context_imports` skip such an import (marked incomplete), and `library_import_root` no longer records it as a dependency, so it binds nothing in any pipeline; a directory library resolves to absolute directories, which never match a standard root. Because the import now fails in the compiler, the language service reports the same diagnostic rather than disagreeing. Test: `a_relative_path_into_the_reserved_root_is_refused_not_resolved` (`./@nx/agent` from `main.nx`, `../@nx/agent` and `../@nx/prelude.nx` from `app/main.nx`, `../../@nx/agent` from an in-memory library module, and the program links nothing under `@nx/` but the prelude). Spec `module-imports` gains the requirement sentence and a scenario.
- **Verification:** Confirmed in code: `standard_import_diagnostics` resolves each non-`@nx` path the way its pipeline does (`normalize_workspace_import_identity` for workspace modules, `normalize_logical_library_path` for in-memory library modules) and reports `import-path-reserved` at the import. `apply_graph_imports` and `apply_build_context_imports` skip the import, and `library_import_root` leaves it out of the dependency roots. Re-ran my probes: `nxlang run` on `import "./@nx/agent"` and on `import "./@nx/prelude.nx"` now both fail with `import-path-reserved` at 1:1, and the Node language snapshot reports the same single diagnostic for `./@nx/agent`, so the compiler and the editor agree. `a_relative_path_into_the_reserved_root_is_refused_not_resolved` passes and covers the workspace, nested and in-memory cases. The spec delta's requirement sentence and scenario were added, and `openspec validate --strict` passes. Nit, no reopen: `resolves_into_reserved_root` (`artifacts.rs:1411`) is a one-line alias of `is_reserved_identity`, and `library_import_root` calls the latter directly. Calling one of them everywhere would be simpler.

### ✅ Verified - RF2 The `ToolContext` scenarios and several `agent-library` evaluation scenarios have no test
- **Severity:** Low
- **Evidence:** Nothing in the change calls a function with a `ToolContext` argument: no test contains `callId`, `whoAmI` or a parameter typed `ToolContext` (`grep` over `crates`, `bindings`, `runtime/typescript/test`). The two `ToolContext` scenarios ("calling `whoAmI` through an IR runtime with a `ChatToolContext`" and "a base-typed parameter accepts the host's subtype") are therefore unverified on both runtimes; `a_host_library_extends_the_agent_types_and_a_program_uses_them` only type-checks a function that takes `ChatToolContext`. A manual probe against the TypeScript runtime returns the expected values, so this is a coverage gap, not a known bug. Likewise "A function tool holds a reference to any function" (two `FunctionTool`s over functions with different parameters and results) and the evaluated `model` of "Any model string is accepted" are only type-checked (`standard_library_tests.rs:700-740`). Task 4.1 also says the version is verified equal across the native, wasm and Node builds, but the wasm and Node tests only match `/^[0-9a-f]{16}$/` rather than the pinned `b06c00c30be50ada`.
- **Recommendation:** Extend the TypeScript and Rust IR runtime agent tests (or the corpus program) with a `ChatToolContext` declared in a second module and two functions, one taking `ChatToolContext` and one taking `ToolContext`, called through `callFunction`/`call_function`; add a second `FunctionTool` with a different signature and assert the `model` field. Assert the pinned version in the wasm test.
- **Fix:** New corpus program `specs/ir-conformance/agent-tool-context`: `ChatToolContext extends ToolContext` in a second module, three `FunctionTool`s over `whoAmI(context: ChatToolContext)`, `callIdOf(context: ToolContext)` and `seatCount(teamSize: int, cap?: int)`, and `model="any-model-name-at-all"`. Both runtimes call all three with a `ChatToolContext` record (base-typed parameter included) and assert the evaluated `model`: `a_tool_function_takes_the_host_context_by_its_subtype_or_its_base` in `crates/nx-ir-runtime/tests/prepare_link.rs` and the same-named test in `runtime/typescript/test/runtime.test.ts`. The interpreter's recorded `results.json` covers `root`. `the_agent_library_image_is_the_same_from_either_corpus_program` checks the two programs emit identical library images. The wasm and Node tests now assert the pinned `b06c00c30be50ada`.
- **Verification:** The corpus program `agent-tool-context` declares `ChatToolContext` in `context.nx`, a module other than the abstract base, and has three tools of different signatures and `model="any-model-name-at-all"`. The Rust test (`prepare_link.rs:702`) and the TypeScript test (`runtime.test.ts:2332`) both call `whoAmI` with the subtype, `callIdOf` through the base-typed parameter and `seatCount` with its optional parameter omitted, and both assert `model`. Both pass. `the_agent_library_image_is_the_same_from_either_corpus_program` passes. The wasm (`standard-libraries.test.ts:90`) and Node (`sdk-node.test.ts:689`) tests now assert `b06c00c30be50ada`, and both pass.

### ✅ Verified - RF3 `nxlang typegen @nx/agent --language csharp` ignores the library's fixed namespace unless the caller repeats it
- **Severity:** Low
- **Evidence:** The static table fixes `NxLang.Agent` as the namespace every host library's generated C# qualifies agent types with (`csharp.rs` `assumed_dependency_namespace_for_library`), but generating the library itself still uses the `--csharp-namespace` default `Nx.Generated` (`crates/nx-cli/src/main.rs:91`, `generate_types` passes `csharp_namespace` unchanged for a standard library). Running `typegen @nx/agent --language csharp` without the flag produces contracts that the host library's generated `global::NxLang.Agent.Tool` references cannot bind to. The design (D10) says a C# host "generates the contracts itself with `--csharp-namespace NxLang.Agent`", so this is easy to get wrong.
- **Recommendation:** For a standard library input, default the C# namespace to the table's `csharp_namespace` when `--csharp-namespace` was not given explicitly (or reject a different namespace with an error naming `NxLang.Agent`), and add a CLI test without the flag.
- **Fix:** `--csharp-namespace` is now optional (`crates/nx-cli/src/main.rs`); when omitted, a standard library input uses the table's `csharp_namespace` (`NxLang.Agent`) and anything else uses `typegen::DEFAULT_CSHARP_NAMESPACE` (`Nx.Generated`, unchanged). Help text says so. Test: `test_cli_typegen_standard_library_csharp_defaults_to_its_fixed_namespace`. Design D10 updated.
- **Verification:** `--csharp-namespace` is now `Option<String>`. `generate_types` picks the explicit flag, else the standard library's `csharp_namespace`, else `DEFAULT_CSHARP_NAMESPACE` (`main.rs:359-365`), so non-standard inputs keep `Nx.Generated`. The help text explains the default. `test_cli_typegen_standard_library_csharp_defaults_to_its_fixed_namespace` passes, and so does the existing explicit-flag test.

(b) `nx_api::unknown_standard_library_message` is the one wording, used by the `unknown-standard-library` diagnostic and by the CLI's `standard_library_input`. (c) New `nx_hir::Fnv1a64` (`crates/nx-hir/src/fnv.rs`, with the published FNV-1a test vectors) is used by both `module_fingerprint` and `StandardLibrary::version`; the pinned corpus images and version are unchanged, confirming the same hash.
- **Verification:** (a) `STANDARD_LIBRARY_ROOTS` no longer appears anywhere in `crates/`. (b) The CLI's `standard_library_input` returns `nx_api::unknown_standard_library_message`, the same function the `unknown-standard-library` diagnostic uses. (c) `nx_hir::Fnv1a64` is used by `StandardLibrary::version` (`artifacts.rs:1219`) and `module_fingerprint` (`ir.rs:319`), and its unit test checks the published vectors. The pinned version and corpus images are unchanged and their tests pass. The remaining copy in `crates/nx-ir-runtime/src/module.rs:1332` was there before this change, in a runtime crate that does not depend on the compiler crates, so it is out of scope.

### ✅ Verified - RF6 The reference-page test fails on a Windows checkout that converts line endings
- **Severity:** Low
- **Evidence:** `the_reference_page_quotes_the_library_and_the_worked_example_exactly` (`crates/nx-api/src/standard_library_tests.rs:876`) compares a block of `agent.md`, read with `include_str!` (`standard_library_tests.rs:860`), byte for byte with `agent.nx` and the corpus `main.nx`. `.gitattributes` pins `*.nx` to `eol=lf` but leaves `.md` under `* text=auto` (`git check-attr eol` reports `unspecified` for the page). On a Windows checkout with `core.autocrlf=true`, which matches AGENTS.md's "CRLF on Windows", the page is checked out with CRLF while the `.nx` files stay LF, so `cargo test` fails there. CI runs `cargo test` only on Ubuntu (`.github/workflows/build.yml:239`), so CI won't catch this.
- **Recommendation:** Strip `\r` from the page block before comparing (in `reference_block`). Alternatively, pin `sites/website/src/content/docs/reference/libraries/agent.md` (or `*.md`) to `eol=lf` in `.gitattributes`.
- **Fix:** `reference_block` (`crates/nx-api/src/standard_library_tests.rs`) now normalizes the page's CRLF to LF before extracting a block, and returns an owned `String`; its doc comment says why. The comparison then holds whatever line endings the Markdown checks out with, while the `.nx` sides stay pinned to LF. Also took the RF1 nit: the one-line alias `resolves_into_reserved_root` is removed and both call sites use `is_reserved_identity`.
- **Verification:** `reference_block` (`standard_library_tests.rs:868`) replaces `\r\n` with `\n` across the page before it extracts a block. The `.nx` sides stay LF because `.gitattributes` pins them, so the comparison no longer depends on how the Markdown file is checked out. `the_reference_page_quotes_the_library_and_the_worked_example_exactly` passes. The `resolves_into_reserved_root` alias is gone and both former call sites (`artifacts.rs:2470`, `artifacts.rs:3095`) call `is_reserved_identity` directly. Behavior is unchanged: `a_relative_path_into_the_reserved_root_is_refused_not_resolved` passes, the `nxlang run` probe on `import "./@nx/agent"` still reports `import-path-reserved`, and `cargo test --workspace` passes.

## Questions
- Single-file `nxlang typegen main.nx --language typescript` on a file that imports `@nx/agent` emits `agent?: Agent` with no `import type` and no warning. That is pre-existing for any library import in single-file mode, so it is not listed as a finding. Should single-file output use the fixed `@nx-lang/agent` target too, since a standard library has no directory to guess from?
  - **Response:** Not changed here. Single-file typegen emits no cross-library imports for any library today, so fixing it for standard libraries alone would be a partial rule; it belongs with a change that gives single-file output library imports generally.

## Summary
- The mechanism is small and fits the existing pipelines: a standard library is an ordinary `LibraryArtifact` answered by the registry and build-context lookups, its version flows through the library version into `module_version` with no codegen special case, and IR output for programs that import no standard library is unchanged. The agent source matches the design, and the Rust, TypeScript, wasm, Node, .NET, CLI, LSP, docs and playground coverage is broad and passes.
- One correctness gap: a relative path that normalizes under `@nx/` resolves to the standard library, against the reserved-root rule, and the editor then disagrees with the compiler (RF1). The rest are low-severity coverage, CLI-default, docs-drift and duplication items.
