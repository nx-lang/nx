- **Verification:** `crates/nx-ir-runtime/tests/damage.rs` asserts that the programs above the limit are exactly `LEFT_OUT_OF_THE_SWEEP` (`["large-catalog", "question-flow"]`), so a program that crosses 16,384 bytes fails the test. `cargo test -p nx-ir-runtime --test damage -- --nocapture` passes with the same counts as before (21 swept, 89,725 opened, 126,927 refused) and prints the two left out; `cargo fmt --all --check` and `cargo clippy -p nx-ir-runtime --all-targets -- -D warnings` are clean. ### ✅ Verified - RF4 One side failing to load or run a step aborts the whole comparison instead of marking the step not comparable
- **Severity:** Low

The spec delta, the design (D7) and the README name the new reason and the two exit codes. `--base 7b0baa6` now runs and compares the tool calls.
- **Verification:** Most of the fix holds. `corpus.mjs` reads `operations.json` only when it exists, and `--base 7b0baa6` now runs and compares the tool calls. A bad `--samples`, an unknown revision and a directory with no build exit with 2. What is still wrong: the fix note, the header of `compare.mjs` ("with 2 when it could not compare at all: an option it cannot read") and the README say an unreadable option exits with 2, but `parseArgs` at `compare.mjs:43-54` is outside the `try`, so `node bench/compare.mjs --bogus` and `node bench/compare.mjs --base` (no value) exit with 1, the code that means a step is slower. Move the `parseArgs` call inside the handling that ends in `cannotCompare`. A lesser point: when the base fails first in round 0 the head is never timed (`whoAmI` showed no time where `seatCount` did), which the comment at `compare.mjs:173` says does not happen.
- **Fix (second pass):** `parseArgs` is now inside a `try` whose handler is `cannotCompare`, so `compare.mjs --bogus` and `compare.mjs --base` with no value print the parser's message and exit with 2. When the base fails first in a round the loop no longer stops there: the working tree is still timed once, as the comment says, and its times are in the row (checked with a build whose `callFunction` throws given as `--base-runtime`: the four tool-call rows show the working tree's times and `not comparable: it fails with the base's runtime`; given as `--head-runtime` they show none).
- **Verification (second pass):** `parseArgs` is inside a `try` that ends in `cannotCompare` (`compare.mjs:48-64`). `compare.mjs --bogus` prints "Unknown option '--bogus'", `--base` with no value "Option '--base <value>' argument missing", and a stray positional argument its message; each exits with 2, as `--samples abc` and an unknown revision still do. ## Questions
- Will the pull-request job fit the five minutes task 3.4 sets? A comparison with every variant comparable took 100 s here on a 12-core desktop CPU. The first pull request compares only the 10 `calls` variants (38 s here), so it will not show the time the job takes from the second pull request on.
- One `bench/run.mjs --samples 20` run reported `dispatch` at 77.7 µs warm; 24 further isolates gave 48.2 to 58.1 µs. `bench` reports one isolate's median for each call, where `bench:compare` has rounds. Is a single isolate enough for figures that are then written into `specs/future.md`, or should `bench` take the median of a few isolates?
- The job passes `--base "origin/$BASE_REF"`, the tip of the base branch, where D8 says the merge base. With `actions/checkout`'s default on `pull_request` (the merge commit) the two are the same commit; is that the intent, and should the workflow comment say so?

### Answers (from the fix pass)
- **Five minutes.** Not known until the job runs on a runner, which task 3.4 still has open; its note now carries the question. A fully comparable comparison is 30 variants at about 100 s on this machine, and `--samples` and `--rounds` are what to lower if a runner needs it.
- **One isolate.** No: `bench` now times each call in three isolates and reports the one whose median is in the middle (`--isolates`, design D5, the README). The comparison keeps one isolate a side in each round, since its rounds do the same work.
- **`--base origin/$BASE_REF`.** That is the intent, and the workflow now says why: on a pull request the checkout is the merge commit, so the tip of the base branch is the revision the checkout is based on.

## Summary
- The implementation matches the spec deltas and the design: the two programs meet the stated sizes and are held to their results in both runtimes, the core is import-free and its counts equal the corpus's, the harness is not packed, and a build compared with itself names nothing at the defaults. No correctness bug was found in the measuring or the comparing at their defaults.
- The finding that matters is RF1: pointed at the commit before `define-host-values`, the harness reports a cost several times the 5% that `specs/future.md` still states, and a two-fold cost on a small tool call that the document does not mention.
- RF2 is the one place existing blocking coverage can shrink without notice. RF3 to RF6 are robustness gaps in the drivers and the CI step, none of which affects a default run that succeeds. RF7 to RF10 are documentation and test-coverage drift.
- 10 findings: 2 Medium, 8 Low.
