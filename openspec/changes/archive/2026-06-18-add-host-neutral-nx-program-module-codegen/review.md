## Findings

### ✅ Verified - RF1 Runtime-helper and manifest identifiers are not reserved by the global name planner
- **Severity:** Low
- **Evidence:** In program-module mode the global name planner (`global_used_names`) is seeded empty and only ingests declaration/component names ([emit.rs:139-165](../../../crates/nx-codegen/src/emit.rs#L139-L165)). It never reserves the imported runtime helper names (`nxElement`, `nxField`, …) emitted at [emit.rs:543-550](../../../crates/nx-codegen/src/emit.rs#L543-L550), nor the fixed manifest export `nxProgramModuleManifest` emitted at [emit.rs:626](../../../crates/nx-codegen/src/emit.rs#L626). Because every declaration is flattened into one module and emitted with an `export` prefix, an NX program containing a top-level item whose `safe_identifier` is e.g. `nxElement` (and that also triggers the `nxElement` helper import) or `nxProgramModuleManifest` would emit a duplicate ESM binding. The result is JavaScript that fails to parse, and codegen returns success with no diagnostic. The single-module flattening introduces/amplifies this versus the per-file layout. No test covers an NX identifier that collides with a runtime helper or the manifest name.
- **Recommendation:** Pre-seed `global_used_names` with the manifest identifier and the runtime helper candidate names before planning declaration names in `EmitMode::JsProgramModule` (or alias the manifest/runtime imports through planned names). Add a test with a user declaration named `nxElement`/`nxProgramModuleManifest`.
- **Fix:** Program-module name planning now reserves the fixed manifest export and runtime helper identifiers before declaration/component name allocation, with regression coverage for `nxElement` and `nxProgramModuleManifest` source declarations.
- **Verification:** Confirmed. `reserve_js_program_module_names` ([emit.rs:344-349](../../../crates/nx-codegen/src/emit.rs#L344-L349)) seeds `global_used_names` with `JS_PROGRAM_MODULE_MANIFEST_EXPORT_NAME` plus the full `JS_PROGRAM_MODULE_RESERVED_RUNTIME_NAMES` list ([emit.rs:23-46](../../../crates/nx-codegen/src/emit.rs#L23-L46)), which mirrors the importable helper candidates in `collect_module_runtime_helpers`; it is invoked only for `EmitMode::JsProgramModule` ([emit.rs:189-191](../../../crates/nx-codegen/src/emit.rs#L189-L191)) so file output is unchanged. The new `js_program_module_reserves_runtime_helper_and_manifest_names` test ([tests.rs:1050-1091](../../../crates/nx-codegen/src/tests.rs#L1050-L1091)) proves a user `nxElement`/`nxProgramModuleManifest` declaration is renamed to `_2`, the canonical import/manifest names are preserved, and references resolve to the renamed identifier. `cargo test -p nx-codegen` passes (47 tests).

### ✅ Verified - RF2 Program module exports every flattened declaration, not just the curated public surface
- **Severity:** Low
- **Evidence:** `emit_declaration` always prefixes declarations with `export` ([emit.rs:739-879](../../../crates/nx-codegen/src/emit.rs#L739-L879)), and program-module emission emits every declaration of every module ([emit.rs:552-564](../../../crates/nx-codegen/src/emit.rs#L552-L564)). The cross-module test confirms internal library helpers become public exports (`export const bonus = 1;`, `export function add(a, b)`, `export function answer()` in [tests.rs](../../../crates/nx-codegen/src/tests.rs)) even though only `root` is an entrypoint. Design decision 5 / spec task 2.5 frame the public surface as "function entrypoints, concrete component descriptor functions, schema values, and state helper exports", but the implementation exports all flattened internals. Within a single module these declarations are referenced directly and do not need to be exported, so this leaks library internals into the cached module's public namespace. Functionally harmless (metadata still curates the intended entrypoints), but a divergence from the stated intent.
- **Recommendation:** Either limit `export` in program-module mode to the curated entrypoint/component/schema/state set (emitting internals as plain declarations), or document explicitly that the program module intentionally re-exports all flattened declarations and that callers must rely on the structured metadata for the public surface.
- **Fix:** Program-module emission now computes an explicit public export set from function entrypoint metadata, concrete component/schema metadata, state helpers, and the manifest; declarations outside that set are emitted as local bindings while file output continues to export its existing surface.
- **Verification:** Confirmed. A new `ExportPolicy` ([emit.rs:123-144](../../../crates/nx-codegen/src/emit.rs#L123-L144)) drives every `emit_declaration` call: file output passes `ExportPolicy::All` (preserving prior behavior, [emit.rs:580-590](../../../crates/nx-codegen/src/emit.rs#L580-L590)) while program-module output passes `ExportPolicy::Names(&collect_program_module_public_names(...))` ([emit.rs:618-634](../../../crates/nx-codegen/src/emit.rs#L618-L634)). The public name set ([emit.rs:751-771](../../../crates/nx-codegen/src/emit.rs#L751-L771)) is exactly the manifest + function-entrypoint export names + concrete-component descriptor/schema/initial-state/render names — i.e. it equals the structured metadata surface. The cross-module test now asserts non-entrypoint internals are local (`const bonus = 1;` / `const Theme = …` with no `export`) while entrypoints and components/schemas stay exported ([tests.rs:846-862](../../../crates/nx-codegen/src/tests.rs#L846-L862)), and execution-vs-interpreter parity still holds. CLI/.NET tests that assert `export function root()` and `export const nxProgramModuleManifest` still pass. `cargo test -p nx-codegen` (47) and `cargo test -p nx-cli` (123) pass.

### ✅ Verified - RF3 Determinism test reuses one artifact instead of two independently built equivalent artifacts
- **Severity:** Low
- **Evidence:** The spec scenario "Equivalent inputs produce equivalent program modules" calls for *two equivalent `ProgramArtifact` inputs*. `js_program_module_output_is_deterministic` builds a single `artifact` and calls `emit_js_program_module` on it twice ([tests.rs](../../../crates/nx-codegen/src/tests.rs)), which exercises emission determinism but not the artifact-build → global-name-planning path across two independently constructed artifacts (where module-id assignment order could in principle differ). Cross-module name stability (e.g. `value` vs `value_2`) depends on `program.modules` ordering, which this test does not re-derive.
- **Recommendation:** Add a determinism assertion that builds two separate artifacts from identical source/workspace inputs and compares the full `GeneratedJsProgramModule` (source + metadata), at least for the multi-module case.
- **Fix:** The program-module determinism test now builds two independent equivalent multi-module workspace artifacts and compares the complete `GeneratedJsProgramModule` values.
- **Verification:** Confirmed. `js_program_module_output_is_deterministic` ([tests.rs:1022-1048](../../../crates/nx-codegen/src/tests.rs#L1022-L1048)) builds `first_artifact` and `second_artifact` from the same two-module workspace files via separate `artifact_from_workspace` calls and asserts `assert_eq!(first, second)` over the full `GeneratedJsProgramModule` (source text + all metadata), exercising the build → global-name-planning → emission path across independent artifacts, including a cross-module component. Test passes.

## Questions
- Is exporting every flattened declaration (RF2) intended as the program-module contract, or should the public ESM surface be restricted to entrypoints/components/schemas/state helpers? The answer determines whether RF2 is a doc fix or a code change.
  - **Answer:** The implementation now follows the restricted public ESM surface described by the OpenSpec artifacts.

## Summary
The change is implemented coherently and matches the proposal/design and spec scenarios end-to-end: a single host-neutral ESM module with only the runtime import, structured metadata (fingerprint, runtime ABI, entrypoint/component exports), topological flattening with a global name planner, an explicit CLI `--format program-module` (JS-only, TS rejected), an FFI surface with the ABI bumped to 11 in both Rust and .NET, and managed `GenerateJSProgramModule` returning typed metadata. Test coverage is strong (unit, snapshot, cross-module execution vs interpreter parity, component-schema execution against a separately supplied runtime, host-neutrality, FFI, and .NET), and the targeted `cargo test -p nx-codegen` suite passes. Findings were all Low severity: an unreserved-identifier collision edge case (RF1), an over-broad public export surface that diverges from the stated public-API intent (RF2), and a determinism test that does not exercise two independently built artifacts (RF3). No High/Medium correctness or requirement-gap issues found.

**Verification (2026-06-17):** All three findings (RF1, RF2, RF3) are fixed and verified. The program module now reserves runtime-helper/manifest identifiers before name planning, restricts ESM exports to the curated metadata surface (manifest + function entrypoints + concrete components/schemas/state helpers), and the determinism test compares two independently built workspace artifacts. `cargo test -p nx-codegen` (47) and `cargo test -p nx-cli` (123) pass. No findings reopened; no new findings.
