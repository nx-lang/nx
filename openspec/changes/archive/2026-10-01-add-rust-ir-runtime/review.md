# Review: add-rust-ir-runtime

## Scope
**Reviewed artifacts:** `proposal.md`, `design.md`, `tasks.md`, `specs/rust-ir-runtime/spec.md`  
**Reviewed code:** `crates/nx-ir-runtime/src/` (`eval.rs`, `normalize.rs`, `component.rs`, `module.rs`, `program.rs`, `value.rs`, `helpers.rs`, `update.rs`, `text.rs`, `error.rs`, `lib.rs`), `crates/nx-ir-runtime/tests/` (`corpus.rs`, `damage.rs`, `prepare_link.rs`, `common/mod.rs`), `crates/nx-ir-runtime/README.md`, `crates/nx-ir/` (`lib.rs`, the diff of `image.rs` against the old `ir_image.rs`), `crates/nx-codegen/src/ir_runtime_tests.rs`, `ir_runtime_sources.rs`, the diff of `prelude_image_tests.rs` and `lib.rs`, the diffs of `docs/nx-ir-format.md`, `crates/README.md`, `specs/ir-conformance/README.md`; compared against `runtime/typescript/src/index.ts`.  
**How it was checked:** `cargo test -p nx-ir-runtime`, `cargo test -p nx-codegen --lib ir_runtime`, `cargo clippy -p nx-ir-runtime -p nx-ir --all-targets`, `cargo tree -p nx-ir-runtime`, `openspec validate add-rust-ir-runtime --strict` all pass. Findings marked "experiment" were confirmed with a throwaway crate outside the repository that compiles NX source with `nx-codegen`, runs the image on `nx-ir-runtime`, and, for the comparison runs, runs the same image and arguments on `runtime/typescript/dist/src/index.js`.

## Findings

### ✅ Verified - RF1 A dispatch batch can nest component state without bound and overflow the native stack
- **Severity:** High
- **Evidence:** `dispatch_component_actions` applies each patch to `working` (`component.rs:806-813`) and only checks value depth when the batch is over, in `fields_to_host` (`component.rs:885`, guard at `value.rs:322-325`). Nothing between bounds the depth: `normalize`/`normalize_nominal`/`normalize_fields` recurse per level with no depth check (`normalize.rs:111`, `216`, `404`), they are not under `eval`'s nesting counter or stack budget, and dropping a deep `Value` recurses too. Experiment: `type Link = { child?:Link }`, `component <Deep /> = { state { tree?:Link } <Button onTapped=<Update tree=<Link child={tree} /> /> /> }`, initialized and dispatched with a batch of 5,000 `h1-1` invocations, aborts with `thread 'main' has overflowed its stack` on the 8 MiB main thread, in debug and in release. The same component with `tree:object` and `type Wrap = { inner:object }` returns the 256-level diagnostic at 5,000 entries and aborts at 200,000. A batch of 300 returns `nx-ir-resource-limit` as intended. This breaks the spec's "no host value ... SHALL cause the runtime to panic or to exhaust the native stack" and the README's Limits section.
- **Recommendation:** Enforce `MAX_VALUE_DEPTH` on the working state after every patch (in `patch_state`, before or instead of relying on `to_host`), so a batch fails with `nx-ir-resource-limit` at the entry that crosses the bound and no value deeper than the bound is ever built or dropped. Add a test that dispatches a long batch against a self-nesting state on a 2 MiB thread.
- **Fix:** `patch_state` now checks the nesting of the state it returns (`check_depth` in `value.rs`, a handler's capture counting as a level), so a batch fails with `nx-ir-resource-limit` at the entry that crosses 256 and nothing deeper is built or dropped. Investigating this showed a second path to the same overflow: `normalize` recursed outside the stack budget, and its unoptimized frames are about 10 KB per level, so it now asks `Machine::within_stack` first. Test `a_batch_that_nests_state_past_the_limit_fails_at_the_entry_that_crosses_it` dispatches 300, 5,000 and 200,000 entries on a 2 MiB thread.
- **Verification:** Reran the experiment against the fixed code: the `Link` component with batches of 300, 5,000 and 200,000 entries, and the `object` variant with 200,000, each return `nx-ir-resource-limit` with no abort, in debug and release. `patch_state` calls `check_depth` on the state it returns (`component.rs:500`) and `normalize` asks `within_stack` first (`normalize.rs:118`). The new test runs on a 2 MiB thread and passes. One side effect is recorded as RF12.

### ✅ Verified - RF2 Integer arithmetic past 2^53 gives different values and diagnostics from the TypeScript runtime, which the spec forbids and the design misstates
- **Severity:** Medium
- **Evidence:** The spec requires the same canonical value and the same diagnostic code as the TypeScript runtime for every node kind (`spec.md:117-123`); `design.md:106-109` says wrapping `i64` arithmetic "matches both JavaScript backends". It does not past the safe range. Experiment, same image on both runtimes: `{ 3037000500 * 3037000500 }` is `-9223372036709301616` in Rust (wrapped, `eval.rs:1336-1338`) and `9223372037000250000` in TypeScript; `{ 9007199254740991 * 9007199254740991 }` is `-18014398509481983` against `8.112963841460666e+31`; `{ 9007199254740992 + 1 }`, `{ 9007199254740993 / 2 }` and `{ 9007199254740993 > 1 }` return values in Rust and fail with `nx-ir-number` in TypeScript, because a `bigint` constant is an `i64` in Rust (`module.rs:597-604`) and an `nx.int` record that arithmetic refuses in TypeScript (`index.ts:2716-2717`, `3875-3879`). `docs/nx-ir-format.md` records only that a wide integer is returned as `NxValue::Int`; neither the arithmetic difference nor the silent wrap is recorded, and no test pins either.
- **Recommendation:** Decide the intended behavior and write it down: either carve the exception into the `rust-ir-runtime` requirement and `docs/nx-ir-format.md` (wide integers compute as wrapping `i64`), or make arithmetic that leaves the safe range fail with `nx-ir-number` as the TypeScript runtime does for wide operands. Correct design decision 3 either way and add tests for the chosen behavior.
- **Fix:** Kept the behavior and wrote it down, since `primitive-type-names` makes wrapping 64-bit arithmetic the rule until checked arithmetic lands and matching JavaScript's precision loss would give up exact `int`. The `rust-ir-runtime` requirement now carves out integers outside the safe range, design decision 3 no longer claims agreement there, `docs/nx-ir-format.md` lists the difference, and `integers_past_the_float_safe_range_compute_as_wrapping_int64` pins the values from the review's experiment.
- **Verification:** Accepted as a documented decision. The requirement now states the exception (`spec.md:123-126`), design decision 3 no longer claims agreement outside the safe range, `docs/nx-ir-format.md:783-787` lists it, and `integers_past_the_float_safe_range_compute_as_wrapping_int64` pins the values, including the 64-bit wrap.

### ✅ Verified - RF3 Restoring an instance does not validate its props, state or handler properties, although the design says it checks everything and dispatch trusts it
- **Severity:** Medium
- **Evidence:** `restore_component_instance` walks `props` and `state` only looking for function and handler values (`component.rs:965-967`, `1021-1040`); nothing normalizes them against the component's fields, checks `handler_props` keys against the component's emits, or looks at `generation`. Experiment: a serialized `Counter` instance with `state` replaced by `[["count", {"Str": "oops"}], ["bogus", {"Bool": true}]]` and `generation` set to 41 is restored successfully; a later dispatch fails inside the body with `nx-ir-operator` rather than at restore, and a body that does not read the field would return the invalid state to the host. `design.md:159-167` says restore "checks everything" so that dispatch need not, and `normalize_component_state` would reject the same state with `nx-ir-boundary-field`.
- **Recommendation:** In restore, run `state` and `props` through `normalize_fields` (state with `require_explicit`), and require each `handler_props` entry to be `on<Emit>` of the component with a handler whose `component` and `emit` match, as `split_handler_properties` does. Extend `an_altered_instance_is_refused` with altered state, props and handler properties.
- **Fix:** Restore now normalizes `props` and `state` against the component's fields with nothing defaulted and passes `handler_props` through `split_handler_properties`, refusing any that is not a handler for an emit of the component. `an_altered_instance_is_refused` covers a wrong-typed state value, a missing and an undeclared state field, an undeclared prop, and a handler property the component declares no emit for. `generation` is not checked: every value is a consistent one, it only names the tokens.
- **Verification:** Reran the experiment in the new serialized form: a `count` pointing at a string entry is refused with `nx-ir-boundary-type`, an added `bogus` state field with `nx-ir-boundary-field`. Restore normalizes props and state with nothing defaulted and passes handler properties through `split_handler_properties`. A legitimately produced instance with an omitted optional state field, a `float32`/`int32` record, a union case, a constant case and an update record in state restores, dispatches and restores again. Leaving `generation` unchecked is fine.

### ✅ Verified - RF4 An instance is tied to source fingerprints, not to the images, so renumbered handler nodes are accepted and a token can run another handler
- **Severity:** Medium
- **Evidence:** `belongs` compares `(identity, fingerprint)` pairs (`component.rs:540-553`), and the fingerprint is a hash of the module's identity and source text (`docs/nx-ir-format.md:342`), not of the image. Restore then accepts any handler node the named declaration reaches whose component, emit, action and owner match (`component.rs:1056-1082`). Experiment: for a component with two buttons whose handlers differ only in body (`count + 1`, `count - 1`), swapping the two `node` values in the serialized instance restores without error, and token `h1-1` then yields `count = -1` where the original yields `1`. So an instance stored by one compiler release and restored against images another release emitted from the same source, with any change in node or slot numbering, passes both checks and dispatches the wrong handler or reads the wrong captured slots. The spec promises acceptance only for "a program linked from the same images" (`spec.md:244-246`); nothing checks that.
- **Recommendation:** Record a hash of each module's image content (the sections evaluation reads, debug section excluded) in `ProgramData::fingerprints` and in the instance, computed once in `PreparedModule::prepare`, and compare that in `belongs`. Add a test that an image with the same module fingerprint and different nodes refuses the instance.
- **Fix:** `PreparedModule::prepare` hashes the image's bytes (FNV-1a) and the program and the instance record that hash in place of the source fingerprint (`ProgramData::images`). The whole image is hashed, debug section included, so the same source emitted with and without it are different programs; `an_instance_is_tied_to_the_images_and_not_only_to_the_source` uses exactly that pair. The node swap in the experiment is still accepted, and has to be: both are handlers of the component, and nothing short of authenticating the stored bytes tells a rewritten valid instance from an original. The README and design decision 5 now say the check is against mistakes and not an adversary.
- **Verification:** `belongs` now compares image hashes (`ProgramData::images`), and the new test refuses an instance across the debug and stripped images of one source. The node swap from the experiment is still accepted (`h1-1` yields `-1`); that is inherent without authentication, as the fix note says, and the README (`README.md:143-145`) and design decision 5 now say the check is against mistakes, not an adversary. Accepted. Hashing the whole image means a debug and a stripped build of the same source cannot share stored instances, which is the safe side.

### ✅ Verified - RF5 A serialized instance copies every handler's captured frame, so its size grows with handlers times captured data
- **Severity:** Medium
- **Evidence:** Each handler owns `captured: Vec<Option<Value>>` (`value.rs:86`, cloned from the frame at `eval.rs:1106`); in memory the frames share their `Arc`s, but `serde`'s `rc` feature (`Cargo.toml`) serializes each `Arc` by value and deserialization does not restore the sharing. Experiment with `component <Rows items:string+ /> = { state { n:int = 0 } for item in items { <Button label={item} onTapped=<Update n={n + 1} /> /> } }`: the JSON of the initialized instance is 4,458 bytes for 10 items, 196,248 for 100 and 18,162,948 for 1,000. A restored instance then holds 1,000 separate copies of the list, and restore walks all of them. A list UI is the first workload the proposal names.
- **Recommendation:** Serialize through an explicit form that writes shared values once (a table of frames or values referenced by index, deduplicated by `Arc` pointer) and rebuilds the sharing on restore. Add a test that bounds the serialized size of an instance with many rows.
- **Fix:** The serialized form is now a flat table (`src/stored.rs`): each value is written once, keyed by the allocation it shares or the scalar it is, and entries name earlier entries by index. A handler stores its module, declaration, node and capture only; the rest is rebuilt from the node. `a_stored_instance_writes_a_shared_value_once_and_nests_no_deeper_than_its_table` bounds 1,000 rows at under 200 times the size of 10. A restored instance holds the props list twice (the normalized props and the captured one) until its next dispatch, not once per handler.
- **Verification:** Reran the experiment: the `Rows` instance serializes to 1,244 bytes for 10 items, 11,356 for 100 and 117,858 for 1,000 (was 18 MB), linear in the rows. The table deduplicates by allocation and restore rebuilds the sharing. The new form introduced RF11.

### ✅ Verified - RF6 An instance the runtime produced cannot be restored with serde_json once its values nest about 40 levels
- **Severity:** Medium
- **Evidence:** `Value` derives `Serialize`/`Deserialize` (`value.rs:26-39`), so one level of value nesting costs about three levels of JSON (`{"Record": {"fields": [[name, value]]}}`), and `serde_json` refuses input nested more than 128 levels. The boundary admits values 256 levels deep (`value.rs:24`). Experiment: `initialize_component("Holder", { data: <object nested N deep> })` then `serde_json::to_string` and `restore_component_instance`, the pair the README shows: N = 25 restores, N = 40 fails with `nx-ir-component: ... recursion limit exceeded`. The spec says a restored instance SHALL be accepted with the same results as the original (`spec.md:244-246`). A host that lifts the deserializer's limit to get past this removes the only bound on the derived, recursive `Deserialize`, which runs before `Restorer`'s own depth check (`component.rs:952`, `1022`).
- **Recommendation:** Give the serialized form a nesting cost of one level per value level or better (the canonical JSON shape, or the flat table of RF5), and bound depth while deserializing rather than after. Test a round trip of an instance whose state nests to the boundary limit.
- **Fix:** The flat table of RF5 nests a fixed few levels whatever the values do, and the reader computes each entry's depth as it is read, without recursion, refusing past 1,024 (an instance can hold its ancestors' captures, so the bound is above the boundary's 256). The same test round-trips a value nested 250 levels through `serde_json` with its default recursion limit and compares a dispatch, and checks that a 2,000-level table is refused.
- **Verification:** Reran the experiment: instances whose prop nests 40 and 120 levels restore with `serde_json` at its default recursion limit. The form nests a fixed few levels, entries name only earlier entries (a forward or self reference is refused: "value N is named before it is written"), and depth is computed per entry without recursion.

### ✅ Verified - RF7 The host `null` is accepted at an `object` site and rewritten to the empty sequence, where the TypeScript runtime rejects or preserves it
- **Severity:** Low
- **Evidence:** `from_host` turns every `Null` into the empty sequence before any type is known (`value.rs:254`), and an `object` site returns its value untouched (`normalize.rs:165-169`, `594`). Experiment with `let o(x:object): object = { x }` on both runtimes: `o(null)` is `[]` in Rust and `nx-ir-boundary-type` in TypeScript (`index.ts:3531`); `o({"a":null,"b":[null,1]})` is `{"a":[],"b":[[],1]}` in Rust and `{"a":null,"b":[null,1]}` in TypeScript. The spec says `null` SHALL be rejected where the site does not admit zero (`spec.md:163-165`). Of the 179 calls in that comparison run (integer, float, `float32`, text, occurrence, record, union and update-record sites) the only other differences were the three `nx.int` wrapper inputs, which the spec has the Rust runtime accept.
- **Recommendation:** Keep `null` distinct until the value reaches a typed site (a `Value::Null`-like marker resolved in `normalize`), or reject it at an exactly-one `object` site, and add the two cases to `host_absence_decodes_by_the_declared_occurrence`.
- **Fix:** Kept the behavior and wrote it down rather than adding a second representation of nothing to the value type: the runtime reads `null` as the empty value before any type is known, and `object` takes any value. The requirement, design decision 3 and `docs/nx-ir-format.md` now state it, and `a_host_null_at_an_object_site_is_the_empty_list` pins both cases from the review.
- **Verification:** Accepted as a documented decision. The requirement now says an `object` site admits `null` as the empty list, the design and `docs/nx-ir-format.md:788` state it, and `a_host_null_at_an_object_site_is_the_empty_list` pins both cases.

### ✅ Verified - RF8 The damage test evaluates one 760-byte image and never a lifecycle, so it does not support the "damage tests are the proof" claim
- **Severity:** Low
- **Evidence:** `every_cell_of_an_image_can_be_overwritten_without_a_panic` picks the smallest image with a function entrypoint (`tests/damage.rs:31-47`), which is `trailing-element/input.nx` (760 bytes, one component construction; printed by the test with `--nocapture`), with four cell values, and calls only `evaluate_function`. No damaged image with a `for`, a match, an intrinsic, a handler or an update record is evaluated, and `initialize_component`, `dispatch_component_actions` and `restore_component_instance` are never run on one. Experiment: overwriting every cell of every corpus image (debug and stripped) with seven values and running every function entrypoint, every component initialization, each recorded batch entry, `evaluate_component` and a serialize/restore produced 113,211 prepared images and no panic, in well under a second per image in release. So the code holds; the test would not notice if it stopped holding.
- **Recommendation:** Run the overwrite loop over every corpus image and drive lifecycles as well as function entrypoints.
- **Fix:** The overwrite test now covers every cell of every corpus image, both variants, and runs each function entrypoint, `evaluate_component`, `initialize_component`, a serialize and restore before each batch, and each batch. It reports 53,851 damaged images opened and about a million operations, in 20 s unoptimized and 2.5 s optimized.
- **Verification:** `every_cell_of_every_corpus_image_can_be_overwritten_without_a_panic` now covers every cell of every corpus image in both variants and drives function entrypoints, `evaluate_component`, `initialize_component`, a serialize/restore and each batch. It passes in 17 s unoptimized.

### ✅ Verified - RF9 Some spec statements have no test
- **Severity:** Low
- **Evidence:** (a) "its canonical JSON wrapper `{ "$type": "nx.int", ... }` SHALL be accepted at an integer site" (`spec.md:165-167`): `nx.int` appears in the tests only inside `canonical_eq` (`tests/common/mod.rs:168-174`), which compares outputs; no test passes the wrapper as input. (b) Lifecycle `state` after dispatch is compared only for `Counter` in `ir_runtime_tests.rs`; `corpus.rs` compares `rendered` and `effects` because `results.json` records nothing else, and the differential test does not dispatch, so the spec's "compare ... with native interpreter evaluation ... for ... dispatch" rests on the two corpus programs with lifecycles (`handlers`, `two-module`). (c) "the build SHALL NOT compile the NX syntax, HIR, type-checking, interpreter or codegen crates" is checked by hand (`cargo tree`, task 2.1) and by nothing in CI; a dependency added to `nx-value` would go unnoticed.
- **Recommendation:** Add a test that passes the `nx.int` wrapper to an `int` parameter; assert `state` in the corpus lifecycles from the interpreter, or dispatch in the differential test; add a test or CI step that fails when `cargo tree -p nx-ir-runtime` lists a compiler crate.
- **Fix:** (a) the `nx.int` wrapper is passed to an `int` parameter, valid and malformed, in the wide-integer test. (b) The differential test now dispatches every handler of each initialized component on both engines and compares rendered output and effects, with a new source whose state shows in its output; discarding the patch in `dispatch_component_actions` made it fail, and the first attempt without that source did not, which is why the source was added. (c) `tests/dependencies.rs` reads the manifests of `nx-ir-runtime`, `nx-ir` and `nx-value` and fails on any workspace dependency beyond `nx-ir` and `nx-value`.
- **Verification:** (a) the wrapper is passed to an `int` parameter in the wide-integer test; (b) the differential test dispatches on both engines (`ir_runtime_tests.rs:1346-1352`); (c) `tests/dependencies.rs` fails on a workspace dependency beyond `nx-ir` and `nx-value`. It reads manifests rather than the resolved tree, which is enough for the crates named.

### ✅ Verified - RF10 Small duplications in the runtime and its tests
- **Severity:** Low
- **Evidence:** The identity of a program module by index is written five times (`eval.rs:463-467`, `eval.rs:1084-1089`, `component.rs:231-236`, `component.rs:1090-1096`, `program.rs:272-276`). A diagnostic with no declaration is built by three helpers (`error.rs:35`, `module.rs:970`, `program.rs:57`). The value-depth refusal is written three times (`value.rs:229`, `component.rs:160-165`, `component.rs:1022-1024`). Five one-off `Display` adapters do the work of `format_args!` (`Quoted` in `eval.rs:1158`, `Labeled` in `normalize.rs:33`, `Labeled2`, `Labeled3` and `Position` in `component.rs:524-538`, `998`). The numeric-aware comparison exists twice (`tests/common/mod.rs:167`, `ir_runtime_tests.rs:76`), and only the first knows the `nx.int` spelling.
- **Recommendation:** Add `ProgramData::identity(module)`, keep one diagnostic constructor and one depth check, replace the adapters with one generic adapter or `format_args!`, and share one comparison (for example by exposing it from `nx-value` behind a test-support feature).
- **Fix:** `ProgramData::identity` replaces the five lookups, `Diagnostic::new` the three constructors, and `too_deep` is the one depth refusal (the restore walk that had the third is gone). - **Verification:** `ProgramData::identity`, `Diagnostic::new` and the single `too_deep` are in place. Leaving the `Display` adapters and the two test comparers is an acceptable call for a Low finding.

## New Findings Discovered During 2026-10-01 12:25 Verification

### ✅ Verified - RF11 A serialized instance of a few kilobytes can name a value of exponential size, and restore accepts it
- **Severity:** Medium
- **Evidence:** The table form lets an entry name the same earlier entry more than once (`stored.rs:254-311`), and the only bound is depth (`MAX_STORED_DEPTH`, `stored.rs:25`). A table whose entry `i` is a record holding entry `i-1` twice is `n` entries long and stands for 2^n values. Restore does not notice where the value sits at an `object` site, since `normalize` returns it untouched; every later walk treats it as a tree: `fields_to_host` at the end of a dispatch, `check_depth` in `patch_state`, `to_host` of rendered output, `values_equal`. Experiment (release build) with `component <Deep /> = { state { tree:object = 0 } ... }`: a hand-written instance whose `state.tree` names such a chain restores in about 25 microseconds, and an empty-batch dispatch against it then takes 0.5 s at 20 entries (1,408 bytes of JSON), 2.1 s at 22, 15.6 s at 24 (1,644 bytes), and does not finish at 60. Before the fix the serialized form wrote each value in full, so the input's size bounded the work. A program can build the same sharing in memory (the first question below), but this needs no program beyond one `object` field and comes from stored bytes, which the restore path is there to check.
- **Recommendation:** Compute each entry's expanded size beside its depth while reading (one plus the sum of its children's, saturating) and refuse an instance whose props, state or captures exceed a fixed bound; an honest instance's expanded size is what `to_host` would walk anyway. Add a test with a doubling chain.
- **Fix:** The reader now tracks, beside each entry's depth, how many values it holds written out (a saturating sum over the entries it names, so a doubling chain cannot overflow the count) and refuses an entry past 2^24 (`MAX_STORED_SIZE` in `stored.rs`). The stored-instance test restores a 60-entry doubling chain placed in a prop and expects `nx-ir-component`. The README's limits table and design decision 5 list the bound.
- **Verification:** Reran the doubling chain in `object` state (release): chains of 24, 25, 60 and 900 entries are refused at restore in under half a millisecond with "a value holds more than 16777216 values"; the size is a saturating sum computed per entry beside the depth (`stored.rs:267-327`), and the stored-instance test covers a 60-entry chain. Legitimate instances are not caught at realistic sizes: the `Rows` instance with 100,000 items (13 MB of JSON, each handler entry about 100,000 values written out) restores in 118 ms and dispatches. What remains is the bound itself: a 23-entry chain (1,585 bytes) is under it and an empty dispatch against it takes 5.7 s, once per `object` field that names such an entry. That is bounded work and the README now tells a host that stores instances where others can write to authenticate them, so I accept it; lower `MAX_STORED_SIZE` if that amplification matters to a host.

### ✅ Verified - RF12 In an unoptimized build a typed value nested about 120 levels is refused, well under the documented 256
- **Severity:** Low
- **Evidence:** The RF1 fix puts `normalize` under the 1 MiB stack budget (`normalize.rs:118`), and its unoptimized frames are large (the fix note says about 10 KB per level). Experiment with `type Link = { child?:Link }` state nested one level per batch entry: a debug build accepts 100 levels and fails at 120, 200 and 250 with `nx-ir-resource-limit: ... nests too deeply to check within the stack an evaluation may use`; a release build accepts all of them and refuses only past 256. So the same program and input succeed or fail by build profile, and the README's limits table (256 for a value crossing the boundary) is not what a debug build delivers. The message also prints the whole path, one segment per level.
- **Recommendation:** Shrink the per-level stack of normalization (keep diagnostics and `Path` formatting out of the recursive frames, as `eval` does with its cold functions, or walk iteratively), or say in the README that the 1 MiB budget can be met before 256 levels in unoptimized builds. Truncate the path in the message.
- **Fix:** The message no longer prints the path, so it is one sentence whatever the depth. The earlier refusal in an unoptimized build is kept and documented rather than changed: the README's Limits section says that checking a value against a type is under the stack budget and that an unoptimized build refuses a deeply nested typed value sooner than 256. The alternative, lifting `normalize` out of the budget, is what overflowed in RF1.
- **Verification:** The message is now one sentence whatever the depth (`normalize.rs:118-123`). Keeping the earlier refusal in unoptimized builds and documenting it in the README's Limits section is acceptable for this finding: it is a diagnostic, not an abort, release builds reach the documented 256, and taking `normalize` out of the budget is what RF1 was.

## Questions
- There is no budget on total work or allocation: nested ranges (`for i in 0..1000000 { for j in 0..1000000 { j } }`) and a result that shares a subtree twice per call level (expanded to a tree by `to_host`) run until memory is exhausted, from a small valid image. The TypeScript runtime behaves the same and the spec promises only "no panic, no stack exhaustion". Is that the intended line for a runtime that evaluates a stranger's image?
- `restore_component_instance` accepts any `serde` deserializer. Is a host expected to use one with a recursion limit, and should the documentation say so (see RF6)?
- A float result of negative zero serializes as `-0.0` from `NxValue` where the TypeScript runtime's JSON is `0` (seen for `{ 0.0 * -1.0 }`). The values compare equal numerically; does any consumer compare the JSON text?

## Summary
- Verification (2026-10-01): RF1 to RF10 verified; RF2 and RF7 accepted as documented decisions and RF10 as done in part. Two new findings, RF11 and RF12, were opened and, after a second pass the same day, verified. No finding is open.
- The evaluator follows the TypeScript runtime closely: of 179 calls compared across arithmetic, text forms, `float32`, occurrences, records, unions and update records, all agreed except the two in RF7 and three `nx.int` wrapper inputs the spec deliberately accepts (wide-integer arithmetic, RF2, was compared separately), the corpus passes in both variants, and a damage run far wider than the one in the repository found no panic.
- One real hole in the "never exhausts the stack" claim (RF1), reachable with a valid image and a long batch.
- Stored instances are the weakest part: restore validates handlers only (RF3), ties the instance to source text rather than images (RF4), and the serialized form is quadratic in size (RF5) and too deep for `serde_json` at modest nesting (RF6).
- The spec's blanket "same value and same code as TypeScript" is not true for integers past 2^53 (RF2) and needs either an exception or a behavior change before `retire-hir-interpreter` builds on it.
