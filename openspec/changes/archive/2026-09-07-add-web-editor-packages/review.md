## Findings

### ✅ Verified - RF1 The HTTP client can hang forever after the server has sent response headers
- **Severity:** High
- **Evidence:** [`packages/language-client/src/index.ts:67`](/home/bret/src/nx/packages/language-client/src/index.ts:67) awaits an asynchronous header hook before it creates the abort controller or timeout. More importantly, the timeout and caller-abort listener are removed as soon as `fetch` resolves at [`index.ts:99`](/home/bret/src/nx/packages/language-client/src/index.ts:99), before `response.text()` at [`index.ts:104`](/home/bret/src/nx/packages/language-client/src/index.ts:104). A response whose headers arrive but whose body never completes therefore leaves `hover`/`completions` pending after both caller cancellation and `timeoutMs`; this reproduces with a `ReadableStream` that never closes. That violates the protocol's cancellation and timeout requirements and prevents Monaco from silently degrading when the route stalls mid-response.
- **Recommendation:** Start cancellation/timeout coverage before awaiting the header hook, retain it through response-body consumption, and race/abort both phases. Add tests for an abort or timeout while headers are being produced and while a 200 response body is stalled.
- **Fix:** `packages/language-client/src/index.ts` now creates the abort controller and timer before awaiting the header hook, and races the hook and `response.text()` against the controller's abort, so the timeout and the caller's signal cover the whole query through body consumption. Two tests added in `client.test.ts`: timeout and caller abort while the header hook is pending (and no request is sent), and timeout and caller abort on a 200 whose body never closes.
- **Verification:** Verified with the language-client regression tests and an independent never-closing `ReadableStream`: the request rejects with `LanguageServiceTimeoutError` rather than remaining pending. The header-hook and response-body paths both reject promptly on caller cancellation.

### ✅ Verified - RF2 An initial highlighting-only registration permanently suppresses a later language service
- **Severity:** Medium
- **Evidence:** [`packages/monaco/src/index.ts:89`](/home/bret/src/nx/packages/monaco/src/index.ts:89) records the first registration for a Monaco namespace. Its providers are selected only from that first call at [`index.ts:92`](/home/bret/src/nx/packages/monaco/src/index.ts:92); subsequent calls merely increment `references` at [`index.ts:101`](/home/bret/src/nx/packages/monaco/src/index.ts:101). Consequently, `registerNxLanguage(monaco)` followed by `registerNxLanguage(monaco, { service })` leaves both provider arrays empty, contrary to the requirement that registration with an `NxLanguageService` provides hover and completions. This is a realistic host sequence when highlighting is initialized before an authenticated or remote service is available.
- **Recommendation:** Treat provider registration as independently upgradable: when an existing registration has no providers and a later call supplies a service, install them (and retain the associated options/service). Add a registration-order test for the no-service-then-service sequence.
- **Fix:** `registerNxLanguage` in `packages/monaco/src/index.ts` now installs providers on an existing registration whenever it has none and the call brings a `service`; the first registration no longer decides forever. The doc comment and the README's idempotence paragraph say so. Test added in `monaco.test.ts`: highlighting-only, then with a service, gives one hover and one completion provider answered by that service, a third call adds nothing, and disposing the last handle removes them.
- **Verification:** Verified the new registration-order test and an independent `registerNxLanguage(monaco)` then `registerNxLanguage(monaco, { service })` probe. It creates one hover provider and one completion provider, and retains idempotent disposal behavior.

### ✅ Verified - RF3 Snapshot caching is keyed by editor version rather than document content
- **Severity:** Medium
- **Evidence:** [`packages/language-http/src/cache.ts:13`](/home/bret/src/nx/packages/language-http/src/cache.ts:13) describes a content key, but [`cache.ts:17`](/home/bret/src/nx/packages/language-http/src/cache.ts:17) hashes `document.version`. The handler uses that key at [`packages/language-http/src/index.ts:126`](/home/bret/src/nx/packages/language-http/src/index.ts:126). Two requests with the same URI, identity, and source but versions 1 and 2 construct two snapshots, despite analysis being identical; D4 specifies a hash of `(uri, source)` pairs and the capability requires identical content to share one analysis. This forfeits reuse after a revert or a host version bump that does not alter text.
- **Recommendation:** Separate analysis cache identity from response version metadata: exclude `version` from the snapshot cache key, then reattach the current request's document versions to hover, completion, and diagnostic answers. Add a same-source/different-version cache test that also proves the returned version is current.
- **Fix:** `documentSetKey` in `packages/language-http/src/cache.ts` no longer hashes `version`, and `answerQuery` in `index.ts` stamps the current request's per-URI versions onto hover, completion, and each document's diagnostics answer (`null` where the request sent none). README's cache paragraph updated. Test added in `handler.test.ts`: the same text under versions 1, 2, 3, 4 and unversioned constructs one snapshot, and each answer carries the version of the request that produced it.
- **Verification:** Verified the cache key now excludes `version`, while response adaptation returns the current request's version for hover, completions, and every diagnostics document. The new regression test constructs one snapshot for versions 1–4 and an unversioned request, and passes.

### ✅ Verified - RF4 `toNodeListener` crashes the host process on a request whose `Host` header does not form a valid URL
- **Severity:** High
- **Evidence:** [`packages/language-http/src/index.ts:411-431`](/home/bret/src/nx/packages/language-http/src/index.ts:411) builds `http://${host}${incoming.url}` from the raw `Host` header and passes it to `new Request(...)` synchronously, outside the `handler(request).then(...).catch(...)` chain. Node's parser accepts a `Host` value such as `a b`, but `new Request` throws `TypeError: Failed to parse URL`, and a throw inside an `http.createServer` listener is an uncaught exception. Reproduced against the built package: a raw socket sending `POST /api/language/hover` with `Host: a b` ends the process (`UNCAUGHT: Failed to parse URL from http://a b/api/language/hover`, exit 3). The `language-http-service` spec requires malformed requests to be refused "without harming the process", and the README's plain `node:http` mount has no try/catch around the listener; the fiddle survives only because `server/index.mjs` wraps every route in its own `try`.
- **Recommendation:** Construct the `Request` inside a `try` (or inside the promise chain) and answer 400 with a JSON error body when it throws; ignore `Host` for routing entirely, since only the path is needed (`new URL(incoming.url ?? "/", "http://localhost")`). Add a listener test that sends a malformed `Host` over a raw socket and asserts a 400 and a still-listening server.
- **Fix:** `toNodeListener` in `packages/language-http/src/index.ts` now builds the `Request` in a `toRequest` helper from the path alone on a fixed `http://localhost` origin, ignoring `Host`, and wraps the construction in a `try` that answers 400 `invalid-request` if it ever throws; the 500 path shares a `writeJson` writer. Test added in `handler.test.ts`: a raw socket sending `Host: a b` gets a 200 hover answer and the server answers a normal request afterwards.
- **Verification:** Verified. `toRequest` builds the URL on a fixed `http://localhost` origin from the path alone, and its construction sits inside a `try` that answers 400. Re-ran the original raw-socket reproduction (`Host: a b`): the server now answers and stays up instead of exiting with an uncaught `TypeError`. The new listener test in `handler.test.ts` covers the same path and a follow-up request; the language-http suite passes (18 tests).

### ✅ Verified - RF5 The Monaco highlighter silently switches the editor to the first theme once it loads, so the README's own examples end up light
- **Severity:** Medium
- **Evidence:** `shikiToMonaco` ends by calling `monaco.editor.setTheme(themeIds[0])` (`@shikijs/monaco/dist/index.mjs:88`), and [`packages/monaco/src/index.ts:194`](/home/bret/src/nx/packages/monaco/src/index.ts:194) calls it after an async import and wasm load. Any theme the host selected before `ready` resolved is overwritten. Reproduced with the package's fake: `registerNxLanguage(monaco)` (default themes), `setTheme("github-dark")`, `await ready` → the active theme is `github-light`. Both README examples hit this: the direct `monaco.editor.create({ theme: "github-dark" })` call does not await `ready`, and the `@monaco-editor/react` example sets `theme="github-dark"` at mount while `beforeMount` has only just started loading. The README table says "Pick one with the editor's `theme` option", which is exactly what does not hold. The fiddle escapes only because it passes `themes: [THEME]` and awaits `ready` before creating the editor.
- **Recommendation:** After `shikiToMonaco`, re-apply the theme the host had chosen: record `setTheme` calls made between registration and `ready` (wrap `monaco.editor.setTheme` before loading, the way the bridge itself does) and replay the last one, or accept a `theme` option and document that the first entry of `themes` is what becomes active when nothing else is set. Add a fake-namespace test for "theme set before ready survives ready". Fix the README's direct example to `await registration.ready` or pass `themes: ["github-dark"]`.
- **Fix:** `loadHighlighter` in `packages/monaco/src/index.ts` watches `monaco.editor.setTheme` and the `theme` option of `monaco.editor.create` while Shiki loads, stops watching just before the bridge installs (so the bridge wraps Monaco's originals, not the watchers), and re-applies the host's last choice after it: through the bridge when it is one of the loaded themes, through Monaco's own `setTheme` otherwise. Doc comment and README (`themes` row, new **Themes** paragraph) say so; the README examples now hold without awaiting `ready`. Test added in `monaco.test.ts` covering `setTheme` before ready, `create({ theme })` before ready, and a theme Shiki does not know.
- **Verification:** Verified. `watchThemeChoice` records `setTheme` calls and `create({ theme })` while Shiki loads, is removed just before `shikiToMonaco` installs, and the recorded choice is re-applied afterwards (through the bridge for a loaded theme, through Monaco's original `setTheme` otherwise). Re-ran the original fake-namespace reproduction: `setTheme("github-dark")` before `ready` now survives (`github-dark` after ready, was `github-light`). Also probed a host that wraps `setTheme` itself during the load: the watcher stays in the chain harmlessly and later theme changes still apply. README `themes` row and new **Themes** paragraph match the behavior.

### ✅ Verified - RF6 Re-registering after the last handle is disposed reloads the highlighter and re-wraps Monaco's `setTheme` and `create`
- **Severity:** Medium
- **Evidence:** `dispose()` deletes the namespace's entry at [`packages/monaco/src/index.ts:124`](/home/bret/src/nx/packages/monaco/src/index.ts:124), so the next `registerNxLanguage` takes the `registration === undefined` branch at [`index.ts:93-102`](/home/bret/src/nx/packages/monaco/src/index.ts:93): it calls `setLanguageConfiguration` again (dropping the previous disposable) and `loadHighlighter` again, which re-imports Shiki, re-instantiates the Oniguruma engine, and runs `shikiToMonaco` a second time. That bridge monkey-patches `monaco.editor.setTheme` and `monaco.editor.create` on every call, so each cycle adds a wrapper layer holding the previous highlighter alive, and resets the theme again (RF5). Reproduced with the fake: after dispose + register, `setTheme` is a new wrapper and two language configurations were set. The doc comment and README state the opposite ("the language, its configuration, and the highlighter stay"). A host that registers in a React effect and disposes in its cleanup, which is the natural pairing for the returned `IDisposable`, cycles this on every remount and twice under strict mode.
- **Recommendation:** Split the per-namespace state: keep language registration and the highlighter promise in a `WeakMap` that is never cleared, and let the reference-counted entry own only the providers. Re-registration then reuses `ready` and adds providers. Extend the "two registrations" test to assert that dispose + register leaves one configuration set and the same `setTheme` function.
- **Fix:** Per-namespace state is split: a never-cleared `languages` `WeakMap` holds the highlighter's `ready`, and the reference-counted `registrations` entry owns only the providers. Dispose then register reuses the language, its configuration and the highlighter. The 'two registrations' test now asserts one configuration set and the same `setTheme`/`create` functions after the cycle. README idempotence paragraph updated.
- **Verification:** Verified. The highlighter's `ready` now lives in a never-cleared `languages` WeakMap and the reference-counted entry owns only providers. Re-ran the original reproduction: after dispose + register, `setTheme` is the same function and one language configuration was set (was two, with a fresh wrapper). The extended 'two registrations' test asserts the same; monaco suite passes (14 tests).

### ✅ Verified - RF10 Prelude shifting misses related locations that point into the queried document from another document
- **Severity:** Low
- **Evidence:** [`packages/language-http/src/index.ts:208-211`](/home/bret/src/nx/packages/language-http/src/index.ts:208) passes every non-queried document's diagnostics through untouched. A diagnostic reported on a sibling whose `related` entry names the queried document (an import conflict, say) therefore carries combined-text coordinates for that location, while the same location in the queried document's own diagnostics is shifted. - **Recommendation:** Shift `related` locations whose `uri` is the queried document in every document's diagnostics, not only in the queried document's, or state in the README that the prelude is single-document only.

README prelude bullet says so. Test added in `handler.test.ts` with a fake snapshot whose sibling diagnostic points into the queried document: the sibling's own range is untouched, its related location is shifted, and the queried document's diagnostics are as before.
- **Verification:** Verified. `shiftRelated` is applied to every document's diagnostics, so a sibling's related location into the queried document is shifted while the sibling's own range is untouched; the queried document's path is unchanged. The new test in `handler.test.ts` exercises exactly that with a fake snapshot, and the README's prelude bullet states it.
