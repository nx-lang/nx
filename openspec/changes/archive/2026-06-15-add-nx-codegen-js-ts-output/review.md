## Findings

### ✅ Verified - RF1 Fieldless union-case member access generates `undefined` instead of a case record
- **Severity:** High
- **Evidence:** For `type LoadState = | idle | loading` with `let root(): LoadState = { LoadState.idle }`, generated JS emits `return LoadState["idle"];`. `LoadState` is the emitted union metadata const `Object.freeze({ kind: "union", cases: ["idle","loading"] })`, so `LoadState["idle"]` is `undefined`. The interpreter produces `{"$type":"LoadState.idle"}`. The builder only has an `EnumMember` path (`enum_member_reference` in builder.rs:753) that requires `ResolvedItemKind::Enum`; union cases fall through to the generic `Member` branch (builder.rs:501-531) and emit `base[member]`. This is a silent wrong-result, not a diagnostic.
- **Recommendation:** Add a union-case construction path mirroring the interpreter: a member access whose base resolves to a `Union` (and whose member is a declared case) must emit a record literal `{ $type: "LoadState.idle", ...defaults }`, not an index into the metadata object. Add union parity tests (see RF8).
- **Fix:** Added union-case expression modeling/emission so fieldless member access emits a direct case record, with parity/snapshot coverage.
- **Verification:** Confirmed. New `CodegenExpressionKind::UnionCase` path (builder.rs:672-727, 905-1011) resolves member/element-tag union cases through the owning module and emits a `{ $type: "Union.case", ... }` literal. Independently ran `LoadState.idle` through node: generated output `{"$type":"LoadState.idle"}` equals interpreter `interpreter_json_root`. Snapshot test asserts `return ({ $type: "LoadState.idle" });` and `generated_javascript_serializes_union_cases_and_defaults` runs the parity check.

### ✅ Verified - RF2 Record/union-case default field values are dropped from generated output
- **Severity:** High
- **Evidence:** For `type User = { name: string age: int = 30 }` with `<User name="Bob" />`, generated JS emits `({ $type: "User", name: "Bob" })`; the interpreter emits `{"$type":"User","age":30,"name":"Bob"}`. `emit_record_object` (emit.rs:592) and `emit_element` (emit.rs:677) only emit properties present in the source literal — declared defaults are never injected. Same gap applies to union-case defaults (RF1's `failed { retryable: bool = true }` loses `retryable:true`). `CodegenRecordField` records `is_required` but never carries the default expression, so the emitter cannot apply it.
- **Recommendation:** Preserve record/union-case default expressions in the codegen model and emit them for fields omitted by the constructing literal, matching interpreter semantics. Add a parity test where a defaulted field is omitted at the construction site.
- **Fix:** Preserved field default expressions in record/union metadata and materialized omitted defaults during generated record/union-case construction, with parity tests.
- **Verification:** Confirmed. `CodegenRecordField.default` now carries the lowered default expression (model.rs:131; builder.rs:298-368), and `emit_materialized_record_object` injects omitted defaults — either inline or via an IIFE when materialization is needed (emit.rs:723-861). Independently ran `type User = { name: string age: int = 30 }` + `<User name="Bob" />` through node: generated `{"$type":"User","name":"Bob","age":30}` matches the interpreter. Same for the union payload default (`retryable: bool = true`) and for an omitted nullable field (emits `nick: null`, matching the interpreter).

### ✅ Verified - RF3 Local/parameter bindings that shadow a module-level or imported item are mis-resolved
- **Severity:** High
- **Evidence:** `build_expression` resolves every `ast::Expr::Ident` via `resolve_visible_reference` (builder.rs:262, 715), which only consults `resolved_program.local_item` / `imported_item` — both keyed by top-level/imported names with no awareness of function params or `let`/block locals. Confirmed: `import { answer } from "../shared/value.nx"` with `let root(answer: int): int = { answer }` generates `return m1_answer;` (the imported value 42) instead of the parameter. The interpreter returns the parameter. (Same-module shadowing happens to survive only because both emit the identical identifier.)
- **Recommendation:** Track lexical scope during model building (params + `Let`/block `Let` bindings) and resolve an identifier to a module/import reference only when no in-scope local binding shadows it.
- **Fix:** Added lexical scope tracking for parameters, `let` expressions, block lets, and loop bindings before resolving top-level/imported references.
- **Verification:** Confirmed. A `LexicalScope` stack (builder.rs:147-178) is threaded through `build_expression`; params, `Let`/block-let, and `for` item/index bindings are inserted with proper push/pop, and `Ident`/member/enum/union resolution short-circuits to `None` when the name is in scope (builder.rs:386-390, 926-928, 1138-1140, 1155-1157). The `local_bindings_shadow_imported_items` test plus my independent node run of `root(answer)` over the shadowed-import program returns the parameter (`7`), not the import; generated module no longer contains `m1_answer`.

### ✅ Verified - RF4 Generated TypeScript uses `.ts` import specifiers that standard `tsc` rejects
- **Severity:** Medium
- **Evidence:** `emit_module` emits `import { ... } from "./nx-runtime.ts"` (emit.rs:146) and cross-module imports through `context.module_file` (e.g. `./m1_value.ts`, emit.rs:154-160); `emit_index` likewise re-exports from `./<stem>.ts`. Under default `tsc`, importing a path with a `.ts` extension is error TS5097 unless `allowImportingTsExtensions` (which itself requires `noEmit`/`emitDeclarationOnly`). The spec requires "readable executable TypeScript modules" with imports/exports "needed for cross-module execution", but only the JavaScript target is ever executed/validated in tests (`execute_generated_javascript_root`), so this never surfaces in CI.
- **Recommendation:** Emit extensionless or `.js` specifiers for the TypeScript target (common for `tsc`/bundler interop), or document the required `allowImportingTsExtensions`/bundler assumption. Add a `tsc --noEmit` smoke check for a small generated TS program if a TS toolchain is available, analogous to the node ESM check.
- **Fix:** TypeScript output now emits `.js` import/re-export specifiers, and an optional `tsc --noEmit` smoke test runs when `tsc` is available.
- **Verification:** The specifier fix is confirmed: `import_file` rewrites `.ts` → `.js` for the TypeScript target (emit.rs:1489-1495), applied to runtime, cross-module, and `index.ts` re-export specifiers. The `typescript_uses_js_import_specifiers_and_only_used_runtime_helpers` test asserts `from "./m1_value.js"`, `from "./m0_main.js"`, and no `.ts"` specifier — the original TS5097 trigger is gone. **Caveat:** the end-to-end `tsc --noEmit` smoke test (`generated_typescript_type_checks_when_tsc_is_available`) does **not** actually validate compilation — `tsc` is absent in this environment so it skips, and its NX source does not even parse, so it would panic before reaching `tsc` on any `tsc`-equipped machine. See RF10. The specifier-rejection finding itself is resolved; full tsc compilation remains unexercised.

### ✅ Verified - RF5 Every generated module imports runtime helpers unconditionally
- **Severity:** Low
- **Evidence:** `emit_module` always emits the three-symbol runtime import (emit.rs:146-149) regardless of use. A trivial `let root() = { 1 + 2 }` TS module imports all three while using none. Under `noUnusedLocals` or typical lint configs this is an error/warning, compounding RF4 for the TS target.
- **Recommendation:** Emit only the runtime helpers actually referenced by the module, or import the runtime namespace lazily.
- **Fix:** Added runtime-helper usage collection so modules import only helpers they actually reference, omit the runtime import entirely when none are used, and no longer use an array helper for plain generated arrays.
- **Verification:** Confirmed. `collect_module_runtime_helpers` walks declarations and imports only the `nxElement`/`nxRuntimeError` helpers actually referenced; the import line is omitted entirely when the set is empty (emit.rs:167-174, 1266-1407). `nxArray` was removed from both runtime sources (runtime.rs) and arrays/loops now emit plain `[...]` / `Array.from(...).map(...)` (emit.rs:593-615) — verified by node parity for `{ 1 2 3 }` → `[1,2,3]`. The trivial `let root() = { "hello" }` TS module contains no `nx-runtime` import (asserted by test and re-confirmed).

### ✅ Verified - RF6 `safe_identifier` collisions can emit duplicate top-level declarations
- **Severity:** Low
- **Evidence:** `safe_identifier` (emit.rs:1025) maps `.`, `-`, `/`, `\`, and whitespace to `_`, so distinct NX names like `my-name` and `my_name` both become `my_name`. `emit_declaration` emits one `export const`/`function` per declaration with no per-module uniqueness pass, so a collision yields duplicate identifiers (a JS/TS error). The spec requires deterministic *and* coherent generated identifiers.
- **Recommendation:** Deduplicate generated declaration names within a module (and align import-alias generation, which already disambiguates by module id but not by collided local name).
- **Fix:** Added per-module generated declaration-name deduplication and routed local references, exports, and import specifiers through the deduplicated names.
- **Verification:** Confirmed by inspection. `EmitContext::new` builds a per-module `declaration_names` map via `unique_identifier`, which appends `_2`, `_3`, … against a per-module `used_names` set (emit.rs:78-88, 1501-1514). All emission sites resolve names through `declaration_name`/`reference_name` (declarations, local references, `index` exports, and import specifier left-hand sides), so a `safe_identifier` collision now yields distinct emitted identifiers. Note: this dedup covers top-level declarations; record/union field-name collisions inside the materialization IIFE are not deduped, but that is a much narrower edge (see RF11).

### ✅ Verified - RF7 Cross-module record literals lose declaration field order
- **Severity:** Low
- **Evidence:** `record_field_order` (builder.rs:655) searches only the *local* `lowered_module` for the record declaration. When the constructed record type is imported from another module, it returns an empty order, so `emit_record_object` falls back to sorting the provided properties alphabetically (emit.rs:617-621). Output stays deterministic but no longer follows declaration order, diverging from the same-module case and the spec's "emitter-controlled declaration/effective-field order" intent.
- **Recommendation:** Resolve the record declaration through the reference's owning module (the import reference is available) to recover declared field order for cross-module records.
- **Fix:** Resolved record literal/element shapes through the owning module so imported records use declaration field order and defaults.
- **Verification:** Confirmed. `record_literal_shape` (builder.rs:1013-1058) resolves the record reference to its owning module, loads that module's lowered record definition, and returns fields (with defaults) in declaration order; `build_element_expression` uses the same path for record-tag elements. The `cross_module_record_literals_use_declared_field_order` test asserts an imported `User` constructed as `<User age=42 name="Ada" />` emits `{ $type: "User", name: "Ada", age: 42 }` (declaration order), which passes.

### ✅ Verified - RF8 Union/discriminated-union value parity is claimed complete but untested (and currently broken)
- **Severity:** Medium
- **Evidence:** Task 8.2 and the "Generated behavior is validated against the interpreter" requirement list discriminated unions and enum values in parity coverage, but `tests.rs` contains no union case. The only test touching unions is absence — and RF1 shows fieldless union construction is actually wrong. The snapshot test (`emits_supported_subset_snapshots_in_both_target_modes`) also omits unions.
- **Recommendation:** Add interpreter-parity tests for both fieldless (`LoadState.idle`) and payload (`<LoadState.failed .../>`) union cases. These will fail until RF1/RF2 are fixed, which is the intended signal.
- **Fix:** Added generated/interpreter parity coverage for fieldless and payload union cases, plus snapshot-subset coverage for fieldless union output.
- **Verification:** Confirmed. `generated_javascript_serializes_union_cases_and_defaults` exercises fieldless (`LoadState.idle`), payload-with-default (`<LoadState.failed message=... />`), and record-default cases against the interpreter via node, and the snapshot test now includes a `union` case. All run and pass (node present in this environment). I also independently confirmed a union case with a `content` field serializes its content into the declared field (`kids: ["a","b"]`), matching the interpreter.

### ✅ Verified - RF9 Dead record/union/type-alias metadata constants are still emitted
- **Severity:** Low
- **Evidence:** Records emit `export const User = Object.freeze({ kind: "record", fields: [...] })`, unions emit `{ kind: "union", cases: [...] }`, and type aliases emit `{ kind: "type-alias" }` (emit.rs:265-310). Record/enum construction now uses direct literals (task 9.3/9.5), so these consts are unreferenced. Beyond being dead weight, the union metadata const is what RF1 mistakenly indexes into. Design decision 4 calls for "ordinary JavaScript data construction … keep the helper surface small".
- **Recommendation:** Drop the unused metadata consts (or, if any are intended for future runtime use, reference them so the intent is explicit and they don't collide with value-position member access).
- **Fix:** Removed record, union, and type-alias metadata const emission; TypeScript keeps type-only surfaces while JavaScript omits dead declarations.
- **Verification:** Confirmed. `emit_declaration` for `Record`/`Union` now emits only TypeScript type surfaces (and nothing for the JavaScript target), and `TypeAlias` emits nothing at all (emit.rs:309-335). No `kind: "record"`/`"union"`/`"type-alias"` const remains, so value-position member access can no longer collide with a metadata object. The `emits_strong_typescript_records_and_string_union_enums` test asserts `!record_module.contains("export const User")`.

## New Findings Discovered During 2026-06-15 17:28 Verification

### ✅ Verified - RF10 The RF4 `tsc` smoke test never validates TypeScript compilation (and would panic where `tsc` exists)
- **Severity:** Medium
- **Evidence:** `generated_typescript_type_checks_when_tsc_is_available` (tests.rs:291-338) was added to validate the RF4 fix end-to-end, but its NX source (`type User = { name: string age: int = answer }`) does not parse — NX record field defaults cannot reference an identifier; only literal defaults are allowed. I confirmed `build_workspace_program_artifact` returns `["Invalid record definition"]` for that exact source. Because the test checks `tsc --version` first and returns early when absent, it silently no-ops on machines without `tsc` (this environment). On any `tsc`-equipped machine it would reach `artifact_from_workspace(...)`, which `.expect()`s the build and would therefore **panic** before ever invoking `tsc`. Net effect: the RF4 fix's only end-to-end compilation check is dead — it provides false confidence and would break a `tsc`-equipped CI.
- **Recommendation:** Replace the default with a literal (e.g. `age: int = 0`) or drop the cross-module default entirely so the source parses, then re-run with `tsc` installed to actually exercise `tsc --noEmit` against generated `.js`-specifier output. Consider building the artifact before the `tsc` availability gate so an invalid fixture fails loudly rather than masquerading as a skip.
- **Fix:** Updated the smoke-test fixture to use a literal record-field default while still referencing an imported value in record construction, and moved artifact generation before the optional `tsc` availability gate so invalid NX source fails even when `tsc` is unavailable.
- **Verification:** Confirmed. The fixture is now `type User = { name: string age: int = 0 }` with `<User name="Ada" age={answer} />` (tests.rs:300-313), which parses cleanly — `emit_program(...).expect("ts output")` runs at line 314, *before* the `tsc --version` gate at 315, so an unparseable fixture would now panic regardless of `tsc` presence. I independently emitted this fixture: it produces `import { answer as m1_answer } from "./m1_value.js";`, an optional `age?: number` record field, and `return ({ $type: "User", name: "Ada", age: m1_answer });` — valid `.js`-specifier, strict-mode-friendly TS that exercises the RF4 cross-module path. The test passes (artifact builds + emits); the actual `tsc --noEmit` subprocess still skips in this environment because `tsc` is not installed, but the test is now structurally correct and will run it wherever `tsc` exists.

### ✅ Verified - RF11 Record/union field-name collisions are not deduplicated in the materialization IIFE
- **Severity:** Low
- **Evidence:** When a record/union case needs default materialization, `emit_materialized_record_iife` emits `const <safe_identifier(field.name)> = …;` per field (emit.rs:820-835). Two fields whose names collapse to the same `safe_identifier` (e.g. `my-field` and `my_field`) would emit duplicate `const` bindings — a JS/TS error — and a field literally named `__nx_prop_<n>` would alias an explicit-property temp. RF6's dedup pass only covers top-level declaration names, not field locals inside this IIFE. This is a narrow edge and may be unreachable if NX record field names are restricted to plain identifiers; it is filed for completeness rather than as a confirmed defect.
- **Recommendation:** If non-identifier field names are reachable, key the IIFE temporaries by index (as already done for explicit props) instead of by `safe_identifier(field.name)`, or run field locals through the same dedup helper. Otherwise document that record field names are constrained to collision-free identifiers.
- **Fix:** Changed materialized record/union field locals to deterministic `__nx_field_<index>` temps and added a model-level regression test covering both escaped-name collisions and a field named like an explicit-property temp.
- **Verification:** Confirmed. `emit_materialized_record_iife` now binds each field to an index-based `__nx_field_<n>` const and maps `safe_object_key(field_name): __nx_field_<n>` in the returned literal (emit.rs:820-847), so field names never become `const` identifiers and cannot collide. Explicit-property temps remain in the disjoint `__nx_prop_<n>` namespace. The `materialized_record_iife_uses_collision_free_field_temps` test drives the exact adversarial case — fields `my-field`, `my_field`, and `__nx_prop_0` plus an explicit `explicit` property — and asserts distinct `__nx_field_0/1/2` consts, no `const my_field =`, and a correct returned literal; it passes. The pre-existing record/union default parity tests still exercise the IIFE end-to-end through node.

## Questions
- Is the generated TypeScript target intended to be consumed only by `.ts`-extension-tolerant bundlers (Vite/esbuild/Deno/Bun), or should it also compile under stock `tsc`? The answer determines RF4/RF5 severity. (RF4's specifier fix is in place; RF10 now makes the optional `tsc` path usable where `tsc` is installed.)
- Are union case values in scope for "this change" parity, or deferred? The spec text lists them as covered, which is why RF1/RF8 are filed as defects rather than deferrals. (Now resolved — union parity is implemented and tested.)

## Summary
The crate boundary, model/emitter split, `nx-api` source accessors, CLI `typegen`/`codegen` separation, and the `typegen` rename are well structured and match the design. However, three High-severity correctness/parity bugs escape the test suite because parity is only exercised for a narrow set of fully-specified record/enum/element programs run through node: fieldless union cases generate `undefined` (RF1), record/union default field values are silently dropped (RF2), and local/parameter bindings that shadow module/imported items resolve to the wrong target (RF3). RF4/RF5 mean the TypeScript target likely does not compile under stock `tsc`, and that target is never compiled in tests. The union parity coverage claimed by tasks 8.1–8.2 is absent (RF8). Recommend addressing RF1–RF3 before archiving and expanding parity tests (shadowing, omitted-default fields, both union case forms) to lock in the fixes.
