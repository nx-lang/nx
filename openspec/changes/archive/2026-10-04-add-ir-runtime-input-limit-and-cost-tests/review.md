## Findings

### ✅ Verified - RF1 The input size is not defined for the values whose JavaScript form and `NxValue` form differ, and the two runtimes already disagree on one of them
- **Severity:** Medium
- **Evidence:** `specs/nx-ir-format/spec.md` defines the size by "one for each value" and says every runtime measures the same input alike; `design.md` decision 2 says "Both runtimes already compute it and already agree on it". They do not for the wide-integer wrapper. `writtenCost` counts `{ "$type": "nx.int", "value": "<digits>" }` as one value and does not look inside (`runtime/typescript/src/index.ts:3315`, `:3342`); the Rust runtime reads the same record as a record with one string field, and only a typed `int` site turns it into an integer (`crates/nx-ir-runtime/src/value.rs:470`, `normalize.rs:533`). Probe on the corpus function `repeated(o:object, n:int)` with `n` 1: the wrapper costs 15 in Rust and 14 in TypeScript; a list of two wrappers 18 and 16; `NxValue::Int(9007199254740993)` costs 14. So the same JSON input has size 2 in a Rust counter built into `from_host` and 1 in a TypeScript walk built on `writtenCost`, and a third runtime reading the requirement would say 2. Other forms the requirement leaves open, each of which gives a different number depending on the reading:
  - a `$type` key in a map the host passes (props, a state, arguments by name): the TypeScript measure reads it as a type name, a Rust `BTreeMap<String, NxValue>` holds it as a field;
  - a `$type` that is not a string in JavaScript: `writtenCost` adds nothing for it and no walk enters it, so whatever it holds has size 0;
  - a map the TypeScript host leaves out (`props` and `args` default to `{}`), which the Rust API cannot leave out: 0 or 1;
  - `undefined` as a positional argument, which the TypeScript runtime reads as "left out" (`index.ts:2485`) and Rust cannot express;
  - values outside the canonical encoding (a hole, a `bigint`, a `Date`, a `Map`, a typed array), and the runtime's own `ActionHandlerValue` and function reference objects, which `writtenCost` counts as one and a plain walk would follow into the linked program.
  
  The cases the task brief asked about and that are fine as written: `null` and an empty list are one each, an integer and a float are one each in every carrier, a string is measured in UTF-16 code units in both (`utf16_len`, `length`), a value reached twice counts twice in both, and a batch entry that names a handler by token is an ordinary record in both.
- **Recommendation:** Add the rules to the requirement, with a scenario for each that changes a number: a wide-integer wrapper is one value in every runtime (the Rust counter recognizes the record); `$type` is a type name only where it is a string, and say whether a top-level map has one; a map parameter counts as one record whether or not the host passed it, and an absent state counts nothing; `undefined` and any value outside the canonical encoding counts one and is not entered (or is refused). Correct decision 2's "already agree". Put a wide integer at `object` in the corpus cases of task 5.2, since both runtimes return it.
- **Fix:** The first requirement of `specs/nx-ir-format` now has a list of rules for the forms that differ, with a scenario for each that changes a number: a wide integer is one value in either spelling, the Rust measure recognizing the `nx.int` record with one string field `value`; props or named arguments left out are an empty record, size one, and a state not passed is not input; `$type` holding a string is a type name wherever it appears and a field otherwise; an absent or undefined positional argument is the empty value; a value that is not a canonical value, the runtime's own handler and function objects included, is one value and is not entered. Decision 2 no longer says the runtimes already agree and lists the same rules; tasks 2.1, 3.2 and 4.2 carry them. Not taken up: a wide integer in the corpus cases. A corpus case is one JSON spelling read by both runtimes, and the Rust runtime evaluates the `nx.int` record at `object` as a record (15 against 14), so the case would fail for a reason that is the cost model's, not this change's; decision 5 and the corpus requirement say cases use inputs spelled alike, the generated cases carry wide integers as `NxValue::Int` in Rust, and the question of evaluation is in Open Questions for the user.
- **Verification:** (2026-10-03 17:08) Reopened, narrowed to two of the new rules; the rest is verified. The rules are in the requirement, in decision 2 and in tasks 2.1, 3.2 and 4.2, decision 2 no longer says the runtimes agree already, and the new scenario numbers are right: 1 for props left out (`props` and `args` default to `{}` in TypeScript and are required maps in Rust, while a state is optional in both), 1 and 3 for wide integers, 2 for props with a type name. Declining a wide integer in the corpus is accepted: a corpus case is one JSON spelling, and `NxValue::from_json_str` hands Rust the record, which costs one more to return than in TypeScript, so the case could not pass today. What is wrong is that two rules let an unbounded value in at size one. (1) "is one value, and its text is not counted": `{ "$type": "nx.int", "value": <a megabyte of text> }` matches the rule, so it has size 1 under any limit. In the TypeScript runtime it also costs 1 to write: returned 100 times through the corpus function `repeated` it costs 311 operations and is 105 MB of JSON to the host, and two of them compared cost one pair for a comparison of both strings (`runtime/typescript/src/index.ts:3716`). (2) "any object the runtime made for its own use" is one value and is not read further. The runtime knows its handler objects only by a tag, `$nxKind === "actionHandler"` (`index.ts:3468`), which a host value can carry: an object from `JSON.parse` with that key and a megabyte string under `action.declaration.name`, returned 100 times, also costs 311 operations and 105 MB, where a plain record holding the same string costs 1,638,811. Under the rule as written both shapes pass the input limit at size one, so the limit does not bound the very kind of step it is for. Remaining work: count the text of the `nx.int` form by its length like any string (twenty digits cost nothing, so a real wide integer is still 1 and agrees with `NxValue::Int`), or recognize the form only when `value` is at most twenty characters of digits and a sign; and say that an object counts as the runtime's own only when the runtime can tell it made it (by identity, as a set of the handlers it created, or by class as the function reference already is), an object that merely carries the tag being a plain object that is entered. Add a scenario for each. RF16 is the same two shapes in the code that exists.
- **Fix (second round):** The two rules that let an unbounded value in at size one are changed. The `nx.int` form is one value and one more for every 64 code units of its `value`, so a megabyte of text spelled as a wide integer is 16,385 and a real integer is still one (spec rule and a new scenario, decision 2, tasks 2.1 and 3.2). A value is the runtime's own only when the runtime can tell it made it; an object that only carries the marking, as one read from JSON can, is a plain object and is measured (spec rule and a new scenario, decision 2, task 4.2). The runtime itself now behaves that way: see RF24 of `add-ir-runtime-evaluation-budget`.
- **Verification:** (2026-10-03 17:21, second round) Verified. The `nx.int` form is one value and one more for every 64 code units of its `value`, and an object counts as the runtime's own only when the runtime can tell it made it; both are in the requirement with a scenario each, in decision 2 and in tasks 2.1, 3.2 and 4.2, and "its text is not counted" is gone. The numbers are right: a megabyte of text in the form is 1 + 16,384 = 16,385, and the tagged object is the object, its marking and the string, which is more than 16,384. The text agrees with the runtime as it now is: against the rebuilt `dist`, one return of the megabyte `nx.int` form costs 16,398 operations (100 returns cost 311 before), and the tagged object 16,402, the same as the Rust runtime's count for 100 returns (1,639,111 in both). `isActionHandler` now asks a `WeakSet` (`runtime/typescript/src/index.ts:3481`). A real wide integer is still 1. Two small points are in RF20: no task asserts the tagged-object scenario's number, and the runtime's test for the form is wider than this rule's.

### ✅ Verified - RF2 The Rust design counts input "where it is read", which is after evaluation has started in three methods
- **Severity:** Medium
- **Evidence:** Both runtime specs require the refusal "before any value is checked against a type and before any node is evaluated", and `design.md` decision 4 has the order "validate the options, measure the input, then proceed". The same decision says of Rust that `from_host` and `fields_from_host` take a counter and "host values are counted where they are read", and task 3.2 implements exactly that. Where they are read today:
  - `dispatch_component_actions` converts each entry inside the loop, after the handlers of the entries before it have run (`crates/nx-ir-runtime/src/component.rs:803-845`);
  - `initialize_component` converts the state after the props have been normalized, defaults evaluated (`component.rs:674-704`), and `evaluate_component` likewise (`:751-759`);
  - `evaluate_function` and `call_function` look the entrypoint up first (`:578-587`, `:601-608`), which task 3.4 does cover.
  
  So a batch of a small entry and an oversized one runs the first handler before it is refused, and props that fail their type check with an oversized state report the type check in Rust and `maxInputSize` in TypeScript, which measures everything in its wrapper first. That breaks "For the same input and the same limit, the Rust runtime SHALL refuse a call the TypeScript runtime refuses" in which diagnostic comes back, and the scenario "no node SHALL have been evaluated". Task 3.3 says "one counter per public call" and nothing about order.
- **Recommendation:** Measure before anything else in Rust as well. The simplest form is a count-only pass over the `&NxValue` arguments at the top of each public method: it allocates nothing, stops at the limit, and makes "reads no more than the limit allows" true without touching the conversion. Otherwise convert every host value of the call before any lookup or normalization, the whole batch included. Amend decision 4 and tasks 3.2 and 3.3, and add to task 3.4: a batch whose second entry is oversized fails naming `maxInputSize` under `max_operations: Some(0)`; props of the wrong type with an oversized state fail naming `maxInputSize`; the same two cases in task 4.3 with the same expectation.
- **Fix:** Decision 4 now has the Rust runtime measure in a count-only pass of its own over the `&NxValue` arguments at the top of each public method, with an explicit stack, before the entrypoint is looked up or anything converted; the conversion is untouched. Context records where the three methods convert today. Tasks 3.2 and 3.3 are rewritten to that, and 3.4 and 4.3 add the two order cases (a batch whose second entry is oversized under a budget of zero runs no handler; wrong-typed props with an oversized state), which both runtime deltas now have as scenarios.
- **Verification:** (2026-10-03 17:08) Verified. Decision 4 now measures in a count-only pass over the `&NxValue` arguments at the top of each method, before any lookup or conversion, and Context records where the three methods convert today, which matches `component.rs`. Tasks 3.2 and 3.3 build that, 3.4 and 4.3 test the two order cases, and both deltas have the scenarios ("A batch is measured whole before any of it runs", "Oversized input is reported before any other fault of the call"). No text still says the count rides on `from_host`.

### ✅ Verified - RF3 "No more work than the limit allows" cannot be met in JavaScript for one wide object, and is not what the Rust string count does
- **Severity:** Medium
- **Evidence:** `specs/nx-ir-format/spec.md`: a runtime "SHALL do no more work measuring the input than the limit allows, however large the input is and however the host holds it"; the TypeScript delta: "SHALL read no more of the input than the limit allows". A walk has to list an object's keys before it can count one, and V8 collects every key when a `for...in` starts, not as it iterates. Measured on Node 24 with an object of 2,000,000 keys: a `for...in` that breaks after 10 keys takes 410 ms, the same as `Object.keys` (395 to 450 ms), for a plain object and for one from `JSON.parse`. So under `maxInputSize: 10` the walk does work and allocates in proportion to the width of the object that takes it over the limit. Task 4.2's check, a getter that throws after a fixed number of reads, counts value reads and cannot see this. In Rust, `utf16_len` scans a whole string (`str::is_ascii` first, then a decode), so a megabyte string under a limit of 10 is read end to end; task 3.6 measures allocation and does not see it either. "However the host holds it" also cannot hold for a getter or a Proxy, which may answer differently when evaluation reads the value again after it was measured.
- **Recommendation:** State what is achievable: the work of measuring is bounded by the limit plus one enumeration of the keys of the object at which the count passes it, and it is done once per call. Say the measure is of plain data, and that a host object with getters or a Proxy is outside the guarantee. In Rust, refuse from the byte length before scanning: a string of `b` bytes has at least `b / 3` code units, so `b / 192` over what is left is a refusal, and anything else is a scan the limit bounds. Change task 4.2 to assert what the walk can promise (values read, and the engine's stack) and drop "no more than limit + 1" as a claim about work.
- **Fix:** The requirement now says a runtime stops measuring as soon as the size passes the limit, and bounds the work, for plain data, by the limit plus at most once in a call the number of members of the one record at which the limit is passed; it adds that a runtime does not read the whole of a string or a name to refuse it when its length alone passes the limit, with a scenario. "However the host holds it" is gone, and a getter or a Proxy is a stated non-goal. Decision 4 gives the Rust byte-length test (`bytes / 192`) and the measured 410 ms for the JavaScript listing; task 4.2 asserts indices read on an array and records the wide-object time instead of claiming limit + 1; task 3.6 adds a 64-megabyte string.
- **Verification:** (2026-10-03 17:08) Verified. The requirement bounds the work by the limit plus, once in a call, the members of the one record at which the limit is passed, for plain data; "however the host holds it" is gone from every artifact and a getter or Proxy is a non-goal. The `bytes / 192` test is right: a UTF-16 code unit is at most three bytes of UTF-8, so a text of `b` bytes costs at least `b / 192`, and one that is not refused that way is at most `192 × (what is left + 1)` bytes to scan. Task 4.2 counts indices read through a Proxy over an array, which works since `Array.isArray` is true for one. One sentence is stronger than the design can meet and one scenario has no test that can observe it; both are in RF19.

### ✅ Verified - RF4 The time rule would not have reported RF9, RF11 or RF18, and its only guard against an honest case is the floor
- **Severity:** Medium
- **Evidence:** `design.md` decision 8 reports a case when its count less than doubles over an eightfold size while its time more than quadruples, and says that "is the signature of every break the review found". Checked against the budget change's `review.md`:
  - RF8, RF10, RF20 and the flat-count rows of RF17 fit: the count did not depend on the size.
  - RF11 (a comparison quadratic in the fields) does not: the count is `n + 1`, so it grows eightfold and the first condition is false, while the time grows sixty-four-fold.
  - RF9 and RF18 (state walked on every patch) do not: the state is written for the host at the end of every dispatch, so the count is about `n + patches` and grows with the size; the work is `patches × n`. Scaling the size alone leaves time over count constant, so no rule on these two runs can see it.
  
  The other direction: the Rust runtime converts host input once, uncharged by design ("reading the host's input before it is checked" is free in *Evaluation cost*), so every probe that holds a value at `object` has a flat count and a time that grows eightfold. Only the floor keeps those out of the report, and a floor high enough for that also hides a real step unless the repeat count is large; decision 6 gives sizes and no repeat counts. Nothing says how many times a case is timed, and one Node run includes compilation and collection.
- **Recommendation:** Compare growth with growth, and scale both dimensions. Run each case at a base size and repeat count and again with both multiplied by eight, and report when `time(big) / time(base)` is more than twice `(count + input size)(big) / (count + input size)(base)`, past the floor. An honest case keeps the two ratios equal, the one-time conversion included; RF8, RF9, RF10, RF11, RF17, RF18 and RF20 each raise the first well above the second. Take the least of several timed runs. Say in decision 6 what repeat counts the generator draws. Correct the "every break" sentence, and make task 9.3 re-introduce one hole of each kind (RF8's and RF11's, or RF9's) rather than one.
- **Fix:** The rule is now growth against growth over two scales that multiply the value and the repeats together by eight: a case is reported when its time grows by more than twice the growth of its operation count plus input size, past the floor, with a time the least of five runs (spec requirement three, decision 8, proposal). Decision 6 sets the repeats at 16 and 128. Decision 8 says which review breaks each form of the rule fits instead of "every break", and why the Rust conversion on the way in is not reported. The spec has scenarios for a copy on every call, a walk repeated within one call, and honest work that is not reported; task 9.3 re-introduces one hole of each kind (RF8's, RF9's, RF11's) and checks the honest case.
- **Verification:** (2026-10-03 17:08) Verified for the rule. Two scales with the value and the repeats both multiplied by eight, and a report when time grows by more than twice the growth of count plus input size, is in the spec, decision 8, the proposal and task 9.3, and the old two-condition rule is gone everywhere. Checked against the budget review's holes by their arithmetic: a copy on every call (RF8, RF10, RF20, RF17's flat rows) has units growing eightfold and time sixty-four-fold; a walk repeated in a call (RF9, RF18) the same; a quadratic comparison (RF11) has time growing eight times faster than its units with or without repeats. An honest case has time `T0 + a × count + b × input`, whose growth cannot exceed the growth of the units unless a unit of input costs many times what an operation does and the input is a small part of the units, which a single conversion on the way in is not. So the rule reports every kind and stays quiet on the honest one. Whether a reported hole clears the floor at the scales chosen is a separate matter, RF17.

### ✅ Verified - RF5 The allocation bound is one calibrated constant over the whole suite, so what it can catch depends on repeat counts the design does not set; and equal bytes in every build is not guaranteed
- **Severity:** Medium
- **Evidence:** `design.md` decision 7 asserts `bytes ≤ K × (operations + input size) + C` with `K` about four times the largest ratio any case shows. The largest honest ratio is set by the least favourable case: a string under 64 code units has size 1 and can be 189 bytes of UTF-8 plus its headers, and a value returned is copied in and out, so `K` will be in the high hundreds of bytes or more. An uncharged copy of `n` items made `r` times allocates about `16 × r × n` bytes against a bound of `K × (c × r + n)`: it is outside the bound only when `r` is well above `K / 16`, some tens of repeats, at a size well above `K × c / 16`. With the input size inside the bound, a step that copies the input a fixed number of times is never outside it. So "within the bound at the base size, outside it at eight times" holds for a generator that draws large repeat counts, and decision 6 does not say it does. Task 9.2's two mutations would show whether it does, after the fact. Separately, the Rust delta's scenario "The check does not depend on the machine" requires the same bytes in an optimized and an unoptimized build. Bytes requested are equal on two runs of one build, but the compiler may remove an allocation in an optimized build, and sizes change with the toolchain and the pointer width; CI runs only the unoptimized build, so a difference would go unseen until someone ran the other.
- **Recommendation:** Add a relative assertion beside the absolute one, which needs no calibration: `bytes / (operations + input size)` at the larger run is at most twice what it is at the base run, plus a small constant. Scale the repeat count with the size, as in RF4, and state the repeat counts in decision 6. Narrow the scenario to "the same bytes on two runs of one build, and inside the bound in both builds", and keep task 9.1's comparison of the two builds as a measurement to record, not an equality to hold.
- **Fix:** Decision 7, the Rust delta's second requirement and task 9.1 add a relative assertion that needs no calibration: bytes for each unit of operations plus input size at the larger scale are at most twice those at the base. The repeats scale with the size (16 and 128, decision 6). The text says a step that copies the input a fixed number of times is within the bounds and is not what the check looks for. The scenario is narrowed to the same bytes on two runs of one build and within the bounds in both builds; task 9.1 measures both builds to set `K`, and 9.2 expects its mutations to fail on the relative assertion.
- **Verification:** (2026-10-03 17:08) Verified. The relative assertion does what decision 7 says: an uncharged copy of `n` items on each of `r` repeats allocates `r × n × s` bytes, which at the larger scale is sixty-four times as much for eight times the units, so bytes per unit grow about eightfold against a bound of two; it holds as long as ninety-six times the bytes one copy takes per item exceed the honest bytes per item, which they do by a wide margin. It does not misfire on growth by doubling: a vector's or a map's capacity scales by exactly eight when its length does, so requested bytes per item are the same at both scales. The Rust delta, decision 7 and tasks 9.1 and 9.2 agree, the scenario is narrowed to one build, and the text says a fixed number of copies of the input is not what the check looks for.

### ✅ Verified - RF6 "Held to the same count" cannot be met where one runtime refuses the input, and the generator has no rule for those inputs
- **Severity:** Medium
- **Evidence:** `specs/nx-ir-format/spec.md`: "Where the format documents that two runtimes compute different values for an input, a case with such an input SHALL still be held to the same count." `design.md` decision 5 sends the two documented differences, a `null` inside a value at `object` and integers outside the safe range, to the generated cases. For two of the forms these take, the TypeScript runtime has no count. Task 7.2 lists "`null`s and empty lists inside lists and objects" and no wide integers at all, although decision 5 promises them, and says nothing about which probes a shape may be paired with. The wide integer also has to reach the two runtimes in different spellings (an `NxValue::Int` and the wrapper), which the case JSON of decision 6 does not mention; bare digits in JSON lose precision in `JSON.parse`.
- **Recommendation:** Say in the requirement what is compared when the format documents that one runtime refuses an input: either such a case is not generated, or both runtimes must agree that it is a boundary failure in one and a count in the other, by a rule the test states. Give task 7.2 the pairing rules (a wide integer and a top-level `null` only at `object` probes), add wide integers to its list, and say that the case file spells a wide integer as the wrapper and the Rust side reads it as the integer. RF1 decides whether Rust is also given the wrapper.
- **Fix:** Requirement three now says the generator does not give a probe a value the format documents one runtime as refusing where another accepts it, naming the two (a `null` as a whole argument at `object`, a wide integer at a typed integer), and that for inputs both accept with documented different values the count is still held equal. Decision 6 has the pairing table and the spelling (the `nx.int` record in the case JSON, `NxValue::Int` in Rust); task 7.2 lists wide integers, the pairing table and the spelling.
- **Verification:** (2026-10-03 17:08) Verified. The requirement forbids generating a value one runtime is documented to refuse where the other accepts, names the two, and keeps the count equal for inputs both accept. Decision 6 and task 7.2 carry the pairing table and the two spellings of a wide integer. That the generated cases only ever give Rust the integer form is part of RF16.

### ✅ Verified - RF8 The corpus extension pins the size of positional arguments only, and three of its details do not match how the corpus works
- **Severity:** Low
- **Evidence:** (1) The input-size requirement lists eight kinds of host input; `inputSizes` is recorded for function cases only, so the rules "props are measured as one record", "each entry of a dispatched batch", content, a state, a patch, arguments by name and the function record are pinned by each runtime's own tests, held together by task 4.5's "the same size the Rust tests assert". Lifecycles already carry props and batches. (2) "No existing file changes" is not achievable as the tasks check it: `manifest.json` is regenerated with the program list and the coverage of every kind (`crates/nx-codegen/src/ir_corpus_tests.rs:778-797`), and task 5.1 itself edits `specs/ir-conformance/README.md`, so 5.1's "`git status specs/ir-conformance` shows no modified file" and 10.3's "shows only the new program" both fail, and `design.md` (Migration) says "The corpus's existing files are unchanged". The spec scenario, which speaks of expected artifacts, results and counts, is achievable. (3) The key for an entrypoint with `arguments` and no `case` is not defined.
