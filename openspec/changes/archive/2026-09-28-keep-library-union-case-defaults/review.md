## Findings

### ✅ Verified - RF1 The rule that turns interface flags into `has_default` is written inline in a struct literal, apart from the `is_required()` rule it must invert
- **Severity:** Low
- **Confidence:** Medium. This is a maintainability point, not a behavior bug. The derivation is correct today.
- **Evidence:** `crates/nx-hir/src/prepared.rs:856-866` builds `UnionCaseField { .., default: None, has_default: !field.is_required && !field.optional, .. }` directly. `UnionCaseField::is_required()` (`crates/nx-hir/src/lib.rs:407-410`) is `!has_default && !optional`. The two are correct only as inverses of each other, and they live in different files. `default` and `has_default` are both `pub`, so any future struct literal can set them out of step. The derivation is exact only because the parser rejects `?` combined with a default (`optional-property-with-default`, `crates/nx-syntax/tests/parser_tests.rs:4553`). An interface field that is optional and not required always means "no default". The comment on `has_default` does not record that assumption. Records already solve the same problem with a named constructor, `EffectiveField::from_interface_field` (`crates/nx-hir/src/lib.rs:744`), which the design cites as the model.
- **Recommendation:** Add `UnionCaseField::from_interface_field(&InterfaceField) -> Self` next to `from_record_field` and `is_required()` in `crates/nx-hir/src/lib.rs`, and call it from `interface_union`. The derivation and its inverse then sit together. Optionally, note in the `has_default` doc comment that `?` and a default are mutually exclusive, which is what makes the derivation exact.
- **Fix:** Added `UnionCaseField::from_interface_field(&InterfaceField) -> Self` in `crates/nx-hir/src/lib.rs`, between `from_record_field` and `is_required()`, with a doc comment saying it is the inverse of `is_required()` and relies on `?` and a default being mutually exclusive. `interface_union` in `crates/nx-hir/src/prepared.rs` now maps `UnionCaseField::from_interface_field` in place of the inline struct literal. The `has_default` field doc now records that the parser rejects `?` with a default (`optional-property-with-default`), so the two flags are never both true. No behavior change: `cargo test --workspace` passes 2554 tests, and rustfmt and clippy on `nx-hir` are clean.
- **Verification:** Confirmed. `UnionCaseField::from_interface_field` (`crates/nx-hir/src/lib.rs:413`) now sits between `from_record_field` and `is_required()`. It sets `default: None` and `has_default: !is_required && !optional`, and its doc comment names `is_required()` as the inverse and states that `?` and a default are mutually exclusive. The `has_default` field doc cites `optional-property-with-default`. `interface_union` (`crates/nx-hir/src/prepared.rs:856`) calls `.map(UnionCaseField::from_interface_field)`, and no struct literal of `UnionCaseField` remains outside `nx-hir/src/lib.rs`. The `UnionCaseField` import in `prepared.rs` is still used. I re-ran the checks: `cargo test --workspace` passes 2554 tests with 0 failures, `cargo clippy -p nx-hir --all-targets` reports no warnings, and `cargo fmt --check -p nx-hir` is clean.

### ✅ Resolved - RF2 Records and component props still spell out the "required" rule inline, so the "one rule" covers union cases only
- **Severity:** Low
- **Confidence:** Low. This is out of the change's stated scope and does not cause a bug. It is recorded so the choice is made on purpose.
- **Evidence:** The proposal says "the union-case field check and the published interface both derive 'required' from one rule", and that holds for union cases. The same expression `default.is_none() && !optional` still appears in `crates/nx-api/src/artifacts.rs:3404` (`record_field_to_interface_field`), `crates/nx-codegen/src/builder.rs:881`, `crates/nx-types/src/infer.rs:2992`, `infer.rs:3722` and `infer.rs:4137` (the local-record and component fallbacks), and `crates/nx-hir/src/lib.rs:730` (`EffectiveField::from_record_field`). Those sites read local declarations, where the expression exists, so they are correct.
- **Recommendation:** No change is needed for this fix. If more consistency is wanted, add `RecordField::is_required()` and use it at those sites in a follow-up. Or close this finding as Resolved (out of scope).
- **Status:** Not addressed. This is outside the change's scope (union-case defaults across a library boundary), and those sites read local declarations where the default expression exists, so they are correct. Recommend closing as Resolved (out of scope) or doing a follow-up that adds `RecordField::is_required()` and uses it at the six listed sites.
- **Verification:** Resolved as out of scope, with the follow-up deferred. The reviewer and the fixer agree that the six record and component sites read local declarations, where the default expression exists, so they are correct and the behavior does not change. A `RecordField::is_required()` helper can come in a separate change. Reopen this finding if the follow-up should land in this change.

## Summary
- The fix is small, correct and targeted. Consumers see imported unions through `interface_union` (the type checker in `infer.rs`, and the `unions.rs` fallback when no raw reference exists), and each imported case field now carries whether it is required. Codegen and the interpreter still read defaults from the declaring module's raw `UnionDef`, where the expression exists, so evaluation is unchanged. The new test shows that. Typegen and the language service do not use the interface-derived union fields for requiredness.
- The new test covers both spec scenarios: a defaulted field is omitted and takes its default, and a required field (`options`) still reports `missing-union-case-field`. It also covers a `?` field. Without the fix, `interface_union` would report `min` and `step` as required, so the test would fail, which is consistent with task 1.3.
- All tasks are complete, and the full Rust suite passes (2554 tests). The two findings are Low-severity maintainability notes. Neither blocks archiving.
