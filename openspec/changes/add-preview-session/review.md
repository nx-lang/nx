# Review: add-preview-session

## Scope
**Reviewed artifacts:** proposal.md, design.md, specs/preview-session/spec.md, tasks.md (all tasks marked done; `openspec validate add-preview-session --strict` passes)  
**Reviewed code:** commit 38c2f11 (`git diff 7d11e04 38c2f11`): packages/previewer/src/{index,program,pointer,session,types}.ts, packages/previewer/test/{fixtures,session,scenario,reload,origins,readme}.test.ts, packages/previewer/{README.md,package.json,tsconfig.json}, docs/deployment.md, docs/deployment-setup.md. `pnpm test` passes (37 tests) and `pnpm run verify:package` packs the package. I also ran throwaway probe scripts against the built package and the question-flow program.  

## Findings

### 🟡 Fixed - RF1 Reload treats every failure of the keep-state attempt as a state mismatch, so a resource limit on the session's own state turns a label fix into a full replay reported as `replayed`
- **Severity:** Medium
- **Evidence:** `packages/previewer/src/session.ts:288-296` catches any `NxIrRuntimeError` from the keep attempt and moves on to the probe and replay. Through `#initialize` (`session.ts:376-381`) the keep attempt passes the current tick's state as the `state` option, and the runtime counts that state as input against `maxInputSize` (`runtime/typescript/src/index.ts:2147-2152`). The state grows as the run goes on, but the props and batches a host sends stay small. I measured the question flow at question 22: state 91, props 2, largest batch 19. With `maxInputSize: 20` (every host input fits), `reload()` with the label-only edit from the "A label fixed on question 22" scenario returned `outcome: "replayed"` and created a second root. It should have returned `kept`. The same session's `setProps({ respondent: "Grace" })` fails with `nx-ir-resource-limit` / `maxInputSize` (`session.ts:234-237`). The README tells hosts to set these limits (README.md:101-105), so this is a realistic setup. A stage-2 UI would show "the state no longer fits" when nothing about the state changed, and it would re-run the whole path on every edit. The same fallback applies when the new program's body throws a runtime error on the current state: the session replays the whole path only to stop at the same step, and the diagnostics of the keep attempt are lost.
- **Recommendation:** High confidence in the minimal fix. In `reload()`, when the keep attempt fails with an `nx-ir-resource-limit` diagnostic, return `{ outcome: "failed", diagnostics }` (or a distinct outcome) instead of replaying, and add a test with `maxInputSize`. There is also a design choice the authors should make (see Questions): should `maxInputSize` apply to the state the session passes back itself? That state is the runtime's own output, not host input. If it should not, measure only the props against the limit (`measureInputSize`) and omit `maxInputSize` from the `setProps` and reload calls. Either way, document in the README that `setProps` and `reload` pass the state as input.
- **Fix:** Took the exemption the Questions section raises, plus the minimal fix. A call that passes back a state (`setProps`, the reload's keep attempt, a props step of a replay) now checks `maxInputSize` against the props alone with `measureInputSize`, raising the runtime's own `nx-ir-resource-limit` / `maxInputSize` diagnostic when they are too large, and runs without measuring the state (`withoutInputLimit` in `session.ts`). In `reload()`, a keep attempt that fails with `nx-ir-resource-limit` now returns `failed` with its diagnostics instead of replaying. Spec, design and README say so. Tests: `options.test.ts` "does not count the state the session passes back as input" (question 22 with `maxInputSize: 20`: `setProps` works and the label reload is `kept`) and "a reload that reaches a limit" (`maxOperations: 800` with a title that costs ~1,000 more: `failed`, old program and tick kept).

### 🟡 Fixed - RF2 `maxTicks` pruning during a replay or reload can drop the reviewer's pre-reload path, against "the old ticks SHALL stay in the tree in every case"
- **Severity:** Low
- **Evidence:** `#add` sets the new tick as current and then prunes (`session.ts:522-523`). `#prune` protects only the *current* path (`session.ts:531-554`). During `#replay` (`session.ts:340-363`) the current path is the new replay root's chain, so the previous path becomes eligible to be dropped, leaf by leaf. Probe: with `maxTicks: 12`, I ran 9 batches and then reloaded with the `rating`→`score` rename. The result was `replayed`, `completed: true`, 12 ticks, and the tick the reviewer was on before the reload had been dropped (`session.ticks.includes(before) === false`). The reload requirement (spec.md:129-130) and the design ("The old ticks remain in the tree in every case, so a host can compare") promise to keep those ticks. The maxTicks rule (spec.md:29-31) conflicts with that promise, and neither the spec nor the code says which rule wins. The `before` reference a host kept then fails `goTo` with `nx-preview-tick`. With the default of 1,000 this only happens in long sessions, but those are the sessions where comparing is most useful.
- **Recommendation:** While replaying (in `replay()` and `reload()`), also protect the path that was current when the call began. Compute the protected set once in `#replay` and pass it to `#prune`. Alternatively, amend the spec and README to say that the old ticks stay subject to `maxTicks`. Add a test that reloads with a small `maxTicks` and checks which ticks are kept.
- **Fix:** `#replay` now holds the path that was current when it began in `#kept`, which `#prune` treats like the current path until the replay ends, so neither `replay()` nor `reload()` drops it. The spec and design now say the reload drops none of the ticks of the path it started from, whatever `maxTicks` says; after the replay, the limit applies again. Test: `options.test.ts` "keeps the path a reload started from while it replays" (your `maxTicks: 12` probe, then a dispatch that prunes back to 12).

### 🟡 Fixed - RF3 Several spec and design claims that the session relies on have no test
- **Severity:** Low
- **Evidence:** The behaviors below work in my probes, but no test pins them:
  - "A dispatch or a props change from a tick SHALL run under the program that rendered it" (spec.md:29). Going back to a tick from before a `kept` reload and dispatching should run the old program. This is the reason the design keeps a program on each tick. `reload.test.ts:169-192` checks only the forward direction (`next.program === fixed`).
  - "An entry that is an action the component emits ... SHALL record none" (spec.md:59-60). `Flow` emits `Completed` (`specs/ir-conformance/question-flow/main.nx:203`). No test dispatches it or checks that it exports with a `null` handler.
  - The design's claim that "a scenario exported across a reload still replays" (design.md, Scenarios section). After a `kept` reload, tokens restart at `h1-*`, so this works only through the recorded pointers.
  - That `maxInputSize`, `maxCallDepth` and `maxRangeLength` are passed to every call (spec.md:9-11). Only `maxOperations` is exercised.
  - That a current path longer than `maxTicks` is kept whole (design.md, Risks). `session.test.ts:264-274` covers only the simple leaf drop.
- **Recommendation:** Add a focused test for each item, using the question-flow program: dispatch from `ticks[0]` after a kept reload and assert `tick.program === flow`; dispatch `{ $type: "Completed", respondent: "x", answered: 1 }` and assert `handlers` is `[null]` in the tick and in the scenario; export a scenario across a kept reload and replay it under both programs; run with `maxInputSize`/`maxCallDepth` small enough to fail; set `maxTicks` below the path length.
- **Fix:** Added a test for each: `reload.test.ts` "ticks from before a reload run the program that rendered them" and "export a scenario that replays by its pointers under either program" (tokens read from the reloaded output, handler pointers checked, replayed under both programs to the same state); `scenario.test.ts` "records no handler for an action the component emits, and replays it" (`Completed`, `[null]` in the tick and the scenario); `options.test.ts` covers `maxCallDepth` (stops a run), `maxRangeLength` (a program with a `0..3` loop runs under 3 and stops under 2), `maxInputSize` (a batch and props refused) and `maxOperations`/`maxInputSize` validation; "keeps a current path longer than the limit whole".

### 🟡 Fixed - RF4 The path-to-steps walk is duplicated between `scenario()` and `reload()`, and so are test helpers
- **Severity:** Low
- **Evidence:** `session.ts:239-258` and `session.ts:307-318` each split `this.path` into root and rest, throw the same "does not start with a first render" error, and map `batch`/`props`/`reload` causes to steps. The only difference is that `scenario()` rejects props steps. In the tests, `failure()` appears in both `session.test.ts:147-155` and `scenario.test.ts:25-33`, and the `rating`→`score` program edit appears twice in `reload.test.ts` (lines 198-202 and 225-229).
- **Recommendation:** Add one private `#pathSteps(): { root, steps: ReplayStep[] }` that both callers use, with `scenario()` failing on a `props` step. Move `failure()` and a `renamedRating()` program builder into `test/fixtures.ts`.
- **Fix:** Added `#pathSteps()`, which both `scenario()` (failing on a props step) and `reload()` use. `failure()` and `renamedRating()` moved into `test/fixtures.ts`.

### 🟡 Fixed - RF5 README leaves out session diagnostic codes and says nothing about tokens restarting after `setProps`/`reload`
- **Severity:** Low
- **Evidence:** README.md:78-80 lists `nx-preview-handler`, `nx-preview-scenario` and `nx-preview-tick`. The package also throws `nx-preview-batch` (`session.ts:225`), `nx-preview-options` (`session.ts:167-169`) and `nx-preview-program` (`program.ts`). `setProps` and a `kept` reload call `initializeComponent`, which restarts the generation at 1, so the new tick's tokens are `h1-*` again. A probe that dispatched the lifecycle's recorded token `h4-1` after a kept reload failed with `nx-preview-handler`. A host that holds an old `h1-n` token from the first render would instead hit whatever handler now carries that token. The README says hosts "never track token numbering" (README.md:21-22) but doesn't warn against holding tokens across these ticks.
- **Recommendation:** List every `nx-preview-*` code in the README. Add one sentence: after `setProps` or a reload, tokens are renumbered from the new render, so hosts should dispatch by handler pointer or read tokens from the current tick only.
- **Fix:** The README now lists every `nx-preview-*` code with what raises it, says that `setProps` and a reload renumber tokens from `h1-1` so a host reads tokens from the current tick only or dispatches by pointer, and no longer says hosts never track token numbering without the "by pointer" condition. It also notes the `maxInputSize` and `maxTicks` behaviour from RF1 and RF2 and that ticks before a reload run the old program.

## Questions
- RF1 (answered in the fix): Should `maxInputSize` bound the state the session passes back to the runtime in `setProps` and `reload`? The state is the runtime's own output, and `maxOperations` already bounds the work that produced it. The answer decides whether to exempt the state or to document and report the failure.
- Replay and reload roots do not link to the tick or path they were replayed from (`cause` is just `initial`). A stage-2 timeline that shows "reloaded run beside the original" would have to keep that link itself. Is that intended, or should a root's cause record its origin (for example `{ kind: "initial", replayOf?: PreviewTick }`)?
  - **Status:** Left for the stage 2 timeline, which is where the need and its shape show up; the reload result already returns the replay's tick, and the old path is now kept through the replay (RF2). Not a defect in this change.

## Summary
- The implementation is small and matches the design closely: the tick tree, branching, dispatch by pointer and by token (with pointer recording), scenario export and replay with stop reports, the three reload outcomes, and origins on every call are all present. Tests check against the conformance program's recorded results and origins, and the README example is type-checked and run.
- One Medium finding. Reload counts any failure of the keep attempt, including a `maxInputSize` limit hit by the session's own growing state, as "the state no longer fits", which causes needless full replays and misleading `replayed` reports (`setProps` fails the same way). The other findings are Low: `maxTicks` pruning breaks the "old ticks stay" promise during a replay, several spec claims have no test, some code is duplicated, and the README has gaps.
